# rkllm-runtime Debian 打包工程

把 Rockchip RKLLM SDK（`rknn-llm-release-v1.3.1.tar.gz`，616 MB）裁打成规范、可安装、装完即用的 deb：
依赖板上自带的 NPU 驱动跑本地 `.rkllm` 模型，开箱提供终端对话命令与 OpenAI 兼容 API。

## 产物

```
工具/dist/rkllm-runtime_1.3.1-17_arm64.deb    13.98 MB   解包 84.2 MB   OrangePi 5 Plus 8G (RK3588)
dist/rkllm-toolkit/packages/*.whl                    x86 主机用的模型转换工具（不进 deb）
```

目标平台：OrangePi 5 Plus 8G（RK3588，aarch64），只构建 arm64（用户确认）。
armhf 的构建能力仍保留在构建器里（`python 工具/编译工具链/make_deb.py --arch armhf`），但已从 `dist/` 移除——
它不再随改动同步，留着只会误导。

包内还包含中英双语 man 手册：`man rkllm`（按 locale 自动选语言）、`man -L zh_CN rkllm`。

## 装完即用：三条命令

```bash
sudo apt install ./rkllm-runtime_1.3.1-17_arm64.deb
rkllm selftest                 # 无模型也能验证安装（12 项；无 NPU 时库/模型预期 FAIL）
rkllm chat qwen2.5-1.5b        # 本地对话
rkllm serve qwen2.5-1.5b       # OpenAI 兼容 API（或 systemctl enable --now rkllm-server）
```

`/usr/bin/rkllm` 是统一入口 launcher：把 `/usr/lib/rkllm/current` 挂进
`sys.path` 后调用新栈 `rkllm.cli`（FastAPI 服务端 + 推理子进程）；服务端依赖
走 apt（`python3-fastapi / python3-uvicorn / python3-pydantic`）。详见
[USAGE-CHAT-API.md](USAGE-CHAT-API.md)。

## 构建

```bash
python 工具/编译工具链/make_deb.py --arch arm64 --emit-tree     # 默认 profile=full（目标板唯一构建）
python 工具/编译工具链/make_deb.py --arch arm64 --profile slim  # 剔除自带 OpenCV，改依赖系统 libopencv-dev
```

`--emit-tree` 在 staging 目录已存在时会报错而不是自行删除（本机的安全策略会拦截
Python 进程内的删除操作），需要先 `rm -rf build/tree-arm64`，或用 `--tree-dir <path>` 指定新位置。

常用参数：`--package`（包名，默认 `rkllm-runtime`）、`--revision`、`--maintainer`
（默认 `RedStone <DMRedStone@users.noreply.github.com>`，可用 `--maintainer` 覆盖）、`--source`、`--out`。
设置环境变量 `SOURCE_DATE_EPOCH` 可改变打包时间戳。

## 校验

```bash
python 工具/编译工具链/verify_deb.py 工具/dist/rkllm-runtime_1.3.1-17_arm64.deb   # 静态：包结构（省略参数则自动发现）
python 工具/编译工具链/crosscheck_deb.py                                     # 与上游 tarball 逐文件比对
python 工具/build/tree-arm64/usr/bin/rkllm selftest                            # 自检：无模型也能跑（12 项）
python tools/verify_board.py --host 192.0.2.10:8080 --key 密钥      # 板端端到端验收（10 项）  〔脚本已归档：工具/rkllm-common-tools/legacy；改用 health_check.py --full〕
```

前三条可在开发机上跑；最后一条针对运行中的服务实测，覆盖那些只有真实硬件才暴露的问题：

| 检查 | 防的是什么 |
| --- | --- |
| `long system message answered` | 带长 system 的请求挂起（模型不输出 EOS） |
| `system-only probe answered` | 客户端探测模型时发的空回合请求被 400 拒绝 |
| `no template poisoning after [B]` | system message 污染后续所有请求（内置模板被禁用） |
| `oversized prompt refused` | 超长输入让 runtime 越过 KV cache 崩溃 |
| `service still alive, no errors` | 崩溃后服务进程消失 |

当前状态：FAIL=0 / WARN=0（88 项检查：ar 容器、control 字段、md5 完整性、
root 属主、权限位、目录覆盖、依赖格式、维护脚本副作用、install() 逃逸、CLI 渲染/语法/依赖、
systemd 单元与转义、中英文 man page 结构、时间戳一致性、卸载残留面，
以及 conffile 面：`conffiles` 声明、配置文件双语且不含版本号、
每个参数都有配置项、`postrm` 在 remove 时也删除它；另含版本单源一致性检查）。

交付前还做了两类真实执行验证：

- `rkllm selftest`——用内置假引擎跑通 CLI、HTTP 路由、SSE 流式、错误码、排队溢出，
  12 项中 10 项通过、2 项因缺真实库与 NPU 预期失败；

- 变异测试——故意注入"未渲染占位符 / 第三方 import / 错误 helper 路径 / 绝对 DESTINATION /
删掉 `conffiles` 声明 / `postrm` 不删配置文件 / 配置文件里写入版本号 / 新增未记录的参数"，
确认校验器会精准 FAIL，恢复后归零。

## 安装与使用

```bash
sudo apt install ./rkllm-runtime_1.3.1-17_arm64.deb      # 或 dpkg -i
rkllm info                                    # 确认 NPU 驱动、库、模型搜索路径
rkllm chat qwen2.5-1.5b                       # 本地对话
rkllm serve qwen2.5-1.5b --host 0.0.0.0       # 对外 API
gcc demo.c -o demo $(pkg-config --cflags --libs rkllm)   # 自己写 C/C++ 程序时
cp -r /usr/share/rkllm-runtime/examples/rkllm_api_demo ~/demo && cd ~/demo/deploy && ./build-linux.sh
```

模型不在包里：`.rkllm` 需在 x86 主机上用 `dist/rkllm-toolkit/` 转换，流程见 `USAGE-CHAT-API.md` §5。

卸载：`sudo apt remove rkllm-runtime`，详见 `FILE-MAP.md` 第 5 节的"无残留"证据。

## 目标板：OrangePi 5 Plus 8G（RK3588）

- 架构 arm64，SoC 自动识别为 `rk3588`，锁频用 `/usr/bin/rkllm-fix-freq-rk3588`。

- NPU 驱动由板端镜像提供（本包不含、不打 DKMS）。确认驱动就绪用
`sudo cat /sys/kernel/debug/rknpu/version` 或 `ls -l /sys/class/drm/renderD*/device/driver`，
`rkllm info` 也会替你检查。注意 `/dev/rknpu` 不存在是正常的——0.9.x 驱动把 NPU 注册为
DRM render node，不创建该设备节点（这一点曾导致服务被 systemd 条件误挡，见 changelog 1.3.1-5）。

- 8G 内存建议跑 1.5B~4B 量化模型；7B 量化需压 `--context 2048` 并预留 swap。
