## 4.1 新增组件：`/usr/bin/rkllm`、服务单元、prerm

这部分不是"改写上游"，而是本仓库新增的功能，目的是让包做到"装完即用"。上游发布包里没有任何预编译可执行文件，示例全是要板端编译的 C++ 源码，异步那套 Flask 示例还要 pip 装 flask、且锁频脚本用相对路径。三条路都不满足"安装后能直接本地对话并提供 API"。

### `/usr/bin/rkllm`（约 1730 行，纯标准库）

| 子命令 | 作用 |
| --- | --- |
| `rkllm chat <model>` | 交互式 REPL：`user>/bot>`、`/help` `/clear` `/set <参数> <值>` `/exit`，Ctrl-C 调 `rkllm_abort` 中断生成 |
| `rkllm run <model> "文本"` | 单次推理，只输出答案，便于脚本化 |
| `rkllm serve <model>` | OpenAI 兼容 HTTP 服务 |
| `rkllm list` | 列出可发现的 `.rkllm` 及搜索路径 |
| `rkllm info [--json]` | SoC / `/dev/rknpu` / 库 / python / 模型搜索路径诊断 |
| `rkllm selftest` | 不依赖模型与 NPU 的端到端自检 |

设计要点与原因：

| 决定 | 原因 |
| --- | --- |
| 用 ctypes 直接调 `librkllmrt.so`，不编译 C++ | 板端通常没有 cmake/g++，编译会把"装完即用"变成"装完先配工具链"。所有结构体按 `/usr/include/rkllm/rkllm.h` 逐字段对齐（`RKLLMExtendParam`/`RKLLMParam`/`RKLLMInput`/`RKLLMInferParam`/`RKLLMCallback`…） |
| 只用标准库（无 flask/gradio/requests） | 否则要把 `pip install --break-system-packages` 写进文档，等于让用户污染系统 Python。校验器会扫描脚本正文，出现第三方 import 直接 FAIL |
| 模型名解析（裸名 + 搜索路径） | 让 `rkllm chat qwen2.5-1.5b` 这种短命令成立；搜索目录不由包创建，避免卸载时因目录非空而残留 |
| 锁频走 `/usr/bin/rkllm-fix-freq-<soc>` 绝对路径 | 修掉上游 `subprocess.run("sudo bash fix_freq_X.sh")` 依赖 CWD 的隐性失败（失败时只是静默不锁频，性能下降但无报错，极难排查） |
| SOC 自动探测（`/proc/device-tree/compatible`） | 省掉必填的 `--target_platform`，同时保留 `--platform` 覆盖 |
| 推理缓冲每次运行后释放 | `c_char_p` 指向的 bytes 必须活到 `rkllm_run` 返回；早期实现用全局 list 累积，长跑服务会持续涨内存。现改为 run 级 list，run 结束即清空 |
| API key 走环境变量 `RKLLM_API_KEY` 优先，比较用 `hmac.compare_digest` | 命令行 `--api-key xxx` 会让密钥出现在 `ps aux` 与 `systemctl status`，同机其他用户可见；常量时间比较避免时序攻击 |
| 不调用 `rkllm_set_chat_template` 安装 system prompt（1.3.1-4 修复） | 该调用会让 runtime 禁用模型内置的对话模板解析（runtime 自己会打 warning）。之后模型收到没有特殊 token 的裸文本：乱答（把提问当考卷题目续写）、常常不输出 EOS（表现为请求一直不返回）。更糟的是该设置对整个 handle 生命周期有效——客户端发过一次带 system 的请求（OpenWebUI 生成会话标题时必发），之后所有请求（含不带 system 的）全被污染，直到重启。现改为把 system 文本前置拼进 prompt，内置模板保持完好。`set_system_prompt()` 方法保留但加了 `USE WITH CARE` 警告注释 |
| 非流式响应带上 token 估算值（1.3.1-3 修复） | `_openai_response()` 被调用时漏传 `prompt_tokens`/`completion_tokens`，参数默认 0，于是每条非流式响应的 `usage` 恒为 0，聊天客户端显示 "0 tokens"。已由自检用例 `usage reported, not zeros` 锁定 |
| 绝不向 C API 传 NULL 指针（1.3.1-2 修复） | `rkllm_set_chat_template` 的 `prompt_prefix`/`prompt_postfix` 原被传成 `None`。runtime 对这两个参数无条件解引用，于是任何带 system message 的请求（所有聊天客户端都会发）都会段错误、整个服务进程消失。上游 C++ demo 对此的写法是 `rkllm_set_chat_template(h, "", "<｜User｜>", "<｜Assistant｜>")` —— 永远是真实字符串。现改为传 `b""`，并新增自检用例 `no NULL passed to the C API`（注入记录型假库，逐个检查传给 C 的参数非 NULL，无需模型即可运行）锁定 |
| HTTP 层用 `ThreadingHTTPServer` + 单锁 + 计数信号量 | NPU 一次只能跑一个请求，但"第二个请求立刻 503"对客户端不友好。现在允许排队，超限才 503 并带 `Retry-After` |
| 客户端断开即 `rkllm_abort` | 否则客户端已走、NPU 还在白算 |
| `--fake-engine` + `selftest` | 让整套 CLI/HTTP/SSE/队列逻辑可以在没有模型、没有 NPU、甚至没有真库的机器上被真实执行验证 |

### 服务单元与服务化

- `/usr/lib/systemd/system/rkllm-server.service`：刻意不写 `ConditionPathExists`（早期版本曾写 `ConditionPathExists=/dev/rknpu`，而 0.9.x 驱动把 NPU 注册为 DRM render node、根本不创建该节点，于是单元在正常的板子上被静默跳过——1.3.1-5 已删除）；`ExecStartPre` 校验 `RKLLM_MODEL` 非空；`Restart=on-failure` + `StartLimitBurst=5`；`LimitNOFILE=102400`。单元里用 `$$VAR` 转义（systemd 会自行展开 `$VAR`，不转义会把空串传给 `/bin/sh`，使校验恒失败——本轮实测踩到并修正的点）；两个可选项 `RKLLM_PLATFORM_ARG`/`RKLLM_EXTRA_ARGS` 刻意不加引号，未设置时在 shell 里整个消失。

- `/etc/default/rkllm-server`：dpkg conffile，中英双语逐参数注释（21 个参数各有专用配置项 + 注释形式的可选示例），详见 §4.2。

- 不 enable 不 start：是否开机跑服务由使用者决定。

### `prerm`（新增的维护脚本）

包提供单元但不 enable，可是操作者一旦 `systemctl enable`，`/etc/systemd/system/...wants/` 下的软链是 dpkg 不认识的——卸载后会留下悬空链接。因此新增 `prerm`：`deb-systemd-helper stop`；`postrm` 里 `deb-systemd-helper purge` 清掉软链与状态，再 `daemon-reload`。

## 4.2 服务配置文件的持久性设计（1.3.1-12）

用户的要求是：配置文件放在 `/etc`、升级不改动、卸载同步删除、"如同其他软件一样"。
后两条在 dpkg 的语义里是冲突的（conffile 升级保留、但 `remove` 不删），取舍如下。

| 决策 | 做法 | 理由 / 代价 |
| --- | --- | --- |
| 位置 | 仍用 `/etc/default/rkllm-server` | 这是 Debian 服务环境文件的标准位置（`/etc/default/grub` 等），单元已用 `EnvironmentFile=` 指向它，换路径只会带来迁移成本 |
| 升级不改动 | 声明进 `DEBIAN/conffiles` | conffile 是 dpkg 里唯一"升级时保留本地修改"的机制 |
| 卸载同步删除 | `postrm` 的 `remove | purge`分支`rm -f` |
| 永不被升级改写 | 模板正文不含 `@VERSION@`，也不含任何版本串 | dpkg 只在"包里这份 conffile 的内容发生了变化"时才重写它。正文若随版本变，每次升 revision 都会覆盖用户文件，并把为放密钥而设的 `chmod 600` 复位成 0644。校验器 `conffile content` 规则守住这一条 |
| 每个参数一个专用配置项 | 21 个参数各有 `RKLLM_*`（见下） | 用户要求"给每个参数配置一个可选配置"。为此给 `rkllm serve` 的每个选项加了环境变量回退 |
| 中英双语 | 每个参数一段 EN + 中文，附注释形式的可选示例 | 用户要求；`conffile content` 规则会检查双语与"每个参数都有一个 `#RKLLM_X=` 示例" |
| 解析失败不致命 | 非法值写 journal 后回退默认 | 配置里一个手误若让 argparse 报错，服务会以 `status=2` 静默失败——正是 1.3.1-6 踩过的坑 |

21 个专用配置项（`RKLLM_MODEL` 必填，其余可选；`RKLLM_EXTRA_ARGS` 是兜底）：

```
RKLLM_MODEL  RKLLM_HOST  RKLLM_PORT  RKLLM_API_KEY  RKLLM_PLATFORM_ARG
RKLLM_MODEL_DIR  RKLLM_LIB  RKLLM_CONTEXT  RKLLM_MAX_NEW_TOKENS  RKLLM_THREADS
RKLLM_NO_FREQ_LOCK  RKLLM_SYSTEM  RKLLM_NO_HISTORY  RKLLM_TOP_K  RKLLM_TOP_P
RKLLM_TEMPERATURE  RKLLM_REPEAT_PENALTY  RKLLM_MAX_QUEUE  RKLLM_QUEUE_TIMEOUT
RKLLM_QUIET  RKLLM_EXTRA_ARGS
```

实现方式：`option_default(name, kind, fallback, enabled)` / `option_flag(name, enabled)` 读 `RKLLM_<NAME>`，
只对 `serve` 生效（`add_common_arguments(serve, env=True)`、`add_sampling_arguments(serve, env=True)`）——
交互式 `chat`/`run` 不读这些变量，免得一个已 `export` 的 `RKLLM_TEMPERATURE` 悄悄改变对话行为。
`RKLLM_MODEL_DIR`、`RKLLM_LIB`、`RKLLM_API_KEY` 本来就有环境变量入口，无需改动。
argparse 只在选项缺省时使用 default，因此命令行参数永远优先。

从 ≤1.3.1-11 升级的一次性提示：那些版本里该文件是普通文件而非 conffile，dpkg 无法判断磁盘上这份
是"用户改过的"还是"包自带的"，于是升级到 12 时会问一次 `Configuration file '/etc/default/rkllm-server' ... [default=N]`。
选 N（默认）保留现有设置，选 Y 则装上新模板（`RKLLM_MODEL` 为空，需重填）。从 12 往后不再有提示。

## 5. 卸载无残留的证据

1. dpkg 清单覆盖全部：包内 402 个条目，全部列在 `/var/lib/dpkg/info/rkllm-runtime.list`；`md5sums` 与 data.tar 的文件集合完全一致（校验器已逐项比对）。

1. 维护脚本不产生任何新文件：`postinst` 非条件动作是 `ldconfig` 与 `systemctl daemon-reload`（只刷缓存），另有一个 `is-active` 守卫的 `restart`（只重启操作者原本就启动过的服务）；`postrm` 做 `ldconfig` + `deb-systemd-helper purge`（清掉操作者 enable 产生的软链）+ `systemctl daemon-reload`，并 `rm -f /etc/default/rkllm-server`（唯一一处删除动作，见 §4.2）。校验器扫描三个脚本正文（剔除注释后）确认无 `rm -rf`、`mkdir -p /usr`、`> /etc/`、`useradd`、`apt-get`、`pip install`、`curl`/`wget`；`systemctl` 只允许 `daemon-reload`/`daemon-reexec`/`is-active`/`restart`，且出现 `restart` 必须同时有 `is-active` 守卫；`rm -f` 只允许作用于 `conffiles` 里声明的那一个文件（规则 `postrm deletes the conffile` 精确校验路径）。

1. 不写 `/usr/local`、不写 `/tmp`、不建用户、不编译 DKMS、不复制模型：运行时绝不会生成游离文件。

1. 示例编译产物不会落在系统目录：示例源码装在只读的 `/usr/share`，README 要求先复制出去；被改写的 CMake 把 install 前缀指向 build 目录，所以即便用户直接 `make install` 也写不进系统路径。

1. install() 规则已钉死在 build 树内：校验器 `install() sandboxed` 项扫描包内所有 `CMakeLists.txt`（剔除注释后）的每条 `install(DESTINATION ...)`，凡以 `/`、`${CMAKE_INSTALL_PREFIX}`、`$ENV{` 开头的一律 FAIL。已做变异测试：把旧写法放回去 → `FAIL=1`（精确指向该文件），改回后 → `PASS`。

1. 新增组件同样受校验：`cli rendered`（无残留 `@TOKEN@`）、`cli shebang`（`#!/usr/bin/python3`）、`cli syntax`（`ast.parse`）、`cli dependencies`（无第三方 import）、`cli helper paths`（引用的 `/usr/bin/rkllm-fix-freq-*` 确实在包里）、`unit escaping`、`unit not self-enabling`。同样做过变异测试：注入 `import requests` + 篡改一个 helper 路径 → 两项精准 FAIL，恢复后归零。

1. 私有目录随包消失：`/usr/lib/rkllm-runtime`、`/usr/include/rkllm`、`/usr/include/rknn`、`/usr/share/rkllm-runtime`、`/usr/lib/systemd/system` 等包私有目录在卸载后为空即删除；`/usr`、`/etc`、`/etc/default`、`/etc/ld.so.conf.d`、`/usr/share` 这些共享目录只会被 dpkg 尝试删除（非空即保留，脚本里不会去 `rm -rf` 它们）；`/etc/ld.so.conf.d/rkllm-runtime.conf` 由 dpkg 删除，`postrm` 再跑一次 `ldconfig` 清掉缓存里的 `librkllmrt.so`。

## 6. 已知限制 / 使用注意

- 目标系统需 glibc ≥ 2.29（Ubuntu 20.04+ / Debian 11+），否则运行时报 symbol 找不到。

- 压缩包体是 xz，需要 dpkg ≥ 1.15.6（Debian 6+ / Ubuntu 10.10+），RK3588/RK3576 常用镜像都满足。

- `libgomp1`（OpenMP）是硬依赖，缺了会在加载时失败；已在 Depends 里声明。

- multimodal 示例需要 OpenCV：`full` profile 自带 prebuilt OpenCV（约 56 MB），`slim` profile 依赖系统 `apt install libopencv-dev`。

- 只交付 arm64：`--arch armhf` 的构建能力仍留在 `tools/make_deb.py` 里（改回默认即可用），
但不是交付目标，`dist/` 里也只有 arm64 产物。历史 armhf 包已删除——它缺 man 手册与后续所有修复。
