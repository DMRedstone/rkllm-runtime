## 0. 工程概况

把 Rockchip RKLLM SDK 裁打成规范、可安装、卸载无残留的 Debian 包，并提供 OpenAI 兼容的板端推理服务与 MCP 连接器。

| 项 | 内容 |
|---|---|
| 构建 | 默认调用 `dpkg-deb`（`--packer ar` 保留纯 Python 回退）；入口 `工具/编译工具链/make_deb.py` |
| 校验 | `verify_deb.py` 结构/策略/卸载面自检；`crosscheck_deb.py` 与上游 tarball 逐文件比对；`release_check.py` 版本/键数/caps/deb 一致性 |
| 服务 | `输入/rkllm-runtime-1.3.1/src/rkllm/`：FastAPI、worker 子进程、UDS 帧协议、SSE、队列、supervisor |
| 连接器 | `本地模型连接器/rkllm/`：stdlib MCP stdio，四版协议、6 工具、job、取消传导 |
| 配置 | 84 键 TOML/conffile；`/etc/default/rkllm-server` 由 dpkg 作为 conffile 管理 |
| 交付 | `工具/dist/rkllm-runtime_1.3.1-21_arm64.deb`（构建产物，不入库）；459 文件 / 14.01 MB / 解包 84.3 MB |

### 0.2 工程红线

1. 不向 C API 传 NULL 指针；结构体与 bytes 必须活到 `rkllm_run` 返回。
2. 包内文件必须在 `dpkg` 清单内；安装期不写清单外路径。
3. `/dev/rknpu` 不是 NPU 判据；以 debugfs/DRM/驱动节点多信号判断。
4. 所有影响行为的参数必须进配置表；不静默忽略、不静默改变客户端契约。
5. 失败必须可观测：日志、`/health`、`/metrics`、错误体至少一处留痕。

## 1. 2026-10-14 ～ 10-18：1.3.1-1 ～ 1.3.1-12

### 1.1 工程起点

- 上游只提供 CMake 源码与库，没有可直接安装的 CLI/服务；本仓库补齐 `rkllm` 命令、systemd 单元、man、conffile 与 deb 打包链。
- 构建机没有 `dpkg-deb`、`ar`、`lintian`，因此 `make_deb.py` 直接生成 ar 容器与 tar.xz，`verify_deb.py` 承担 lintian 的结构检查。
- 目标板不参与构建；采用「静态校验 + `rkllm selftest`（fake engine）+ 变异测试 + 板端实测」四层验证。

### 1.2 早期缺陷与修正

|---|---|---|

| 1.3.1-2 | NULL 指针段错误 | `set_chat_template` 的 prefix/postfix 改传空串，不再传 NULL |

### 1.3 打包与运行约定

- 安装布局：`/usr/bin/rkllm`、`/usr/lib/<triplet>/librkllmrt.so`、`/usr/include/rkllm/`、`/usr/share/rkllm-runtime/examples/`、`/usr/lib/systemd/system/rkllm-server.service`、`/etc/default/rkllm-server`。
- 卸载无残留的判据：`/var/lib/dpkg/info/rkllm-runtime.list` 覆盖全部文件；`postinst`/`postrm` 只执行 `ldconfig`、systemd 重读与删除那一个 conffile。
- 交付标准（每次改动后）：`make_deb.py --arch arm64` → `verify_deb.py` → `crosscheck_deb.py` → `rkllm selftest`，四项全绿才可交付。

### 1.4 早期验证与教训

- 变异测试必须逐个、小步执行并直接核对产物内容，不能只信脚本 print。
- 测试工具必须能区分「服务不可达」「鉴权失败」「队列满」「请求级失败」，否则会把故障误判为通过。
- 板端真实模型的能力与 host 上 fake engine 差异很大；涉及 NPU 生命周期的改动必须上板。

##### 一、脚本清单

运行顺序由 `run_all.py` 编排，文件名不带序号——脚本名同时也是合法的模块名，
`import` 与命令行都按常规 Python 习惯使用，顺序只在编排器里表达一次。所有
脚本共享同目录的 `board_api.py`，但仍可 `python llm_stress.py` 单独运行。

- `board_api.py` — 共享 HTTP 客户端：URL 与认证头构造、超时、SSE 解析、
  健康判定（2xx 但空体也算可达，vLLM 就这么回）、百分位算法。工具链内唯一
  副本；旧 `本地模型连接器/` 已裁撤，不再做双份比对。

- `quality.py` — 内容**形态**分析（不是质量评分）：截断与 overrun、重复/退化、
  乱码、流式与非流式一致性、并发响应归属。纯函数、无 HTTP 依赖，压测采集与
  报告渲染共用同一套口径。语义好坏（改写是否保留术语）它不判，只能人读输出。

###### 源码级回归（不需要模型 / NPU / 板子）

1.3.1-16 起旧单文件 `cli/rkllm.py` 已删除，原先直接 import 它的
`verify_server.py` 一并退役；对应回归全部迁到新栈 pytest：

```bash
cd 输入/rkllm-runtime-1.3.1
PYTHONPATH=src python3 -m pytest tests -q      # 373 项
```

覆盖 FakeEngine、worker 帧、配置键生效性/魔法数、MCP 协议与 job、抽取 fixture、
`/v1/responses` 事件序列等；改完服务端源码**先跑 pytest 再上板**，秒级完成。

###### 入口与预检

- `run_all.py` — 一键编排入口（推荐从这里开始）
依次执行：预检 → 压测 → 仿真 → 崩溃复现 → 生成报告。
板端 NPU 是独占资源，脚本自动串行化，并在步骤之间轮询 `/health` 等待守护进程把崩溃的服务拉起。

- `health_check.py` — 服务健康 / 连通性检查（由三个同功能脚本合并而成，详见第二节）
默认做基础 3 项（`/health`、`/v1/models`、端到端对话），数秒完成，适合压测前预检；
加 `--full` 追加 7 项深度检测（鉴权拒绝、长 system 应答、system 模板污染、system+多轮、
system-only 探测、流式 `[DONE]` 收尾、超长 prompt 拒绝），适合交付 / 换板后的完整体检。
退出码 0=健康、1=异常，可直接接入 CI。

###### 合成负载链（由 `run_all.py` 自动串行编排）

- `llm_stress.py` — 压力与极限测试
  除延迟/吞吐/并发/耐力外，含三段内容形态用例：**A2** 流式与阻塞的内容一致性
  （不只比 TTFT）、**A3** 并发响应归属（每请求埋唯一标记，检测串包）、**A5**
  输出形态（finish_reason 分布、overrun 实测、退化分、乱码）。
`A` 单请求延迟基线 · `A2` 流式 vs 阻塞（首字延迟）· `B` 并发→吞吐曲线（p50/p90/p99）·
`C` 持续耐力（延迟漂移）· `D` 过载 / 背压 · `E` 超长 prompt 守卫 + 畸形 body。
段序「先温和、后敌意」：可能压垮服务的用例放最后，每段后做存活探测以精确定位崩溃点。

- `llm_simulate.py` — 客户端行为仿真
握手 / 多轮对话 / 长文档粘贴 / 中断（流式中断线）/ 会话切换 / 后台标题（与对话并发）/ 多 VU 混合负载。

- `crash_probe.py` — 并发崩溃隔离复现
逐个隔离触发条件并量化复现率（`--repeat N`）。

- `make_report.py` — 合成负载报告生成（读 `results/stress_*.json` + `simulate_*.json`）

- `soak_test.py` — 长时浸泡测试（N3 性能基线：首 token p95、改造前后压测对比）

- `export_csv.py` — 结果导出 CSV（并发曲线 / 压测明细 / 仿真时间线，Excel 友好）

###### 真实公文场景链（独立支线：语料 → 测试 → 报告）

- `docx_corpus.py` — 真实 docx → 纯文本语料 + 规模画像（只读源文件，不改动原件；语料清单在文件顶部 `CORPUS` 中配置）

- `llm_realworld.py` — 真实公文场景测试
`A` 串行任务 / `B` 分段处理 / `C` 多轮迭代 / `D` 并发 / `E` 批量；内置崩溃自愈重试。

- `make_rw_report.py` — 真实场景报告生成（自动合并各组最新结果 + 语料画像）

运行期自动产生：`results/`（结构化 JSON、`realworld_samples/` 完整输出）、`corpus/`、`csv/`、`report*.html|md`。

##### 四、快速开始

###### 0. 连接配置（2026-11-10 起）

工具链各脚本可直接复用 `rkllm-mcp` 连接器安装目录的 `mcp.toml`，**不需要手动传 key**：

```bash
python health_check.py --full          # 无参数即可：自动读连接器配置
```

优先级：`RKLLM_HOST` / `RKLLM_KEY` / `RKLLM_API_KEY` 环境变量 > `mcp.toml` 的
`target_endpoint` / `target_api_key`；配置文件路径可用 `RKLLM_MCP_CONFIG` 覆盖。
实现在共享层 `board_api.py` 的 `default_host()` / `default_key()`；key 只在进程内存中使用，
不打印、不写日志、不入库。`--host` / `--key` 显式传参仍然有效。

**板端元信息自动读取（2026-11-11 起）**：`board_api.fetch_server_meta()` 从板端
`/health` 读取 `model` / `version` / `context_len` / `model_class` / `npu`，由各结果产出
脚本写入结果 JSON 的 `meta` 字段；报告生成器只格式化该字段，不联网、不写死型号、
硬件或版本号。`llm_stress.py --context-len` 也改为从 `/health` 自动取值，读不到才需
显式指定。换模型 / 换板 / 升级后，报告与压测守卫会跟着板端自动变化。

##### 五、使用须注意（来自实测结论）

###### 语料必须由人提供（设计边界，不是待补的能力）

自动化能覆盖的是**合成负载**（`run_all.py` 串起来的那条链）：固定 prompt、递增长度、
并发阶梯、崩溃探针——它们不需要语料，回答的是"这块板子撑不撑得住"。

真实场景链（`docx_corpus` → `llm_realworld` → `make_rw_report`）必须人工准备：

- `docx_corpus.py` 顶部的 `CORPUS` 列表指向你手上的 docx（脚本只读，不改原件）；
- `llm_realworld.py` 的 A~E 组任务写死，但"整篇润色 / 长文改写"必须投喂真实文本才有意义；
- 输出质量只能人看 `results/realworld_samples/*.txt` 判断——术语有没有保留、格式合不合规，
  脚本打不出这个分。

两条原因：① 语料通常含业务内容，不该进仓库；② "改写得好不好"不是脚本能给的分，
把判断自动化只会得到一个看着精确、实际无意义的数字。

所以标定配置时的分工是固定的：**机器量延迟与吞吐，人给文本与质量结论**。报告只负责把
量到的东西摆清楚，最后填进 `run_all.py --host/--key` 的那组参数由人确认。

###### 历史观察（早期版本，勿当作当前行为）

以下条目来自早期版本的实测，部分已在后续版本修复。**它们不是当前版本的结论**；
每次换模型 / 换板 / 升级后应以本轮结果重新判定，不要照抄：

- 曾观测到 `max_tokens` 不被遵守、超发且 `finish_reason` 仍为 `stop`；后续版本已按请求上限截断。
- 曾观测到长输出（约 1000 token 以上）退化为重复字符流并串入无关英文；后续版本未复现。
- 曾在长 prompt 下偶发进程崩溃，依赖守护进程拉起；本轮 A~E 全组真实公文测试观测到 0 次崩溃。
- 曾在特定窗口下建议单请求输入控制在约 2000 字；实际窗口由板端 `/health` 的
  `context_len` 声明，脚本已改为自动读取，不再写死。
- 单 NPU 上下文串行，并发无吞吐增益、只增加排队延迟——这条属于架构约束，仍成立。
- 流式能让首字显著提前出现，对话式前端应使用流式——这条属于协议特性，仍成立。

###### 职责边界（2026-11-11 定）

- **测试脚本**：负责采集。板端元信息（模型 / 版本 / 上下文 / NPU）由
  `board_api.fetch_server_meta()` 从 `/health` 自动读取，随结果 JSON 的 `meta` 字段落盘。
- **报告生成器**：只把结果数据格式化为可读表格，**不下结论、不做可用性判断、不给工程建议**，

### 大模型测试工具链开发记录 · 2026-10-19：内容形态覆盖

#### 2026-10-19：内容形态覆盖（截断 / 退化 / 串包 / 流式一致性 / overrun）

##### 一、起因

使用方提的准确：**性能测试跑完，无法验证返回的内容是否可用，最后还得人读**。

这句话把「可用」劈成了两半：

| | 例子 | 谁来判 |
| --- | --- | --- |
| **语义可用性** | 改写是否保留术语、摘要是否抓到重点、公文格式是否合规 | 只能人读 |
| **形态可用性** | 是否被截断、是否塌成重复词流、是否为串包（拿到别人的答案）、流式是否丢字 | **机器能判** |

第二类在改造前几乎是空白：`finish_reason` 只在真实场景脚本里记了一笔，报告里那句
「均为 stop」是**写死的断言**而非统计；并发段只看状态码与延迟，串包完全看不出来；
流式只比首 token 延迟，不比内容。

##### 二、新增 `quality.py`

纯标准库、无 HTTP 依赖的形态分析模块，压测采集与报告渲染共用同一套口径。

| 函数 | 判什么 | 阈值来源 |
| --- | --- | --- |
| `finish_reason_stats` | `stop` / `length` / 空响应分布 | `length` 即被硬截断 |
| `overrun_stats` | 实际 token ÷ 请求 max_tokens | 配置项 `overrun` 的依据 |
| `degen_score` | 8-gram 重复率（0.7）+ 字级熵（0.3） | 实测：正常长文本 0.00，重复词流 0.74 |
| `longest_repeat_run` | 最长整段复现长度 | 正常 0 字，退化 132 字 |
| `mojibake_ratio` | U+FFFD 占比 | 多字节字符在字节预算处被切断 |
| `stream_parity` | 阻塞与流式拼接的一致性 | `identical`/`equivalent`/`mismatch`/`empty` |
| `check_attribution` | 并发响应是否回到自己的请求 | `foreign>0` 即串包 |

**退化分为什么是「重复 0.7 + 熵 0.3」而不是各半**：实测区分度差一个量级——正常长文本
的 8-gram 重复率 0–0.1，重复词流能到 0.9；而两者的字级熵只差 6.2 vs 3.5。各半权重
会让「字符种类多但整段复现」的塌陷（`杭州是一座很好的城市。` ×12）只判到 0.52，卡在
可疑区间。改权重后同一文本 0.74，稳定越过 0.55 的判定线。

阈值：`<0.35` 正常，`0.35–0.55` 可疑（建议人工复核），`>0.55` 退化。

### 大模型测试工具链开发记录 · 2026-10-20：新增 verify_server.py

#### 2026-10-20：新增 verify_server.py（服务端源码级回归）

##### 一、为什么加

1.3.1-15 被外部审查抓到 4 个**新引入**的问题，全是 selftest 覆盖不到的路径：
`finally` 里的锁释放、看门狗线程的生命周期、慢速 socket、`stop` 与 usage 的耦合。
这些问题都没有触发过崩溃，也都不需要模型，但每一个都足以让服务在特定条件下
永久不可用或悄悄算错账。缺一条能秒级复现它们的回归，下次修改还会再犯。

##### 二、怎么做的

- 直接 `importlib` 加载 `cli/rkllm.py` 源码（不是装好的命令），因此能拿到
  `_stream_guard`、`_read_raw_body`、`JSON_HINT` 这些内部对象；
- 起真 HTTP 服务（`Server` + 假引擎），断言走真实协议路径——不是直接调函数，
  因为问题恰恰出在协议层（keep-alive 复用、Content-Length 声明、超时）；
- 要测"stderr 不可写"这种生产环境才有的条件，用两个测试桩：
  `_BrokenStderr`（写就抛 `BrokenPipeError`）与 `_StubThread`（`start()` 同步
  执行 target、`is_alive()` 恒返回 True，逼出 join 超时分支）；
- 路径不写死：默认从脚本位置推导仓库内的源码，可用 `--source` 或 `RKLLM_SOURCE`
  覆盖；纯标准库，只读，不占端口。

##### 三、踩到的坑

- 第一版想用"真让推理线程 hang"来测锁释放，结果生成器挂在 `sink.get()` 上，
  主线程既不能 `close()` 也拿不到控制权，测试直接死锁。改用 `_StubThread` 后
  才走到目标分支；
- 第一版假引擎漏了 `abort()`：流式 `stop` 命中时服务端调 `engine.abort()` →
  `AttributeError` → 工作线程崩溃、连接中断，表现为"流式响应没有 usage"。
  这反而说明 `stop` 分支确实走到了 `abort()`，是测试桩的错不是被测代码的错。

- `tools.py` 为 `extract` 声明了 `output_schema`；MCP 客户端会对**每一次** `tools/call` 结果按该 schema 校验，包括「已转 job、正在运行」的首次响应。

**修复**：
- job 启动首帧：`extract` 的响应补 `structuredContent`（job 信封，含 `job_id/status/poll_hint_s`），先通过客户端 outputSchema 校验。

### 15.8 token 计数：精确 tokenizer + 自校准估算（2026-11-19，版本仍为 1.3.1-21）

- 背景：原实现固定 `UTF-8 字节 / 3`，中文大致准、英文高估约 33%，且不随模型词表变化。
- 约束：板端 Debian 无 `python3-tokenizers`，`.rkllm` 也不附 `tokenizer.json`，所以
  "直接上 HF tokenizer" 在这台机器上不可行。
- 方案（三档，`agent/tokens.py`）：
  1. **精确**：装了 `tokenizers` 且能定位词表（`<model>.tokenizer.json`、同目录
     `tokenizer.json`、或 `RKLLM_TOKENIZER_JSON`）→ 直接编码计数；
  2. **自校准**：用 runtime 每次回报的 `perf.prefill_tokens`（真值）对"字节→token"比例做
     EWMA（α=0.3），夹在 [0.8, 8.0]；提示短于 64 字节不参与（模板开销占比过大）；
  3. **冷启动**：3.0 字节/token。
- 接线：`pipeline` 的预算与 usage 都走 `count_tokens()`；`pipeline_runner` 在
  `perf` 到手后调用 `calibrate(prompt_bytes, prefill_tokens)`（流式与非流式两处）；
  `cli_serve` 启动时 `configure(model.path)`；`/health.tokens` 与
  `/metrics` 的 `rkllm_token_bytes_per_token`、`rkllm_token_calibrations_total` 暴露状态。
- 板端实测：一次 100+ 字节中文请求后 `samples=1`、`bytes_per_token` 3.0 → **3.865**，
  后续请求稳定在 3.865；`usage` 仍是 `estimated=false` 的精确值（perf 优先）。
- 测试：`tests/test_tokens.py` 7 例（含"精确档下不再校准""短提示不计样""EWMA 不被单点带跑"），
  其中精确档用例在未装 `tokenizers` 环境自动 skip；`test_token_budget.py` 改用 `count_tokens`。

- **容器镜像不做**：NPU 驱动在内核、`librkllmrt.so` 须与宿主驱动匹配、模型与 `/dev/shm`

- **服务端会话历史不做**：保持无状态，历史由客户端回传；单槽串行下存历史只增内存与语义分叉。
- **模型文件写操作不做**：只读、手动管理，`GET /admin/models` 是唯一入口。

- **`mirostat`/`mirostat_tau`/`mirostat_eta` 不补**：官方 HTTP 面同样不接受、内部固定

- **embeddings 假实现不做**：没有真 embedding 模型，宁可 unsupported。
- **`n_batch>1` 不做**：单槽串行下无收益。
- **官方 build 脚本 `--adb_device` 一键推送不补**：`dpkg` + systemd 已覆盖且更适合量产；
  gradio 本体同理不做。
- **7b 档参数（384/1536/1024）暂不校准**：8G 板以 4b 为主；触发条件——将来主推 7B 时
  实机复测后收敛。

**受 runtime / 硬件限制的声明性缺口（caps 显性 unsupported，不假装支持）**
- 端点缺口（优先级低/受限）：`/v1/audio/transcriptions`（需外挂 ASR）、`/v1/embeddings`
  （需真 embedding 模型）、`/v1/moderations`、`messages(anthropic)`、FIM/prefix completion。
- 无受约束解码：工具调用与 JSON 走「提示 + 校验 + 重试」（见上一条 GBNF），理论上有失败率。
- 流式不支持 `response_format.json_schema`：流式返回 400（无法追回已发出的帧），
  非流式才做校验+重试。
- 采样可复现性缺口：`seed`、`logprobs`、`top_logprobs`、`n>1` 均 unsupported——无法复现
  同一次生成、拿不到 token 置信度、无法一次出多候选。
- 无批处理：`n_batch=1`、单槽串行，多客户端只能排队，无连续批/in-flight batching。
- 服务以 root 运行：受 NPU/锁频限制，只能靠 unit 加固（`NoNewPrivileges`、

- Responses 是翻译层（emulated）：非原生实现，语义边界见 `caps.py`。
- `tools` 走提示词注入而非 `rkllm_set_function_tools`（ADR-06：handle 级污染，见 §9 工具调用段），
  精度依赖模型输出格式；官方 demo 用原生 API。
- prompt cache 受上游"加载缓存返回 -1（内部码 10000）"限制：SCHEMA 默认关闭

  私有属性（升级后失效会表现为 `/health` 实测速率静默变 None）。
- `StreamTimer.finish` 删除"元组 perf"死分支（`Pipeline.last_perf()` 恒返回
  dict|None）；`sse_stream` 的错误路径补 `timer.finish()`，错误请求的 TTFT 与
  耗时此前不入指标。

**取消路径**
- `streaming.watch()` 的断连处理拆成两段：`token.cancel()` 仍在事件循环同步置位
  （泵线程下一轮即停），`abort_once()` 交 `run_in_executor` 执行——`supervisor.abort()`
  会阻塞写 worker socket，不再卡事件循环。

**config**
- 未知 TOML 键改为 `log.warning`（此前静默丢弃）：只对 TOML 告警，env/`.d` 有大量
  由 cli 层消费的历史变量（`RKLLM_HOST`/`SYSTEM`/`TOP_K`），按 SCHEMA 比对会大面积误报。
- 空值语义：新增 `_overrides()`——`str`/`list` 键的显式空串表示"清空上游层"
  （`RKLLM_SERVER_API_KEY=` 可关掉 TOML 里的 key），数值/布尔键空值仍按未设置跳过。
- 显式 `file=` 时不再读系统 `.d`（测试/客户端要的是隔离配置）；不传 `file` 时行为不变。
- `list` 元素统一 `str()` 并丢空项（`cors_origins = [1, 2]` 不再让下游 `join` 抛错）。
- `server.read_timeout_s` 描述纠正为 HTTP keep-alive 空闲超时（uvicorn
  `timeout_keep_alive`），并同步 `rkllm-server-example` 的中英注释。

**abi**
- `load_library` 候选链加入必需符号预检：dlopen 成功但缺 `rkllm_init` 等符号的库
  （错架构副本 / 同名无关库）不再终止候选，报错里带上"缺符号"明细。
- 新增 `RETURN_CODES` + `describe_rc()`：只登记有实测/代码依据的码（0 / -1 / 10000），
  未登记码原样回显数字，不猜原因；`engine` 的 init / load_lora / run 三处错误文案改用它。
- 新增 `struct_sizes()`：把 7 个结构体的运行时 sizeof 写入
  `/health.lib_fingerprint.struct_sizes` 与启动可读位置，供换库后比对。
  **未采用硬断言**：`_fields_` 就是照头文件写的，拿自己的 sizeof 断言等于自证；
  没有头文件常量来源时，暴露尺寸比伪造校验更诚实。

- 验证：`tests/test_audit_fixes.py` 追加 9 例（metrics 并发原子性、`_hist_stats` 均值、
  StreamTimer 无 perf、空值清空、未知键告警、`.d` 跳过、list 元素字符串化、
  `describe_rc`/`struct_sizes`、read_timeout 描述）；全量 pytest

### 19.1 模块

| `输入/rkllm-runtime-1.3.1/src/rkllm/platform/` | SoC/NPU 探测、内存预算、锁频 |

| `工具/大模型测试工具链/` | 压测、仿真、崩溃复现、真实场景、报告生成 |

### 19.2 端点

- `GET /health`：永远 200，反映进程/模型/队列/缓存/NPU。
- `GET /ready`：模型就绪才 200，加载/崩溃 503 + `Retry-After`。
- `GET /v1/models`、`GET /v1/capabilities`、`GET /metrics`。
- `POST /v1/chat/completions`、`POST /v1/completions`、`POST /v1/responses`、`POST /v1/reset`。
- 未实现的 OpenAI/Anthropic 端点显式 501/400；**其余未知路径为 OpenAI 形状的 404**
  （M-9 起：仅形状改为 `{"error":{...}}`，状态码仍是框架 404——原「不落框架 404」表述不准确）。

### 19.3 运行

- 服务：`rkllm-server.service`，`/etc/default/rkllm-server` 由 systemd `EnvironmentFile=` 注入。
- 配置布局：`/etc/default/rkllm-server` 只放启动最小集（模型/地址/端口/CORS/EXTRA_ARGS，去注释；API key 可追加）；模型/运行参数在 `/etc/default/rkllm-server.d/*.conf`（按文件名排序、后覆盖前）；`/etc/default/rkllm-server-example` 是带中英注释的完整模板（不生效）。优先级：内置默认 < TOML < `.d` < 原文件/环境变量 < CLI。
- 日志：`logging.file` 可切换 JSON/文本；uvicorn logger 归并到同一 handler；`X-Request-Id` 回写。
- 缓存：默认 `/dev/shm/rkllm/prefix`，单槽，字节级 LCP + `similarity=0.5`；失败自动降级。
- 安全：API key 走 Bearer；CORS 可配；请求体上限含 chunked 计数；错误体不回显 traceback。
