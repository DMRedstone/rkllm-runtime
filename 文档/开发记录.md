## 一、工程概况

### 目标

把 Rockchip RKLLM SDK（`rknn-llm-release-v1.3.1.tar.gz`，1038 条目 / 616 MB）裁打成规范、可安装、装完即用、卸载无残留的 deb 包。上游只提供 CMake 源码、没有预编译 demo，需要自己补齐命令行、服务与打包链。

### 环境约束

| 约束 | 应对 |
| --- | --- |
| `wsl.exe` 被 WorkBuddy 安全策略的程序黑名单拦截，无法调用 | 放弃 WSL 路线 |
| 本机没有 `dpkg-deb` / `ar` / `lintian` | 纯 Python 直接构造 `ar` + `tar.xz`；自写校验器替代 lintian |
| 无法在目标平台（aarch64 板 + NPU）执行构建 | 四层验证：静态校验器 + `rkllm selftest`（`--fake-engine`）+ 变异测试 + 板端实测 |
| 主机 safe-delete 策略拦截 Python 进程内的删除调用 | 见 §5.4 |

### 目标平台

- OrangePi 5 Plus 8G（SoC = RK3588，aarch64）；只构建 arm64。armhf 构建能力保留（`--arch armhf`）但不再是交付目标。

- 板子地址 `192.0.2.10`。端口与密钥会变（8080 → 8090 → 8080），验收前先探测，不要假设。

- NPU 驱动由板端镜像提供，本包不含、不打 DKMS。

- 8G 内存现实约束：1.5B～4B 量化模型跑得舒服；7B 需压 `--context 2048` + swap。

### 交付物

- `dist/rkllm-runtime_1.3.1-12_arm64.deb`（14,595,360 B，MD5 `2646caaacbee61a91a08a0ceb81f9682`）

- `dist/rkllm-toolkit/`——x86 主机的模型转换工具（不进 deb）

## 三、缺陷排查档案

按发现顺序记录，含现象 → 根因 → 修复 → 验证。其中多数属于"手动能跑、systemd 起不来"或"curl 裸测永远测不到"的隐蔽类型。

### ① `install()` 逃逸（绝对路径 DESTINATION）

- 现象：用户以默认前缀 `make install` 会把 `llm_demo` 写进 `/usr/local/bin`——dpkg 不拥有、卸载删不掉。

- 根因：上游 `rkllm_api_demo/deploy/CMakeLists.txt` 写 `install(DESTINATION ${CMAKE_INSTALL_PREFIX}/bin)`；CMake 对绝对路径形式的 DESTINATION 原样使用。

- 修复：强制 `CMAKE_INSTALL_PREFIX=${CMAKE_BINARY_DIR}/install` + 相对 `DESTINATION bin`。

- 验证：新增 `install() sandboxed` 检查（扫描包内所有 CMakeLists 的 DESTINATION，绝对路径即 FAIL）；变异测试精准命中。

### ② NULL 指针段错误（1.3.1-2）★

- 现象：带 system message 的请求（4350 字节）→ `RemoteDisconnected` + 服务进程消失；而 2520 字节不带 system 的长 prompt 完全正常。

- 根因：`RealEngine.set_system_prompt()` 调 `rkllm_set_chat_template(handle, system_prompt, None, None)`——prefix/postfix 传了 NULL，runtime 对这两个参数无条件解引用 → SIGSEGV。上游 C++ demo 永远传真实字符串（`""` / `"<｜User｜>"` / `"<｜Assistant｜>"`）。

- 影响面：任何带 system 的请求都会崩，即所有聊天客户端都会崩；curl 裸测测不出来。

- 修复：改传 `b""`（空串＝沿用模型自带模板）。

- 验证：新增自检用例 `no NULL passed to the C API`——用 `object.__new__(RealEngine)` 绕过 `__init__`，注入记录型假 lib，检查每个传给 C 的参数都不为 NULL。这条用例填补了此前的盲区：FakeEngine 根本不经过 RealEngine 的 C 调用路径。

- 教训：绝不向 C API 传 NULL 指针。

### ③ usage 计数恒为 0（1.3.1-3）

- 现象：非流式响应 `usage` 恒为 `{0,0,0}`，客户端显示 "0 tokens"。

- 根因：`_openai_response()` 调用时漏传 token 参数（默认值就是 0）。

- 修复：传 `len(prompt.split())` / `len(answer.split())`（后来发现这两个估算本身也是错的，见 ⑫）。

### ④ chat template 被禁用（1.3.1-4）★★★

- 现象：客户端（OpenWebUI 类）调用后无响应，请求挂着不返回。

```
I rkllm: Reset chat template:
I rkllm: System_prompt: Generate a concise, sentence-case title (3-7 words)...  ← 客户端生成会话标题
W rkllm: Calling rkllm_set_chat_template will disable the internal automatic chat
template parsing, including enable_thinking.
```

- 日志证据：

- 根因：每次收到带 system 的请求就调 `rkllm_set_chat_template`，runtime 明确警告这会禁用内置对话模板解析。禁用后模型收到没有特殊 token 的裸文本 → 像"接着往下写文档"一样乱答，且常常不输出 EOS → 请求永不返回。

- 致命点：该设置对整个 handle 生命周期有效。客户端发过一次带 system 的请求（首轮就发标题生成），之后所有请求都被污染，只有重启服务才能清除。

- 修复：`RealEngine.__init__` 不再调 `set_system_prompt`；启动级 `--system` 与请求级 system 均改为前置拼接进 prompt。`set_system_prompt()` 保留但标注 `USE WITH CARE`，写明三条陷阱（禁用内置模板 / 传 NULL 段错误 / 空串也只是重置而非恢复）。

- 顺带纠正一个错误归因：此前把"用一句话介绍杭州"得到 `的西湖。答：…考查知识点：综合读写` 归因于"VL 模型纯文本模式表现差"——错了。真因是测试第 4 步调过 `set_system_prompt`，模板被破坏并持续污染。修复后同一位置输出 `杭州，位于中国浙江省东部，是一座历史悠久、风景秀丽的城市。` 决定性对比证实了归因。

- 教训：绝不用 `rkllm_set_chat_template` 安装 system prompt。

### ⑤ `ConditionPathExists=/dev/rknpu` 是错误判据（1.3.1-5）★

- 现象：systemd 拉起服务时 `skipped, unmet condition check`，服务始终 `inactive (dead)`，没有报错。

- 根因：0.9.x 起的 rknpu 驱动把 NPU 注册为 DRM render node，根本不创建 `/dev/rknpu`。这个守卫在所有板子上都会失败——它从未真正生效，只是把用户的服务挡在门外。反讽的是 NPU 一直是好的，同一时间我还在 8080 实测过推理成功。

  - 单元去掉 ConditionPathExists，改用 `Restart=on-failure` + `StartLimitBurst=5` 限制重试。

  - CLI 新增 `npu_status()`：多信号检测——`/sys/kernel/debug/rknpu/version`（最权威）→ `/sys/kernel/debug/rknpu` 目录 → `/sys/class/drm/renderD*/device/driver` realpath 含 rknpu → 老式 `/dev/rknpu` → `/sys/module/rknpu`。

  - 校验器规则反转：新增 `unit no bogus NPU path guard`（不应出现该守卫）。

- 修复：

- 教训（写给未来的自己）：不要用一个路径的存在性去代表一个硬件能力可用。 判据应来自权威接口（这里是驱动自己的 debugfs 版本文件），或干脆让权威组件（`rkllm_init`）去判断。"看起来合理"的守卫会造成比它解决的问题更难排查的故障。

### ⑥ ExecStart 把空参数传给了 rkllm（1.3.1-6）★★

- 现象：`systemctl status` 显示 `ExecStart=/usr/bin/rkllm serve ${RKLLM_MODEL} ... (code=exited, status=2)`；`restart counter is at 5`。

- 根因：退出码 2 正是 CLI 在"没有子命令"时的返回值。systemd 会把未设置的变量展开成一个空参数——`RKLLM_PLATFORM_ARG` / `RKLLM_EXTRA_ARGS` 为空，于是传了两个空字符串，argparse 当成多余位置参数 → `unrecognized arguments` → exit 2。而 `systemctl status` 只显示 "status=2"（argparse 报错在 stderr，要 `journalctl` 才看得到）。

```
① 空变量被引号引用（= systemd 展开出的空参数）: 参数个数=8, 含两个 <>
② 未加引号（= sh 包装后）                      : 参数个数=6, 空参数消失
```

- 本机精确验证（关键证据）：用 `sh -c 'set -- ...'` 对比两种展开——

- 修复：单元改用 `/bin/sh -c 'exec /usr/bin/rkllm serve "$$RKLLM_MODEL" ... $$RKLLM_PLATFORM_ARG $$RKLLM_EXTRA_ARGS'`——必填项加引号，可选项不加。CLI 侧过滤空参数，且"无子命令"的帮助输出到 stderr（这样原因能进 journal）。

- 验证：升级后8090 端口首次开放（此前一直 ConnectionRefused），证明 sh 包装生效——服务第一次真正跑起来。

- 给用户的提醒：升级后必须 `systemctl reset-failed rkllm-server` 再 restart（重启计数已达 5，不清除无法再启动）。

- 教训：绝不能裸写 `${VAR}`；这块由校验器规则 `unit ExecStart survives unset vars` 守住。

### ⑦ system-only 请求返回 400（1.3.1-7）★

- 现象：客户端报"模型错误，请切换模型或重试 400"。

- 复现：把 16 种客户端请求形态逐一打过去，400 **全部集中在"没有可用的用户文本"**这一类：只有 system 消息、只有 assistant 消息、`content: null`、空 messages 数组。

- 根因：`last_message()` 只认 `role in ("user","tool")`，找不到就返回空 prompt → 400。而客户端在探测/配置新模型时常发只有 system 的请求，于是把好模型显示成"模型错误"。

- 修复：加 `content_text()` 统一次处理（str / 多模态数组 / 其它）；`last_message()` 增加回退（没有 user/tool 时用最后一条带文本的消息）；system-only 请求不再自己拼自己。

- 顺带修掉一个真 bug：`system = message.get("content")` 未做类型转换，客户端用多模态数组发 system 会让 `system_prompt.strip()` 抛 AttributeError → HTTP 500。

- 真凶确认（1.3.1-8）：journal 显示 `[rkllm] rejected: no usable text in messages=[user/NoneType/0chars]`——客户端发的是 `{"role":"user","content":null}`，空输入框的典型序列化结果。与"3B 小模型"完全无关。

### ⑧ 拒绝原因不留痕（1.3.1-8）

- 现象：排查 ⑦ 时多花了一轮——因为只有 "no usable text" 一个分支留痕，其余 400 在日志里完全不可见。

- 修复：新增 `Handler._reject()` 统一做 rejected 计数 + 写 journal + 回错误体；错误信息改为自解释（附上 messages 的角色/content 类型/字符数）。401/404/503/500 不走 `_reject`（不是"客户端内容有问题"）。

- 教训：被拒时必须留下可自解释的日志，否则单凭 journal 无法定位。

### ⑨ prompt 长度防护阈值宽了一倍 → 服务被打崩（1.3.1-9）★★

- 现象：`prompt just under budget`（32668 字节）→ `RemoteDisconnected` → 服务进程消失。

- 根因：原防护是 `context_len × 8` = 32768 字节。而英文约 4 字节/token、中文约 3 字节/token → 32768 字节 ≈ 8192～10922 tokens，模型窗口只有 4096 → runtime 越过 KV cache 崩溃。更严重的是这不是"边界"问题：整个 16K～32K 字节区间都会崩。

- 修复：阈值改 `context_len × 3`（12288 字节）；并让生成与 prompt 共享窗口——`max_tokens = min(max_tokens, context_len - estimated_tokens)`，长 prompt 得到较短回答而不是崩溃。

- 教训：字节↔token 的换算系数必须实测确认（三种语言密度不同），不能拍脑袋。

### ⑩ TCP accept 队列用默认值 5 → 高并发丢连接（1.3.1-9）

- 现象：60 并发 ×2 轮 → `statuses {200: 65, 'EXC': 15}`，一个 503 都没有。

- 根因：请求根本没到应用层，内核就因 backlog 满把连接丢了——精心设计的"队列满回 503 + Retry-After"完全没机会执行。

- 修复：`Server.request_queue_size = 256`。本地以替身引擎验证：80 并发从 15 个 EXC → 0 个。

- 板端对比（决定性）：旧版 `{200:65, EXC:15}` → 新版 `{503:27, 200:33, EXC:0}`。队列逻辑终于有机会执行了。

### ⑪ 客户端的系统提示词装不进窗口（1.3.1-10）★★★

- 现象：日志里 57283 字节的 400——不是用户粘贴的长文档，用户只在新窗口发了"你好"，57KB 全是客户端自带的系统提示词（agent 类客户端的通用形态）。

- 影响：意味着任何重型系统提示词的客户端都无法使用本服务，哪怕只是打招呼。客户端提示词 × 模型窗口（4096）是硬冲突。

```
[rkllm] system prompt dropped: 57283 bytes does not fit a 4096-token window
```

- 修复：超出窗口时丢弃系统提示词而不是拒绝——分别估算 system / user 的 token，若超窗口且 user 自身放得下，则丢弃 system 照常服务并记 journal；若 user 自己也放不下才返回 400。

- 实测：57283 字节 system + "你好" → HTTP 200（此前 400）。

- 副作用（已在文档标注）：模型会失去该提示词的行为约束与角色设定（仍能正常对话）。

- 推理日志同时改为分别显示 system / user 字节数——此前只有一句 "prompt 57283 bytes"，无法判断是用户粘了文档还是客户端带了巨型提示词，这次排查正是在这里多花了一轮。

- 诚实的观察：短 system prompt 是"软"效果——测试用"你是一个只用中文回答的助手"+ 英文提问，模型仍用英文回答。因为实现只能前置拼接，模型可能把它当作输入的一部分而非指令。这是已知取舍，比"破坏模板"好得多，但不等同于真正的 system role。

### ⑫ usage token 对中文恒为 1（1.3.1-12）

- 现象：`usage.prompt_tokens` 对中文恒为 1。

- 根因：统计用 `len(text.split())`——中文无空格 → 整段算一个 token，对每个中文请求低估约一个数量级；而客户端正是用这个字段估算成本与上下文占用。`/health` 的累计统计同样受影响。

- 修复：新增 `_estimate_tokens()`（按字节 ÷3，与长度防护同一套估算），替换两处调用。

- 自检盲区：原用例 `usage reported, not zeros` 只检查"非零且内部自洽"，错误值同样满足，所以缺陷躲过了测试。新增用例 `token estimate handles space-free text`（153 字节中文 prompt 期望 ~51 tokens），并反向验证旧算法在该用例下必然 FAIL，确认用例不是恒真。

- 教训：「检查指标非零/自洽」≠「指标正确」。写断言时先问：这个断言在已知错误实现下会不会通过？若会，它就没有价值。

## 四、技术要点

### 4.1 打包与布局

- 安装布局：multiarch 路径放 `librkllmrt.so`；rknnrt 放私有目录 `/usr/lib/rkllm-runtime` + `/etc/ld.so.conf.d` 登记，避免与厂商 rknn 包冲突。

- `librkllmrt.so` 的 SONAME 无版本号 → 必须保留原文件名，不能做 `.so.1` 版本化软链。

- 依赖来自 ELF DT_NEEDED：`libgomp.so.1` / `libstdc++.so.6` / `libm` / `libdl` / `libc`，符号版本 GLIBC_2.29 → 目标需 Ubuntu 20.04+ / Debian 11+。

- 体积主体是 multimodal 示例里的 Android OpenCV 静态库（456 MB），裁剪后 arm64 包解包 83.9 MB / 压缩后 13.87 MB。

- 上游三处必须改造才能在板端跑：`fix_freq_*.sh` 的 shebang 是 Android 的 `#!/system/bin/sh`；示例 `build-linux.sh` 硬编码交叉工具链 `~/opts/gcc-arm-10.2-...`；server 示例用 `ctypes.CDLL('lib/librkllmrt.so')` 相对路径。

### 4.2 服务实现

- `rkllm` CLI 约 1730 行、纯标准库：ctypes 直接绑定 `librkllmrt.so`（结构体逐字段对齐 `rkllm.h`），板上零编译、零 pip。

- 模型名解析：裸名搜索 `$RKLLM_MODEL_DIR` → `/usr/share/<pkg>/models` → `/var/lib/rkllm/models` → `~/.local/share/rkllm/models` → CWD。搜索目录不由包创建（避免卸载时目录非空）。

- `--max-queue` 语义：最初把"正在推理的那个"也算进额度 → 第 2 个请求直接 503；改为 `max_queue + 1`。

- ctypes 缓冲生命周期：`c_char_p` 指向的 bytes 必须活到 `rkllm_run` 返回。用全局 list 累积会导致长跑服务内存持续增长；改为 run 级 list + `finally` 清空。

- API key 不走命令行：`--api-key xxx` 会让密钥出现在 `ps aux` 与 `systemctl status`。改为优先读 `$RKLLM_API_KEY`（systemd EnvironmentFile 天然进进程环境），并用 `hmac.compare_digest` 做常量时间比较。

- 路径别名容错：`/v1/chat/completions`、`/v1/models`、`/v1/reset` 同时接受不带 `/v1` 的写法（客户端对 base_url 有无 `/v1` 没有共识，配错只会得到难排查的 404）；404 响应体给出正确填法提示。

- 多模态限制：`qwen2.5-vl-*` 这类 VL 模型在 `/usr/bin/rkllm` 只走纯文本（`RKLLM_INPUT_PROMPT`），不支持图片/音频输入。

### 4.3 配置文件与 conffile（1.3.1-12）

- 位置 `/etc/default/rkllm-server`（Debian 服务环境文件标准位置，单元已 `EnvironmentFile=` 指向）。

- 升级不改动 = 声明 conffile：dpkg 里唯一"升级保留本地修改"的机制。

- 模板正文不含版本号：dpkg 只在"包内该文件内容变了"时才重写 conffile。正文随版本变 → 每次升 revision 都覆盖用户文件，并把他为放密钥设的 `chmod 600` 复位成 0644。

- 卸载也要删：dpkg 对 conffile 只在 `purge` 时删除，`apt remove` 会留下 → 由 `postrm` 的 `remove|purge` 分支显式 `rm -f`（全包唯一一处删除动作，校验器按路径精确校验）。代价：remove 后重装回到默认值。

- 每个参数一个变量：`RKLLM_<OPTION>`（共 21 个，中英双语 + 注释形式的可选示例），只对 serve 生效（chat/run 不读，免得 shell 里 export 过的变量悄悄改变交互行为）；命令行参数永远优先；非法值写 stderr 后回退内置默认（否则一个手误就让服务以 `status=2` 静默失败）。

- 一次性迁移提示：从 ≤1.3.1-11 升级到 12，dpkg 无法判断磁盘上那份是"用户改的"还是"包自带的"，会问一次 conffile 冲突，默认动作为保留（N）。

- `postinst` 在 configure 分支做了 `is-active` 守卫的 `restart`：只有原本在跑的服务才重启（升级换了 `.so`，旧进程映射的是旧 inode），不会悄悄拉起没启动过的服务。

## 五、工程红线与硬约束

### 5.1 四条红线（不可让步）

1. 卸载后无残留：不写 `/usr/local`、不写 `/tmp`、不建用户、不做 DKMS、不复制模型。维护脚本只允许刷缓存类动作（`ldconfig`、`systemctl daemon-reload`、`deb-systemd-helper stop/purge`）。禁 `rm -rf`、`systemctl enable|start|restart`、`apt-get`、`pip install`。

1. 示例的 `install()` 不能逃出 build 树：`DESTINATION` 必须是相对路径。

1. 包内改动必须可追溯：所有对上游文件的改写走 `packaging/overrides/`，理由写进 `FILE-MAP.md`。

1. 改文件前先给书面变更说明（用户的工作习惯）。

### 5.2 关键事实备忘

- systemd 会把未设置的变量展开成一个空参数（见 §3⑥）。`ExecStart` 里绝不能裸写 `${VAR}`。

- 绝不调用 `rkllm_set_chat_template` 来安装 system prompt（见 §3④）。

- 绝不向 C API 传 NULL 指针（见 §3②）。

- `/dev/rknpu` 通常不存在，这不是故障（见 §3⑤）。判据：`/sys/kernel/debug/rknpu/version` 或 `/sys/class/drm/renderD*/device/driver` 指向 rknpu。

- `.rknn`（视觉）≠ `.rkllm`（LLM）。

- 输入长度上限：模型窗口 4096 tokens ≈ 3000～4000 汉字 ≈ 12288 字节。长文档必须由客户端分块/RAG，这不是服务端能解决的。

- 依赖：`libc6 (>= 2.29), libgomp1, libstdc++6, python3:any`。

- `Maintainer` 取自 `DEFAULT_MAINTAINER`（当前为 `RedStone <DMRedStone@users.noreply.github.com>`），需要时用 `--maintainer` 覆盖。

### 5.3 构建环境坑

- Python 进程内的删除被主机安全策略拦截：`shutil.rmtree()` 触发 `SAFE_DELETE_FAIL_CLOSED`，逐个 `os.remove()` 会让整条 Bash 命令收到 SIGTERM；而 shell 的 `rm -rf` 可以。→ `emit_tree` 因此不自行删除 staging 树，目录已存在即报错并提示 `rm -rf` 或 `--tree-dir`。

### 5.4 交付标准（每次改动后都要满足）

```bash
rm -rf build/tree-arm64                              # emit-tree 前必须先删（构建器不自行删除）
python 工具/编译工具链/make_deb.py --arch arm64 --emit-tree     # 唯一交付架构（当前 1.3.1-13）
python 工具/编译工具链/verify_deb.py                            # 83 项 FAIL=0/WARN=0（无参数自动发现 工具/dist/*.deb）
python 工具/编译工具链/crosscheck_deb.py                        # 7 项上游 MD5 一致性，0 BAD
python build/tree-arm64/usr/bin/rkllm selftest        # 23 passed / 0 failed（2 项 SKIP 属正常）
```

修 bug 时必须升 revision（`make_deb.py` 的 `DEFAULT_REVISION`），同时在 `packaging/changelog.Debian.in` 追加一条 changelog——否则用户无法用 apt 正常升级、也分不清装的是哪版。

## 六、流程教训

### 6.1 变异测试后必须核对产物内容（两次遇险）

第二次变异测试后，恢复构建被主机 safe-delete 策略中途 SIGTERM，导致 `dist/` 里的 deb 停留在变异状态（zh_CN man 是 `.ZZ` 那版）。另一次批量变异被 SIGTERM 掐断且 stdout 全丢，`packaging/cli/rkllm.py` 残留了变异代码，直到下一轮输出里冒出 `undocumented parameter(s)` 才发现。

固化为规则：

- 变异测试逐个、小步做；脚本加 `-u` / `flush=True`；自己核对工作区（`grep` 变异标记），不能只信脚本的 print。

- 备份目录 + `shutil.copy2` 恢复可行；只有 `rmtree` / `os.remove` 会触发安全策略。

- 每次"变异 → 恢复"都要重新构建 `dist/`、重跑三项验收、并解包核对产物内容——不能只看校验器输出（源文件未恢复时校验器会"看起来正常"）。

### 6.2 测试工具必须能区分失败模式（三次教训）

存活探测必须与业务请求使用同一套凭据，且任何 `except` 都必须把原因留下，否则"401"会被自己翻译成"服务崩溃"。三次实例：

- `verify_board` 把 401 当成连不上；

- `simulate_client` 把请求 500 当成服务失联；

- 内联复验脚本 health 探测漏带 Authorization → 全程打印 `*** DOWN ***`，而实际所有请求都返回了正确状态码。

另：诊断工具的报错本身要能区分失败模式（`HTTP 401 - the service is up but needs a different API key` / `cannot connect` / `HTTP <code>`），否则它会成为排查的干扰项。

### 6.3 板端 Qwen3-4B 能力评估

用板载模型写了一个连通性脚本（`check_connectivity.py`，3 轮迭代）：

- 第 1 轮（55s）：结构完整、含超时/PASS-FAIL/耗时，但有实质 bug——`url1`/`url2` 在解析 `sys.argv` 之前就构造好，`--host` 永远不生效。

- 第 2 轮（69s，反馈 bug）：未修复，只顺手删了未用的 import。

- 第 3 轮（86s，指明具体位置）：修复成功。

另做 6 项能力测试（全部人工核对）：事实 ✅、指令遵循 ✅、中文概括 ✅；算术 ❌、演绎推理 ❌、幻觉抵抗 ❌（编造"量子曲速引擎"细节，未质疑前提）。

结论：部分可用——能处理语言，不能依赖其正确性。 语言组织/格式遵循/文本改写强；算术/推理/事实性弱，且答错时语气同样自信。作为"本地代码助手"可用，但不该指望它自主 debug（对"变量赋值顺序"这类隐式依赖定位能力弱，需人类点明位置）。

### 6.4 用户的偏好（重要）

- 偏好精简，反感臃肿：曾主动加了一个内置网页聊天页（`/ui`，5.3 KB 内嵌 HTML），被要求删掉，理由是"加上之后太臃肿了"。→ 不要主动增加非必要功能；解决用户提出的问题时优先用最小改动；要加功能先问。尤其不要把 UI/前端代码塞进 CLI。

## 十一、审查驱动的健壮性与安全修复（1.3.1-13，2026-10-19）

起因：对全仓、`输入/` 源码、本地模型连接器、测试工具链做了四轮只读审查，本节记录**输入/ 源码侧**按审查结论落地的修复。连接器与测试工具链的问题（档位吞吐假设、HTTP 客户端重复、分档阈值脱节）不在本次改动范围，另案处理。

### 11.1 请求体分帧：拒绝 Transfer-Encoding: chunked

**现象**：服务声明 HTTP/1.1 keep-alive，但 `_read_body` 只认 Content-Length。客户端用 chunked 发请求时，`length` 为 0 → 返回 400 "empty request body"，而**分块数据仍留在 socket 缓冲区里**，同一连接上的下一个请求会把它当成自己的请求体解析——请求走私的基本形态。

**修复**：`do_POST` 在读取请求体之前检查 `Transfer-Encoding`，非 identity 一律 411 + `close_connection=True`。

**验证**：selftest 新增 `chunked body refused`（用 `http.client` 手发分块请求，断言 411）。

### 11.2 function calling：缓冲区保活 + 空 system 占位 + 永久生效可见化

**现象与定位**：
1. `set_function_tools` 把三个 `encode()` 的**临时 bytes** 直接传给 C。`stream()` 专门用 `_run_keep` 保活 prompt/role，说明作者知道 ctypes 不替 `c_char_p` 保活，此处漏了同一处理。
2. `_run_inference` 里 `system_prompt` 可能为空串，而 `set_system_prompt` 的注释已经写明：**runtime 把空字符串当"重置"而非"保持"**。带 tools 且无 system 的请求会把模板重置掉。
3. `rkllm_set_function_tools` 的效果与 `set_chat_template` 同类：**对 handle 永久生效，runtime 没有文档化的关闭方式**。此前它既没有告警，`/health` 也看不见，一次带 tools 的请求会静默改变之后所有请求的行为。

**修复**：
- 三个 buffers 存入 `self._keep`（与 model_path 同级生命周期）；

### 11.3 频率锁定：补恢复路径 + 校验是否真的生效

**现象**：
1. 上游 `fix_freq_*.sh` 只锁不放——cpuidle 全关、governor 切 `userspace`、频率拉满，脚本和 `prerm`/`postrm` 都没有恢复逻辑。而 `lock_frequencies` 对 `run`/`chat` 这类一次性命令默认开启 → 跑完 `rkllm run` 退出后，板子留在满频 + 深度睡眠关闭状态直到重启。
2. 脚本先切 governor 再写频率，**不检查任何写入结果**。目标频率不在该板 `available_frequencies` 表内时，devfreq 拒绝写入而脚本仍 `exit 0`：governor 已经回不去，板子可能卡在 userspace 下的某个低频率，性能反而下降，且无任何提示。

**修复**（均在 `cli/rkllm.py`，不改上游 tarball 内的脚本）：
- 新增 `FREQ_GOVERNOR_PATHS` / `FREQ_CPUIDLE_PATHS`（候选项，读不到就跳过，因此同一张表适配 RK3588/RK3576/RK3562/RV1126B）、`_snapshot_freq_state()`、`_write_sysfs()`、`restore_frequencies()`；
- `lock_frequencies` 在调用 helper **之前**拍快照；`cmd_run`/`cmd_chat`/`cmd_serve` 的 finally 调用 `restore_frequencies()`（先恢复 governor 再恢复 cpuidle——governor 回到 schedutil 后内核会自行选频，cpuidle 是在那之上关掉的）；
- helper 退出 0 但**没有任何 governor 变成 userspace** 时，返回 `suspect (no governor changed)` 并告警，把"频率表不匹配"这一类静默失败暴露出来；
- 非 root 场景走 `sudo -n sh -c` 写 sysfs（与既有 `sudo -n` 调用 helper 的口径一致），写不进去只告警不中断。

**验证**：Windows 上验证降级路径——空快照返回 `nothing to restore`、缺失路径 `_write_sysfs` 返回 False、未知 SoC/未安装 helper 均正确跳过；语法与 selftest 全通过。**真机上的恢复行为尚未验证**（见 11.6）。

### 11.4 服务单元加固与密钥卫生

- `rkllm-server.service`：新增 `NoNewPrivileges=true`、`PrivateTmp=true`、`ProtectSystem=full`、`RestrictSUIDSGID=true`、`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`。`ProtectSystem=full` 让 /usr /boot /etc 只读但保留 /sys 可写（锁频需要），**故意不设 ProtectHome**——模型常放在 /home 或 /root，隐藏会导致这些板子上单元起不来。注释里写明了这两处取舍，避免后人"顺手补齐"。
- `default/rkllm-server`：SECURITY 段补充 `RKLLM_EXTRA_ARGS` 的真实语义——该值被拼进 `ExecStart` 并由 `/bin/sh` 展开，`"--verbose; 某命令"` 会以 root 执行。只有 root 能改该文件，不构成提权边界，但必须让读者知道它是代码而非选项列表。
- `postinst`：configure 时若 conffile 里存在 `RKLLM_API_KEY=` 且权限不是 600/400/440/640，向 stderr 提示 `chmod 600`。默认 0644 且 dpkg 升级不改权限，"填了 key 忘记 chmod"原本没有任何检查点。
- 服务启动时若**未设 API key 且监听非回环地址**，打印醒目 WARNING（含 `/v1/reset` 可被任意主机调用的后果与修复指引）。保持"未设 key 即放行"的既有语义不变——已有部署依赖该默认值，改为拒绝会让服务起不来。

### 11.5 手册示例改为环境变量写法

### 11.10 背压口径、非流式断开与打包工具链健壮性（2026-10-19 下午）

接续 11.8 的 P1/P2 清单，处理落在 `输入/` 与 `工具/编译工具链/` 的 5 项。**默认监听地址与 TLS 按决定不改**：`DEFAULT_HOST=0.0.0.0` 保持（改 127.0.0.1 会让"装完即可被内网访问"失效，属产品行为而非缺陷），`--api-key-file` 与内置 TLS 不做（穿透链路本身已是 https，再加自签证书收益低于证书分发成本）。

#### 11.10.1 两个背压出口口径一致（P1-5）

`/v1/chat/completions` 有两条 503 路径：队列满、等 NPU 超时。后者本来就带 `Retry-After: 5`，前者没有——同一个状态码两种行为，客户端无法统一处理。`_send_json` / `_send_error_json` 增加可选 `headers`，队列满分支补 `{"Retry-After": "5"}`。

代价是一个函数签名多一个参数；不采用的写法是让 `_reject` 分支自己写响应（会绕过 `stats["rejected"]` 计数）。

#### 11.10.2 非流式请求的断开探测（P1-4）

非流式请求在生成期间没有写操作，客户端断开（Ctrl-C、浏览器取消、超时）只能靠写失败发现——而它根本不写。结果是一段没人要的推理跑完，白占 NPU 与 `infer_lock`（下一个请求要等它）。

新增 `Handler._client_gone()`：`select(..., 0)` 可读 + `recv(1, MSG_PEEK) == b""` 才算断开。两个细节：

- **`MSG_PEEK` 不消费数据**：客户端 pipelined 的下一个请求不能被吞掉。
- **可读不等于断开**：缓冲区还有数据时 `select` 也返回可读，而 `MSG_PEEK` 只能看到数据、看不到后面的 FIN。所以"有数据"必须判为未断开。

推理循环里每 0.5 秒探一次（`time.monotonic()` 节流），断开即 `engine.abort()` + `close_connection`，并在 journal 记一行。0.5 秒是取舍：更密会让长 prompt 的循环多出一堆系统调用，更疏则多跑几秒 NPU。

#### 11.10.3 打包工具链三处（P2-1/2/3）

| 编号 | 问题 | 修法 |
| --- | --- | --- |
| P2-1 | `emit_tree` 建符号链接失败时 `write_text(item.link)` 降级成普通文件——复核树与真实包不一致，而 dpkg-deb 复核正依赖这棵树 | 直接 `SystemExit`，并**回读 `is_symlink()` 确认**：Windows 无权限时 `symlink_to` 可能不抛异常却留下解析不了的条目，只捕 `OSError` 挡不住（本机实测确认） |
| P2-2 | ar 头长度用 `assert` 校验，`python -O` 下整条被剔除 | 改显式 `if len(header) != 60: raise SystemExit` |
| P2-3 | 架构排除用 `marker in low` 子串匹配，`libmyarmhflib.so` 这类合法文件被静默丢弃（只进统计，构建照常成功） | 改为"非字母数字边界"正则匹配；不用 `[-_.]` 分词——`arm64-v8a` 自带 `-`，分词会拆成 `arm64`+`v8a` 反而匹配不上 |

## 十六、1.3.1-15 第三轮：413/408 未关闭连接（2026-10-20 深夜）

### 16.1 主问题：`_read_body` 返回 413/408 时没有关闭连接

`_read_raw_body()` 有三种失败路径，其中两种 body 还留在 socket 里：

| 返回 | body 读完了吗 | 连接能复用吗 |
| --- | --- | --- |
| `empty request body`（400） | 是（`length <= 0`） | 能 |
| `invalid JSON body`（400） | 是（`raw` 已完整读出） | 能 |
| `request body larger than ...`（413） | **否**（超限直接返回） | **不能** |
| `timed out after ...`（408） | **否**（超时留下残余） | **不能** |

`protocol_version = HTTP/1.1` 默认 keep-alive，未消费的 body 字节会被下一个请求当成请求行来解析。`/v1/reset` 分支当时手写了 `close_connection = True`，`/v1/chat/completions` 分支漏了——因为"记得关连接"这件事靠调用方自觉，迟早漏一处。

**修法**：不按审查建议的"在调用方加 if status in (408, 413)"，而是让 `_read_raw_body()` 自己在三条失败路径上都置 `close_connection = True`。理由：调用方会增生，责任放在读取处才是闭合的。顺带把 reset 分支里那行手写的判断删掉（现在由底层负责）。

同类问题一并补上：`do_POST` 的 401（鉴权失败）与 404（未知路径）两条分支也不读 body，同样置 `close_connection`。

### 16.2 顺手修的三处

- **Transfer-Encoding 检查前置**：原本只在 chat/completions 分支里，`/v1/reset` 收到 chunked 会被当成空 body 接受，chunk 帧留在 socket 里污染下一个请求。移到 `do_POST` 开头，所有 POST 端点共享，任何端点都不可能忘。
- **`body` 变量复用**：NPU 排队超时分支把 `body` 从请求 dict 覆盖成 bytes。运行无误（后续不再用），但读起来像 bug。改名 `error_body`。
- **selftest 的 stop 断言**：原本 `content.endswith("AAA")`，而假引擎的输出带回合计数（`answer 7 to: AAA`），隐含依赖测试执行顺序。改为 `content.split("to: ")[-1] == "AAA"`。

### 16.3 修改时撞出来的连锁问题

把 Transfer-Encoding 检查前移之后，selftest 的 `chunked body refused` 开始失败，报 `ConnectionAbortedError`。原因是原测试先发 header、再发 chunk body，而服务端在 header 阶段就 411 + 关连接——两边竞态，客户端 send 撞上 RST。之前能过是运气（中间隔了几行代码的时间差）。

修的是测试本身：改成裸 socket 只发 header 不发 body。服务端对 framing 的判断不应该依赖 body 是否到达，这样测也更严格。连跑三次确认稳定。

## 十七、1.3.1-15 第四轮：关闭流程的清理保护（2026-10-20 深夜，不升版本号）

第三轮之后审查确认前 4 项都修对了，指出最后一处同类问题在 `cmd_serve` 的收尾路上。按要求**不升版本号**，只修 bug。

### 17.1 `cmd_serve` 的 finally：stderr 写失败会跳过清理

```python
finally:
    sys.stderr.write("\n[rkllm] shutting down\n")   # BrokenPipeError 之后全跳过
    server.shutdown()
    server.server_close()
    engine.destroy()                                # NPU 句柄没释放
    restore_frequencies(quiet=args.quiet)           # 频率没恢复
```

systemd 下 stderr 指向 journal，热重启时旧进程的 fd 可能已断开。这时 `engine.destroy()` 与 `restore_frequencies()` 都不会执行——进程退出后 OS 会回收内存与 fd，但 NPU 句柄和 CPU 频率钉在旧状态，`systemctl restart` 的新进程可能继承一个"NPU 仍被占用、频率仍被锁"的板子。

修法与 `RealEngine.stream()` 的 finally 一致：stderr 写入单独 `try/except (OSError, ValueError)`，其余步骤用嵌套 `try/finally` 保证顺序执行。

### 17.2 顺带发现的第二个坑：`shutdown()` 可能永久阻塞

审查没提，但修 17.1 时看到了：`server.shutdown()` 的语义是"等待 `serve_forever` 循环在退出路上设置事件"。如果那个循环**已经死了**（handler 里出现致命错误导致线程退出），`shutdown()` 会一直等一个永远不会被设置的事件——进程卡在收尾里出不来，`engine.destroy()` 反而更不可能执行。

改为先判断 `thread.is_alive()`：

```python
if thread.is_alive():
    server.shutdown()
    thread.join(timeout=5)
```

循环还活着才等它退出；已经死了就直接往下走 `server_close()`。

### 17.3 三处轻微项

- **401 计入 `rejected`**：`do_POST` 与 `do_GET` 的鉴权失败从 `_send_error_json` 改为 `_reject`，`stats["rejected"]` 一并统计。此前 `/health` 的 `rejected` 只算业务拒绝，答不出"一共有多少请求被拒之门外"。
- **`do_GET` 的 401 不关连接**：GET 没有 body，socket 里没有残留字节，不关是安全的。这一点写进了注释——否则下一个人会以为是和 `do_POST` 不一致的疏漏。
- **`_GateEngine.stream` 透传全部参数**：子类签名静默收窄父类，等哪天某个参数开始起作用就是个真 bug。假引擎不用这些参数，但签名要一致。

### 17.4 明确不改：流式分支不加 watchdog

审查提到流式分支在 prefill 期间无法感知客户端断开，并注明这是已知设计选择。同意不改：

- 流式分支全程有 `wfile.write`，`BrokenPipeError` 能覆盖生成阶段；
- 只有 prefill 那段（几十秒）是盲区；
- 加 watchdog 意味着给每个流式请求多开一个线程并引入 abort 与 write 的并发，而收益只覆盖一个窄窗口。

如果将来压测发现流式请求在 prefill 阶段大量空转，再考虑。

## 十八、1.3.1-15 第五轮：响应头一致性与统计口径（2026-10-20，不升版本号）

### 18.1 两个 503 出口长得不一样（主问题）

`do_POST` 有两个 503：

- **queue_slots 满** → 走 `_send_error_json`，带 `Access-Control-Allow-Origin`
- **infer_lock 超时** → 手工拼 `send_response` + 三个头，**不带 CORS**

浏览器客户端在第二种情况下读不到 503 的 body，只能看到 opaque 的 `TypeError: Failed to fetch`，分不清"NPU 忙"和"网络断了"。而这两种情况的处置方式完全不同：前者等 `Retry-After` 重试，后者要查 NPU 是否卡死。

手工拼响应那句注释写的是"`_send_json` would emit a second status line"——这个说法不成立。两个分支都只调用一次 `send_response`；这句注释是更早版本留下的（当时可能先手动 `send_response` 又调了 `_send_json`）。现在统一走 `_reject`，注释一并删掉。

### 18.2 `_reject` 支持 headers，并成为唯一的拒绝出口

`_reject` 原来只接受 `(message, status, error_type)`，所以 queue-full 那个出口只能 `stats["rejected"] += 1` 再自己调 `_send_error_json`——计数、日志、响应头三件事分散在两个地方，`infer_lock` 出口干脆连日志都没有。

现在 `_reject` 多了 `headers` 参数，所有拒绝统一走它：

```python
self._reject("server queue is full ...", 503, "server_error", {"Retry-After": "5"})
self._reject("timed out waiting for the NPU", 503, "server_error", {"Retry-After": "5"})
self._reject("unknown endpoint ...", 404, "not_found")
```

计数、journal 日志、CORS、Retry-After 从此只有一处实现。此前 journal 里看不到"谁被 503 拒了"，运维只能从 `/health` 的数字倒推。

### 18.3 `close_connection` 时补 `Connection: close`

`_send_json` 之前不看 `self.close_connection`。但 401/404/413/408 四条路径都在回答前把它置为 True（body 没读完），服务端写完响应就关——响应头里却没说。

HTTP/1.1 客户端看到没有 `Connection: close` 的响应，会认为连接可复用，下一次请求直接写进一个正在关闭的 socket，得到 `BrokenPipeError` 或 RST。加一行：

```python
if self.close_connection:
    self.send_header("Connection", "close")
```

一处改动覆盖所有关连接分支，包括以后新加的。

### 18.4 两处对齐

- **selftest 的收尾**：`server.shutdown()` + `thread.join()` 无超时，和 `cmd_serve` 第四轮修完的形态不一致。改成同样先判 `thread.is_alive()` 再 `join(timeout=5)`。
- **`server.timeout = 1.0`**：`serve_forever()` 用自己的 `poll_interval`，从不读 `BaseServer.timeout`，只有 `handle_request()` 读。赋值无害但会误导，加注释说明保留原因。

### 五、部署形态：两种链路并存

实际部署是**同一台板端服务被两条链路访问**：

| 形态 | 承载能力 | 说明 |
| --- | --- | --- |
| 内网主机直连 | 不受限 | 另一台主机与板子同处内网，带宽与并发充足 |
| 本机经内网穿透 | 受限 | 隧道带宽与并发连接数有限，连接不复用、RTT 高 |

两条由此确定的原则：

1. **不能把「穿透受限」当全局前提**。用 `link=direct|tunnel` 按目标标（默认 `direct`）：直连是常态，把受限假设设为默认会让所有场景无谓变慢；穿透目标显式声明即可，忘写的最坏后果是「慢」而非「错」。
2. **不靠减少测试项目来迁就慢链路**。`list_targets` 仍然探测**全部**目标——探不全就不知道哪台还能用。链路差异只体现在并发方式与并发上限上。

### 六、链路档位 `link=`

| 行为 | `link=direct`（默认） | `link=tunnel` |
| --- | --- | --- |
| `list_targets` 探测 | 线程池 4 路并发，墙钟 ≈ 单次超时 | 串行，逐条打印进度 |
| 请求并发 | 仅受同目标 `_lock_for` 约束 | 全链路信号量 2 槽（`LINK_TUNNEL_SLOTS`） |
| 适用 | 内网直连、localhost | 内网穿透、反代、跨公网 |

链路闸门 `_link_guard` 按 **link 分组**而不是按目标：多个穿透目标走的是同一条隧道，按目标限流对隧道无效。取值校验在 `_coerce_opt` 里，非法值回落 `direct` 并告警；中文别名「链路」。

`list_targets` 的 `count` 恒等于配置里的目标数、输出顺序不变，每个目标多一个 `link` 字段——慢只影响耗时，不影响覆盖。

### 七、上下文协商（G5-a）

首次调用某目标时读一次 `/health`，若返回 `context_len`（兼容 `n_ctx`）且小于配置的 `context`，则按下调，并把 `max_in` 收紧到 `context - 64 - max_out`（不足 256 时只告警不动手）。**只下调不上调**：上调会让既有的 `max_in` / `max_out` 假设失效。

- 每个目标只探一次（`_context_probed`），失败静默——协商是增强，不能因此让调用失败。
- 配置 mtime 变化时清空 `_context_probed` 与 `_tps_samples`，重新协商。
- 协商后 `max_in` 会再校验一次输入预算，超过就拒绝（否则 context 缩小后输入仍按旧的宽预算放行）。

服务端字段由 `输入/` 侧的 `cli/rkllm.py` 提供（2026-10-19 的 11.1 修复里给 `/health` 加了 `context_len`）。

### 八、吞吐自适应（G3）

每次成功调用记录 `completion_tokens / elapsed`，保留最近 5 次；输出 <40 token 的样本丢弃（首 token 开销占比过高）。取**中位数**（抗单次抖动），样本满 3 个且中位数 **低于配置值的一半**时，写入 `cfg["_measured_tps"]`，`_timeout_for` 改按它推算并 `_warn` 一次。

**只下调不上调**：实测更快时不动配置——超时变小会误杀长尾请求，宁可等久一点。

不采用的写法：每次调用前跑一次校准（弱板子上校准本身几十秒，且会占 NPU 队列）。

### 九、其他修正

## 2026-10-20：会话记忆（session）与服务端 reset

背景：服务端审查发现多轮对话错配（服务端只读最后一条消息、靠内部 KV 记历史），
并给出两路线——A 服务端改 stateless、B 连接器侧维护会话。两条同时实施。

### 一、新增能力

| 能力 | 说明 |
| --- | --- |
| `history_turns`（配置项，默认 0） | 连接器侧会话记忆轮数上限。0 = 关闭（默认），保持"每次调用独立"的既有语义 |
| `ask(..., session=...)` | 同一 session 的多轮调用自动带上之前对话；历史**拼进 prompt 文本**而非 messages 数组 |
| `reset_session()` / CLI `reset` | 清连接器侧历史 + 打服务端 `/v1/reset`；返回清理轮数与服务端状态 |
| `list_sessions()` / CLI `sessions` | 查看当前进程内的会话名与轮数（排查用） |
| MCP 工具 `local_llm_reset` | 工具数 4 → 5；`local_llm_ask` 增加可选 `session` 参数 |

### 二、为什么拼进 prompt 而不是 messages 数组

旧服务端（< 1.3.1-14）只读最后一条 user 消息、前几轮直接从 messages 里丢弃，靠服务端内部 KV
续上下文。把历史拼成「此前的对话」文本放进 content，**新旧服务端都能看懂**——这是兼容优先的选择。
服务端升级到 stateless 后，这段拼接依然成立（等价于客户端自己拼历史）。

### 三、两个防坑设计

1. **预算随历史重算**：拼上历史后若超 `max_in`，从最旧的轮次开始丢（`compose()` 循环），
   而不是直接报错——否则开多轮就必然撞预算墙；
2. **与 `RKLLM_NO_HISTORY=0` 互斥**：服务端自己记历史时若连接器再拼一遍，每轮都会重复。
   文档与示例都注明这条，服务端侧也用 `include_history=False` 做了对称处理。

### 五、遗留

- **服务端已上生产板**：`1.3.1-14` 已装到 192.0.2.10（服务 active，19 项功能验证全过），
  启动日志 `history=0` 即 stateless——与连接器默认 `history_turns=0` 正好匹配，
  **不会出现"服务端历史 + 连接器历史"双份重复**。若哪天把板端改成 `RKLLM_NO_HISTORY=0`，
  必须同时把连接器的 `history_turns` 保持 0，否则上下文会重复一遍；
- 长驻 MCP 进程需重启客户端才加载新代码（既有遗留）；
- `ask` 的 `session` 只在 `history_turns>0` 时生效，默认关闭——MCP 场景下上游大模型自己维护
  上下文，强行开历史反而会打乱单轮任务的语义；
- 会话历史只在进程内存里，MCP 服务重启即丢（有意为之：不做持久化，避免旧上下文串进新任务）。
- **历史渲染标签同步**（2026-10-20 晚）：服务端为通用性把对话记录标签从 `用户/助手` 改为

  否则同一个会话在不同服务端版本下会被模型当成两种格式。

### 一、P0-1 鉴权（新增 `server/auth.py`）

模式：ASGI 中间件 + 默认拒绝 + 仅 `/ready` 豁免 + 常量时间比较。
`api_key_file` 优先于 `api_key`；文件权限过宽（非 0600）只告警不阻断（板上运维
现实）；`api_key` 为空时整条链不挂载——与 1.3.1-15 「空=不鉴权」语义一致，

记得加；中间件是"默认拒绝"，新增路由自动受保护。

### 二、P0-2 取消（三处断点全接）

1. `mcp/tools.py`：`_chat_once` 的 `cancel_check` 形参此前存在但四处调用都
   没传 → 恒 None → `HttpBackend` 的取消分支永不触发。现在 handler 统一收
   `should_cancel`，一路传到 `backend.chat(cancel_check=...)`。
2. `mcp/stdio.py`：reader 线程此前同步执行 handler，一次 ask 最长 45 s 期间

3. 取消匹配键修正：`notifications/cancelled` 携带的是 JSON-RPC **requestId**，
   旧实现却用 `progressToken` 当 key，取消根本对不上号。`Dispatcher` 增加
   线程本地的 `current_request_id`，stdio 用它注册 in-flight。
4. 服务端断连：流式生成器 `GeneratorExit` 时调 `supervisor.abort()`；客户端

5. 伪 job 清理：同步调用此前 `jobs.create()` 造一个永不终结的 job 占表，

### 三、P0-3 档位与内存预算（新增 `platform/`）

设计 §4.4 一直要求 `platform/`，此前缺失。新增：

  medium）→ 默认 small。`model.class` 键名是 Python 关键字，此前根本无法
  `cfg.model.class` 访问，这大概是它一直没被接线的原因；统一走

### 二、缺陷 1：单轮请求每次都写 185 MB 缓存

35 条**互不相同**的单轮请求，每条都把整段 prompt 的 KV 存成新缓存文件，
累计约 6.5 GB 写入，命中率为零。SD 卡/eMMC 上这是纯粹的 I/O 浪费与磨损。

修法：只有"后续可能以这段 prompt 为前缀"的请求才值得存缓存，即
`messages >= 2`（多轮）。链路改为 pipeline 计算 `cache_hint` →
supervisor → 帧参数 → engine；`cache_hint=False` 时完全不碰缓存。

板端验证：单轮请求后缓存目录 4 KB（空）、`hits=0/misses=0`；
两轮对话后 55 MB、`misses=1`；第三轮（以前两轮为前缀）`hits=1` —— 命中链路成立。

### 三、缺陷 2：tool_calls 是扁平结构，标准客户端全挂

- OpenAI Agents SDK：`ModelBehaviorError('Tool  not found in agent board')`（名字是空串）

修复后同一个请求返回：

```json
"tool_calls": [{"index":0,"id":"call_191a4970","type":"function",

```

#### 〇、总体思路、功能范围与进度（2026-10-22 更新）

**版本：1.3.1-16**（本批改动不递增版本号；1.3.1-16 是本次改造的交付版本）

##### 0.1 总体思路

把 OrangePi 5 Plus（RK3588 / 8 GB）上的 4B/7B 模型，做成 **WorkBuddy 可调用的
辅助推理后端**：WorkBuddy 用主模型规划，板端模型承担摘要、改写、抽取、分类、
翻译、短问答与分段批处理——**只做"可判定的短任务"，不做长文创作与多步推理**。

三层结构，边界清晰：

```
WorkBuddy（MCP stdio 客户端）
   │  local_llm_ask/chat/extract/batch/status/job 六个工具
   ▼
客户端连接器（纯 stdlib .py，本机运行）
   │  HTTP：/v1/chat/completions（+ /v1/responses 翻译层）
   ▼
板端服务：FastAPI（鉴权/队列/SSE/能力表）+ 推理子进程（ctypes → librkllmrt.so）
```

六条关键取舍（ADR，详见总体设计 §5）：

| # | 取舍 | 理由 |
|---|---|---|
| 1 | 入口只有一条：`/usr/bin/rkllm` + `rkllm-server.service` + `/etc/default/rkllm-server`（都沿用旧名） | 运维脚本、unit、conffile 零改动 |
| 2 | 推理放子进程，HTTP 崩溃隔离；崩溃自愈（周期探测 + 请求路径重试） | 单 NPU 场景下稳定性优先 |
| 3 | 工具调用用"提示词注入 + 解析"，不碰 handle 级的 `rkllm_set_function_tools` | 后者永久生效会污染后续请求 |
| 4 | 能力三档（native/emulated/unsupported）由 `caps.py` 单一事实源渲染 | 杜绝"看起来支持其实不支持" |
| 5 | 单槽 prompt 前缀缓存 + 内存预算（不足先降 context 再拒绝） | 8 GB 板上 4B/7B 可跑、27B 明确拒绝 |
| 6 | 客户端只走**源码安装**（不打包 wheel、不建 venv） | 纯 stdlib，多一层打包只增负担 |

#### 二、改造目标（合并三份文档的结论）

把板上 4B/7B 模型做成 WorkBuddy 可通过 MCP 调用的辅助工具：

1. **板端**：`rkllm serve` 从 3 122 行单文件重构为模块树（FastAPI + 推理子进程 + UDS 帧协议），修复审核报告 D1–D15；
2. **客户端**：自写纯 stdlib MCP 连接器 `rkllm-mcp`（stdio、6 工具、job 轮询、取消传导），以**源码目录**交付（当晚改定：不走 wheel）；
3. **配置**：80 键 TOML 单一配置表，全部有默认值、启动校验、来源可查；
4. **诚实兼容**：能力三档（native/emulated/unsupported）单一事实源 `caps.py`，杜绝静默忽略。

三个硬约束：客户端 60 s 工具超时（>45 s 一律 job 化）；单 NPU 串行（有界队列+背压+取消）；8 GB 内存（4B/4096、7B/2048、27B 拒绝启动）。
