## 0. 工程概况

把 Rockchip RKLLM SDK 裁打成规范、可安装、卸载无残留的 Debian 包，并提供 OpenAI 兼容的板端推理服务与 MCP 连接器。

| 项 | 内容 |
|---|---|
| 构建 | 纯 Python 构造 `ar` + `tar.xz`，不依赖 `dpkg-deb`；入口 `工具/编译工具链/make_deb.py` |
| 校验 | `verify_deb.py` 结构/策略/卸载面自检；`crosscheck_deb.py` 与上游 tarball 逐文件比对；`release_check.py` 版本/键数/caps/deb 一致性 |
| 服务 | `输入/rkllm-runtime-1.3.1/src/rkllm/`：FastAPI、worker 子进程、UDS 帧协议、SSE、队列、supervisor |
| 连接器 | `本地模型连接器/rkllm/`：stdlib MCP stdio，四版协议、6 工具、job、取消传导 |
| 配置 | 85 键 TOML/conffile；`/etc/default/rkllm-server` 由 dpkg 作为 conffile 管理 |
| 交付 | `工具/dist/rkllm-runtime_1.3.1-17_arm64.deb`；453 文件，14.00 MB，解包 84.2 MB |

### 0.2 工程红线

1. 不向 C API 传 NULL 指针；结构体与 bytes 必须活到 `rkllm_run` 返回。
2. 包内文件必须在 `dpkg` 清单内；安装期不写清单外路径。
3. `/dev/rknpu` 不是 NPU 判据；以 debugfs/DRM/驱动节点多信号判断。
4. 所有影响行为的参数必须进配置表；不静默忽略、不静默改变客户端契约。
5. 失败必须可观测：日志、`/health`、`/metrics`、错误体至少一处留痕。

## 1. 2026-10-14 ～ 10-18：1.3.1-1 ～ 1.3.1-12

### 1.1 工程起点

- 上游只提供 CMake 源码与库，没有可直接安装的 CLI/服务；本仓库补齐 `rkllm` 命令、systemd 单元、man、conffile 与 deb 打包链。
- 构建机没有 `dpkg-deb`、`ar`、`lintian`，因此 `make_deb.py` 直接生成 ar 容器与 tar.xz，`verify_deb.py` 承担 lintian 的结构检查。
- 目标板不参与构建；采用「静态校验 + `rkllm selftest`（fake engine）+ 变异测试 + 板端实测」四层验证。

### 1.2 早期缺陷与修正

| 版本 | 现象 | 修复 |
|---|---|---|
| 1.3.1-1 | 首次打包 | 纯 Python 构建器 + 校验器；CLI 子命令与 systemd 单元落地 |
| 1.3.1-2 | NULL 指针段错误 | `set_chat_template` 的 prefix/postfix 改传空串，不再传 NULL |
| 1.3.1-3 | usage 恒为 0 | 非流式响应补 token 计数 |
| 1.3.1-4 | chat template 被禁用 | 不再调用 `rkllm_set_chat_template`，system 文本前置拼接 |
| 1.3.1-5 | NPU 判据错误 | 去掉 `ConditionPathExists=/dev/rknpu`；CLI 改多信号检测 |
| 1.3.1-6 | ExecStart 空参数 | 单元用 `/bin/sh -c` 包装；CLI 过滤空参数 |
| 1.3.1-7 | system-only 请求 400 | `last_message()` 回退；`content_text()` 统一类型处理 |
| 1.3.1-8 | 拒绝原因不留痕 | 统一 `_reject()`：计数、journal、错误体 |
| 1.3.1-9 | prompt 阈值过宽 / 队列过小 | 预算 `×8`→`×3` 字节；`max_tokens` 与 prompt 共享窗口；队列 256 |

| 1.3.1-12 | conffile / token 估算 | `/etc/default/rkllm-server` 改为 conffile；新增 `_estimate_tokens()` |

### 1.3 打包与运行约定

- 安装布局：`/usr/bin/rkllm`、`/usr/lib/<triplet>/librkllmrt.so`、`/usr/include/rkllm/`、`/usr/share/rkllm-runtime/examples/`、`/usr/lib/systemd/system/rkllm-server.service`、`/etc/default/rkllm-server`。
- 卸载无残留的判据：`/var/lib/dpkg/info/rkllm-runtime.list` 覆盖全部文件；`postinst`/`postrm` 只执行 `ldconfig`、systemd 重读与删除那一个 conffile。
- 交付标准（每次改动后）：`make_deb.py --arch arm64` → `verify_deb.py` → `crosscheck_deb.py` → `rkllm selftest`，四项全绿才可交付。

### 1.4 早期验证与教训

- 变异测试必须逐个、小步执行并直接核对产物内容，不能只信脚本 print。
- 测试工具必须能区分「服务不可达」「鉴权失败」「队列满」「请求级失败」，否则会把故障误判为通过。
- 板端真实模型的能力与 host 上 fake engine 差异很大；涉及 NPU 生命周期的改动必须上板。

### 10.3 extract 工具 job 路径丢失 structuredContent

**现象**：`local_llm_extract` 无论 schema 多宽松都报
`MCP error -32600: Tool local_llm_extract has an output schema but did not return structured content`。

**根因**：
- `tools.py` 为 `extract` 声明了 `output_schema`；MCP 客户端会对**每一次** `tools/call` 结果按该 schema 校验，包括「已转 job、正在运行」的首次响应。
- `extract` 的估算使用 `default_max_tokens*2`，必然超过 45s 阈值而转 job。
- job 启动首帧只返回 `content`（job_id/status），没有 `structuredContent`，客户端在首次调用即报 `-32600`。
- `stdio.py::_job_tool` 的 `get` 分支又把 `job.result`（含 `structuredContent`/`isError`）整体 JSON 序列化进 `content[0].text`，终帧同样丢失结构化字段与错误标记。
- 同步路径（`stdio.py` 直接返回 handler 结果）与协议层 `result_payload` 本身正确，问题只在 job 的首帧与轮询两条响应。

**修复**：
- job 启动首帧：`extract` 的响应补 `structuredContent`（job 信封，含 `job_id/status/poll_hint_s`），先通过客户端 outputSchema 校验。
- 任务 `completed`：直接返回 `job.result`，保留 `structuredContent` 与 `content`；缺少 `content` 时才补摘要文本。
- 任务 `failed`：返回 `isError: true` 与错误文本。
- 新增 `tests/test_mcp_fixes.py::test_extract_job_start_has_structured_content` 与 `::test_job_get_preserves_structured_content_and_errors`。
- 板上端到端验证（MCP stdio，2026-10-27）：`local_llm_extract` 强制转 job 后，首帧返回 job 信封 `structuredContent`，轮询终帧返回 `structuredContent: {"name":"张三","age":35}`，不再报 `-32600`。

- **`finish_reason` 未透传**：连接器 `ask` 只回文本，是工具抽象限制，不是服务端缺陷；raw `/v1/chat/completions` 可验证 `finish_reason=length`。

### 10.7 全面修复 P0/P1（2026-10-27）

## 11. 当前架构与运维

### 11.1 模块

| 路径 | 职责 |
|---|---|
| `输入/rkllm-runtime-1.3.1/src/rkllm/server/` | FastAPI 组装、队列、supervisor、SSE、路由、认证、指标 |
| `输入/rkllm-runtime-1.3.1/src/rkllm/worker/` | 推理子进程、帧协议、引擎、prompt cache |
| `输入/rkllm-runtime-1.3.1/src/rkllm/agent/` | conversation、reasoning、tools、tokens、json_schema、responses 翻译 |
| `输入/rkllm-runtime-1.3.1/src/rkllm/platform/` | SoC/NPU 探测、内存预算、锁频 |
| `本地模型连接器/rkllm/mcp/` | MCP stdio、协议矩阵、backend、jobs、tools |
| `工具/编译工具链/` | make_deb、verify_deb、crosscheck_deb、release_check、模板渲染 |
| `工具/大模型测试工具链/` | 压测、仿真、崩溃复现、真实场景、报告生成 |

### 11.2 端点

- `GET /health`：永远 200，反映进程/模型/队列/缓存/NPU。
- `GET /ready`：模型就绪才 200，加载/崩溃 503 + `Retry-After`。
- `GET /v1/models`、`GET /v1/capabilities`、`GET /metrics`。
- `POST /v1/chat/completions`、`POST /v1/completions`、`POST /v1/responses`、`POST /v1/reset`。
- 未实现端点显式 501/400，不落框架 404。

### 11.3 运行

- 服务：`rkllm-server.service`，`/etc/default/rkllm-server` 由 systemd `EnvironmentFile=` 注入。
- 日志：`logging.file` 可切换 JSON/文本；uvicorn logger 归并到同一 handler；`X-Request-Id` 回写。
- 缓存：默认 `/dev/shm/rkllm/prefix`，单槽，字节级 LCP + `similarity=0.5`；失败自动降级。
- 安全：API key 走 Bearer；CORS 可配；请求体上限含 chunked 计数；错误体不回显 traceback。
