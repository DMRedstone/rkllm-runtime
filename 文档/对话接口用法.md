# RKLLM 本地对话与对外 API 使用说明

配套产物：`dist/rkllm-runtime_1.3.1-12_arm64.deb`、`dist/rkllm-toolkit/`（x86 主机的模型转换工具）。
目标板：OrangePi 5 Plus 8G（RK3588，aarch64），本文所有命令按 arm64 单架构编写。
以下行为均在包内文件上逐条核对，并用 `rkllm selftest` 端到端实测过。

---

## 0. 一句话

装完 deb 就有 `/usr/bin/rkllm`：不用在板上编译任何东西，不用 pip 装任何东西。只要板上跑着 NPU 驱动、你手上有 `.rkllm` 模型，就能 `rkllm chat 模型名` 本地对话，或 `rkllm serve 模型名` 对外提供 OpenAI 兼容 API。

---

## 1. 三步跑起来

```bash
# 1) 安装（Depends 会自动带上 python3 / libgomp1 / libstdc++6）
sudo apt install ./rkllm-runtime_1.3.1-12_arm64.deb
# 2) 自检：不需要模型和 NPU 就能跑，先确认包装好了
rkllm selftest
rkllm info                      # 看 NPU 驱动、运行时库、模型搜索路径
# 3) 放模型（deb 不含模型，见 §5），然后对话
mkdir -p /var/lib/rkllm/models
cp qwen2.5-1.5b.rkllm /var/lib/rkllm/models/
rkllm chat qwen2.5-1.5b
```

## 2. 命令一览

| 命令 | 作用 |
| --- | --- |
| `rkllm chat <模型>` | 交互式本地对话（REPL） |
| `rkllm run <模型> "提示词"` | 单次推理，只打印答案，适合脚本 |
| `rkllm serve <模型>` | 启动 OpenAI 兼容 HTTP API |
| `rkllm list` | 列出能找到的模型（并显示搜索路径） |
| `rkllm info [--json]` | 环境诊断：SoC、NPU 节点、运行时库、模型 |
| `rkllm selftest` | 不需要模型的端到端自检 |

完整手册随包安装：`man rkllm`（按 locale 自动选语言）、`man -L zh_CN rkllm`（强制中文）、`man -L en rkllm`（强制英文）。

> 

模型名既可以是裸名（`qwen2.5-1.5b`，省略 `.rkllm` 也行），也可以是绝对路径。裸名的搜索顺序：

```
$RKLLM_MODEL_DIR（冒号分隔可多个）→ /usr/share/rkllm-runtime/models
→ /var/lib/rkllm/models → ~/.local/share/rkllm/models → 当前目录
```

这些目录不由包创建（避免卸载时因目录非空而残留），用之前先 `mkdir -p`。

> 

常用全局选项：`--context 8192`、`--max-new-tokens`、`--threads N`、`--platform rk3588`（默认自动从设备树识别 SoC）、`--model-dir DIR`、`--no-freq-lock`、`-q`。

### REPL 内命令

| 输入 | 作用 |
| --- | --- |
| `/help` | 帮助 |
| `/clear` | 清 KV cache（忘记上下文） |
| `/set temperature 0.7` | 运行中改采样参数（也支持 top_k / top_p / repeat_penalty） |
| `/exit`、`/quit`、`exit` | 退出 |
| `Ctrl-C` | 中断本次生成（调用 `rkllm_abort`），不退出程序 |

## 3. 对外 API

### 3.1 前台启动

```bash
rkllm serve qwen2.5-1.5b --host 0.0.0.0 --port 8080
```

| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `/health` | GET | 模型名、是否在推理、排队数、累计统计 |
| `/v1/models` | GET | OpenAI 格式模型列表 |
| `/v1/chat/completions` | POST | OpenAI 兼容；支持 `stream`、采样参数、`tools` |
| `/v1/reset` | POST | 清空会话上下文 |
| 请求体可用字段：`messages`、`model`、`stream`、`temperature`、`top_p`、`top_k`、`max_tokens`、`repeat_penalty`、`frequency_penalty`、`presence_penalty`、`enable_thinking`、`tools`。 |  |  |

```bash
curl http://<board-ip>:8080/v1/chat/completions 
-H 'Content-Type: application/json' 
-d '{"messages":[{"role":"user","content":"你好"}],"stream":false}'
```

接 OpenAI SDK / OpenWebUI / Dify：

```python
from openai import OpenAI
client = OpenAI(base_url="http://<board-ip>:8080/v1", api_key="unused")
print(client.chat.completions.create(model="local",
messages=[{"role": "user", "content": "你好"}]).choices[0].message.content)
```

### 3.2 API key（鉴权）

未设 key 时接口完全开放；设置后所有端点都要求 `Authorization: Bearer <key>`，缺失或错误返回 `401`（OpenAI 格式错误体，`type: authentication_error`）。

```bash
# 方式一：命令行（--api-key 写在 serve 之后，位置任意）
rkllm serve qwen2.5-1.5b --api-key 我的密钥
# 等价写法，参数放前面也可以：
rkllm serve --api-key 我的密钥 qwen2.5-1.5b
curl -H "Authorization: Bearer 我的密钥" http://localhost:8080/v1/models
# 方式二（更推荐）：环境变量，密钥不出现在 ps 里
export RKLLM_API_KEY=我的密钥
rkllm serve qwen2.5-1.5b
```

两种方式等价，命令行优先。推荐环境变量：`--api-key` 的值会出现在 `ps aux` 和 `systemctl status` 里，同机其他用户能看到。

用 systemd 时把 key 写进配置文件即可——`EnvironmentFile` 的变量会直接进入服务进程环境，`rkllm` 读的就是它：

```bash
sudo sed -i 's|^#RKLLM_API_KEY=.*|RKLLM_API_KEY=我的密钥|' /etc/default/rkllm-server
sudo chmod 600 /etc/default/rkllm-server     # 该文件默认所有人可读
sudo systemctl restart rkllm-server
```

需要更严格的存放时，把 secret 放进 root-only 文件（`/etc/rkllm/server.env`，`chmod 600`），再用 `sudo systemctl edit rkllm-server` 加 `EnvironmentFile=/etc/rkllm/server.env`。

> 

比较用 `hmac.compare_digest` 常量时间完成，不会被时序攻击逐步猜出密钥长度。安全边界：这是明文 HTTP，key 只挡误用和端口扫描，挡不住同网段抓包；板子若暴露在不可信网络，请在前面套 TLS 反向代理。

### 3.3 作为系统服务

```bash
sudo sed -i 's/^RKLLM_MODEL=.*/RKLLM_MODEL=qwen2.5-1.5b/' /etc/default/rkllm-server
sudo systemctl enable --now rkllm-server.service
systemctl status rkllm-server
journalctl -u rkllm-server -f
```

单元的几个关键设计：

- 刻意不写 `ConditionPathExists` —— 没有任何一个路径能可靠代表"NPU 可用"。曾经的
`ConditionPathExists=/dev/rknpu` 就是错的：0.9.x 驱动不创建该节点（注册为 DRM render node），
于是单元在正常的板子上被静默跳过，`systemctl status` 只显示 `skipped, unmet condition check`。
现在由 runtime 在启动时判断 NPU 是否可用并给出明确原因（见 §7 与 changelog 1.3.1-5）。

- `ExecStart` 用 `/bin/sh -c` 包装 —— systemd 会把未设置的变量展开成一个空参数，裸写 `${RKLLM_PLATFORM_ARG}` 就会给 `rkllm` 传去一个空字符串，argparse 视之为多余的位置参数并退出 2，`systemctl status` 里只剩一句 `status=2`，极难排查。经 shell 包装后，未加引号的空变量会整个消失。校验器以 `unit ExecStart survives unset vars` 守住这条。

- `ExecStartPre` 检查 `RKLLM_MODEL` 是否已填，没填就报错退出（不会静默跑一个空服务）。

- `Restart=on-failure` + `StartLimitBurst=5` —— 崩溃自动重启，但没有 NPU 的机器最多重试 5 次就停，
不会无限刷日志。

- `LimitNOFILE=102400` —— 长上下文需要较大的 fd 上限。

- 包只安装单元，不 enable 不 start —— 是否开机跑服务由你决定。

`/etc/default/rkllm-server` 是 dpkg conffile：本地修改在升级后保留，卸载（`remove` 或 `purge`）时随包删除。文件正文是中英双语，每个 `serve` 参数都有自己的配置项，可选值以注释形式给出（`#RKLLM_XXX=...`），完整清单直接看该文件即可。速查：

| 参数 | 配置项 | 默认 |
| --- | --- | --- |
| 模型（必填） | `RKLLM_MODEL` | 空，不填则服务拒绝启动 |
| 监听地址 / 端口 | `RKLLM_HOST` / `RKLLM_PORT` | `0.0.0.0` / `8080` |
| 鉴权密钥 | `RKLLM_API_KEY` | 空（不鉴权） |
| 跳过 SoC 自动探测 | `RKLLM_PLATFORM_ARG` | `--platform rk3588` 之类 |
| 上下文窗口 | `RKLLM_CONTEXT` | `4096` token |
| 单次生成长度 | `RKLLM_MAX_NEW_TOKENS` | `2048` token |
| CPU 核数 / 不锁频 | `RKLLM_THREADS` / `RKLLM_NO_FREQ_LOCK` | 按 SoC / 关闭 |
| 系统提示词 / 无上下文 | `RKLLM_SYSTEM` / `RKLLM_NO_HISTORY` | 空 / 关闭 |
| 采样 | `RKLLM_TOP_K` / `RKLLM_TOP_P` / `RKLLM_TEMPERATURE` / `RKLLM_REPEAT_PENALTY` | `1` / `0.9` / `0.8` / `1.1` |
| 排队上限 / 超时 | `RKLLM_MAX_QUEUE` / `RKLLM_QUEUE_TIMEOUT` | `32` / `600` 秒 |
| 模型目录 / 运行时库 | `RKLLM_MODEL_DIR` / `RKLLM_LIB` | 内置搜索路径 / 自动 |
| 少打印 / 兜底参数 | `RKLLM_QUIET` / `RKLLM_EXTRA_ARGS` | 关闭 / 空 |

命令行参数永远优先于配置文件；配置文件里的值解析失败会被记录到 journal 并回退到默认值，不会让服务启动失败。

## 3.4 `serve` 启动后终端不再输出，是卡住了吗？

不是。 `rkllm serve` 是前台服务，打印完启动横幅就进入监听状态，本来就不会再有输出。看到这几行就说明已经就绪：

```
I rkllm: loading rkllm model from /path/to/model.rkllm
I rkllm: rkllm-toolkit version: 1.2.1, max_context_limit: 4096, ..., model_dtype: W8A8
I rkllm: Enabled cpus: [4, 5, 6, 7]
I rkllm: Using mrope
rkllm 1.3.1-1 serving model 'xxx' on http://0.0.0.0:8080
status    : model loaded, listening. ...
try       : curl http://127.0.0.1:8080/health        (Ctrl-C stops it)
```

出现 `status : model loaded, listening` 就意味着 `rkllm_init` 已成功返回、端口已绑定。依赖缺失不会表现为"静默卡住"——那会在启动时直接报 `ImportError` / `OSError` 并退出。

正确验证方式是另开一个终端（不要在这个终端按回车）：

```bash
curl -s http://127.0.0.1:8080/health     # 立即返回 JSON，不涉及推理
```

- `/health` 有响应 → 服务正常。它只回报状态，不做推理。

- `/health` 通、但 `/v1/chat/completions` 慢 → 那是推理本身慢，不是卡死。首次请求要先把 prompt 预填充（prefill）进 KV cache，3B 模型 + 长 prompt 在这个阶段可能等几十秒。发起请求后终端会打印 `[rkllm] 127.0.0.1 - "POST /v1/chat/completions HTTP/1.1" 200`，看到这一行说明请求真的在跑。

- `curl` 连不上 → 检查端口占用（`ss -ltnp | grep 8080`）和放行规则，与模型无关。

想在本机做交互式测试，用 `rkllm chat <模型>`（会进 REPL）；`serve` 不提供交互界面。
注意不要同时跑 `chat` 和 `serve` 两个进程——它们会各自加载一份模型，8G 内存扛不住。

多模态模型的限制：像 `qwen2.5-vl-*` 这类 VL 模型，日志里的 `Using mrope` 说明它带多模态位置编码。当前 `/usr/bin/rkllm` 的对话与 API 只走纯文本输入（`RKLLM_INPUT_PROMPT`），不支持图片/音频输入。纯文本对话可以正常使用；要真正用上视觉能力，需要走 multimodal 示例（`/usr/share/rkllm-runtime/examples/multimodal_model_demo`，那部分需要 `.rknn` 视觉编码器）。

补充（1.3.1-4）：早前"回答像考卷"的现象与 VL 模型无关，根因是 chat template 被
`rkllm_set_chat_template` 禁用，详见 §7。

## 3.5 客户端怎么填 API 链接和 API key

### 服务端先决定要不要鉴权

```bash
# 不鉴权（默认）：客户端填什么 key 都会被忽略
rkllm serve /path/model.rkllm
# 鉴权：服务端必须自己设 key，客户端填相同的值
RKLLM_API_KEY=我的密钥 rkllm serve /path/model.rkllm
```

systemd 场景写进 `/etc/default/rkllm-server`（`RKLLM_API_KEY=` 那行，去掉行首 `#`），然后
`sudo chmod 600 /etc/default/rkllm-server && sudo systemctl restart rkllm-server`。

关键规则：服务端设了 key，客户端必须填完全相同的值（不要带引号、不要带 `Bearer ` 前缀，客户端会自己加）；服务端没设 key，客户端的 key 字段随便填一个非空字符串（如 `sk-none`）——留空有些客户端会直接拒绝发送请求。

### Base URL 怎么填

先说结论：填 `http://<板子IP>:8080/v1`，只到 `/v1` 为止。

| 客户端 | Base URL / 接口地址 | 备注 |
| --- | --- | --- |
| Python `openai` SDK | `http://<IP>:8080/v1` | SDK 自己拼 `/chat/completions` |
| OpenWebUI | `http://<IP>:8080/v1` | 模型列表能拉到就说明填对了 |
| Dify / FastGPT | `http://<IP>:8080/v1` |  |
| Cherry Studio / ChatBox / NextChat | `http://<IP>:8080/v1` |  |
| LM Studio 客户端类 | `http://<IP>:8080/v1` |  |
| `curl` | 完整端点 `http://<IP>:8080/v1/chat/completions` | 见下方示例 |

板子 IP 用 `hostname -I` 或 `ip -4 addr` 查。服务端默认 `--host 0.0.0.0`（监听所有网卡），所以局域网内别的机器能直接连。

容错：本版同时接受不带 `/v1` 的路径（`/chat/completions`、`/models`、`/reset`），所以 base_url 填成 `http://<IP>:8080` 也能用。但不要把完整端点填进 base_url——那样会变成 `/v1/chat/completions/chat/completions`，必然 404。

### 完整 curl 示例

```bash
IP=192.0.2.50                       # 换成你的板子 IP
# 探活（不需要 key，也不触发推理）
curl -s http://$IP:8080/health
# 非流式
curl -s http://$IP:8080/v1/chat/completions 
-H 'Content-Type: application/json' 
-H 'Authorization: Bearer 我的密钥' 
-d '{"messages":[{"role":"user","content":"你好"}],"max_tokens":256}'
# 流式
curl -N http://$IP:8080/v1/chat/completions 
-H 'Content-Type: application/json' 
-d '{"messages":[{"role":"user","content":"讲个笑话"}],"stream":true}'
```

### 报错对照表

| 现象 | 原因 |
| --- | --- |
| `404 Not Found` | base_url 写成了完整端点（多带了 `/chat/completions`），或路径拼错 |
| `401 Unauthorized` | 服务端设了 key，客户端没填 / 填错 / 多了空格引号 |
| `503` + `queue is full` | 排队超限，等一会儿重试（见 §4） |
| `400 prompt too long` | 输入超过模型上下文预算，缩短 prompt 或加大 `--context` |
| 连接被拒绝 / 超时 | IP 写错、用了 `localhost`（那是客户端自己）、服务端绑了 `127.0.0.1`、端口不对、防火墙 |
| 客户端能连但模型列表为空 | 少数客户端要求 `GET /v1/models` 返回特定结构；本服务已按 OpenAI 格式返回，可先用 curl 验证 |

## 4. 并发与排队语义

NPU 一次只能跑一个请求，这是物理限制。本版的处理是排队而非直接拒绝：

- `--max-queue N`（默认 32）表示允许等待的请求数；正在推理的那个不占这个额度。

- 超出额度立即返回 `503`，带 `Retry-After: 5` 和 OpenAI 格式错误体。

- 等待超过 `--queue-timeout`（默认 600 秒）也返回 503。

- `/health` 的 `queue_length` 即当前等待中的请求数。

上游的 Flask 服务是「第二个请求立刻 503」，且其队列额度会把正在推理的请求也算进去。本版两处都已修正，并由 `rkllm selftest` 的队列用例锁定（`1 个在跑 + 1 个排队 + 第 3 个 503`）。

> 

会话上下文由服务端维护（`keep_history=1`），客户端只需发最新一条消息；若客户端习惯每轮发完整历史，服务端也只取最新一条交给 runtime，不会重复灌入。要无状态模式用 `--no-history`，`POST /v1/reset` 可随时清空。

## 5. 模型从哪来

`.rkllm` 是 LLM 专用格式，只能在 x86 主机上转换，板上转不了：

```bash
# x86 Ubuntu 主机（Python 3.10 / 3.11 / 3.12 任选，见 dist/rkllm-toolkit/）
pip install dist/rkllm-toolkit/packages/rkllm_toolkit-1.3.1-cp310-cp310-linux_x86_64.whl
pip install -r dist/rkllm-toolkit/packages/requirements.txt
# 转换脚本随 deb 提供
python3 export_rkllm.py ...      # 见 /usr/share/rkllm-runtime/examples/rkllm_api_demo/export/
scp model.rkllm board:/var/lib/rkllm/models/
```

- `.rknn` ≠ `.rkllm`：`.rknn` 是视觉模型格式，LLM 运行时不能直接跑。包内只有 multimodal 示例会用到 `.rknn`（用于图像/音频编码器）。

- 仓库里没有任何模型文件、也没有预编译可执行文件——这是上游发布包的形态，不是打包遗漏。

## 6. 前置条件与已知限制

必须满足：

⚠️ `/dev/rknpu` 通常不存在，这不是故障。 0.9.x 及更新版本的驱动把 NPU 注册成
DRM render node，不创建字符设备节点。正确的确认方式：

```bash
sudo cat /sys/kernel/debug/rknpu/version          # 最权威，应输出 "RKNPU driver: v0.9.8"
ls -l /sys/class/drm/renderD*/device/driver       # driver 链接应指向 RKNPU
dmesg | grep -i rknpu                             # 应有 "Initialized rknpu x.y.z"
ls /dev | grep -E 'galcore|rknpu'                 # 空的是正常的，别被这一点误导
```

`rkllm info` 会替你依次检查这些信号（含老式 `/dev/rknpu`），并打印驱动版本。
驱动未就绪时先解决它再谈跑模型（OrangePi 官方源安装或自行编译均可）。

1. 板上要有 rknpu 内核驱动。本包不含驱动、不编译 DKMS，用 `rkllm info` 确认。

1. glibc ≥ 2.29（Ubuntu 20.04+ / Debian 11+），库引用了 GLIBC_2.29 符号。
OrangePi 5 Plus 官方 Ubuntu 22.04/24.04 镜像均满足。

1. python3，已写进 `Depends`。

1. 锁频提升性能需要 root —— `rkllm` 在 root 下自动调用 `/usr/bin/rkllm-fix-freq-rk3588`（绝对路径，不依赖当前目录，这修掉了上游 Flask 脚本的隐性坑）；非 root 会跳过并提示，不报错。

OrangePi 5 Plus 8G 的选型建议：1.5B~4B 量化模型跑得舒服；7B 量化在 8G 内存下要压
`--context 2048` 并预留 swap，否则 prefill 阶段可能 OOM。

限制：

- 单并发（NPU 物理限制），吞吐 = 1/延迟。

- `usage` 里的 token 数是 `len(text.split())` 估算，不是真实 tokenizer 计数，别用于计费。
非流式响应从 1.3.1-3 起才带上这两个数字（此前恒为 0，客户端会显示 "0 tokens"）。

- `--context` / `--max-new-tokens` 只是上限，实际还受模型本身支持的上下文长度约束。

- 输入长度上限（真实客户端最容易撞上的限制）：模型窗口 4096 tokens，换算过来大约是
3000~4000 个汉字（更准确地说约 12288 字节）。用户自己的文字超过这个量会被 400 拒绝。
实测：3000 字符的文档可处理但需要约 30 秒（prefill 占绝大部分）；8000 字符会被拒绝。
长文档需要客户端自己分块或做 RAG——这是模型能力上限，服务端无法绕过。

- 客户端的系统提示词不再需要用户操心（1.3.1-10）：Agent 类客户端（WorkBuddy 等）会附带
几十 KB 的自有提示词——实测某客户端在用户只输入"你好"时发出了 57283 字节 system 内容，
任何 4096 token 窗口都装不下。现在遇到这种情况会丢弃系统提示词并把请求正常服务，
而不是整个请求失败。日志会记录：
`[rkllm] system prompt dropped: 57283 bytes does not fit a 4096-token window`。
注意副作用：模型会失去该提示词给出的行为约束与角色设定（仍能正常对话）。
另外推理日志现在分别显示 system / user 的字节数：
`[rkllm] inference: prompt ~2 tokens (6 bytes: system 0, user 6), ...`

- 如果模型本身支持更大的上下文，可以用 `--context 8192`（或更大）来容纳更多内容；
超过模型上限时 runtime 会自动按模型上限截断，不会报错，可以直接试。

- CLI 输出为英文，因为板端镜像常见 `C` locale，中文会乱码。需要中文提示可直接改 `packaging/cli/rkllm.py` 重新打包。

## 7. 段错误 / 请求挂起 / 回答异常排查

已确认并修复的根因之一：不要在 system prompt 上调用 `rkllm_set_chat_template`（1.3.1-4）

之前每当请求里带 system message，脚本就会调用 `rkllm_set_chat_template`。runtime 对此有明确警告：

```
W rkllm: Calling rkllm_set_chat_template will disable the internal automatic
chat template parsing, including enable_thinking.
```

一旦调用，模型内置的对话模板就被禁用，模型开始收到没有任何特殊 token 的裸文本。后果是
它像"接着往下写文档"一样乱答（例如把提问当成考卷题目作答），并且常常不输出 EOS，表现为
请求一直不返回——这正是"调用后无响应"的原因。

更糟的是这个设置对整个 handle 生命周期都有效：客户端发过一次带 system 的请求（OpenWebUI
生成会话标题时就会发），之后所有请求——包括不带 system 的——都被污染，直到服务重启。

现已改为把 system 文本前置拼接到 prompt 里，完全不再调用该函数，内置模板保持完好。
新增自检用例 `system message reaches the model` 锁定。
另外这也意味着：此前"模型回答质量差"的现象不是 VL 模型的问题，是模板被破坏所致。

`rkllm_set_chat_template` 的封装仍保留在脚本里（带警告注释），只在确实要自定义模板时才该用；
且 prefix/postfix 绝不能传 NULL（见下一条）。

> 

已确认并修复的根因之二：绝不向 C API 传 NULL 指针（1.3.1-2）

`rkllm_set_chat_template` 的 `prompt_prefix` / `prompt_postfix` 两个参数曾被传成 `NULL`。
runtime 对它们无条件解引用，于是任何带 system message 的请求会让进程直接段错误。
上游 C++ demo 对此的写法是 `rkllm_set_chat_template(h, "", "<｜User｜>", "<｜Assistant｜>")`
—— 永远是真实字符串。复现记录：不带 system 的请求（含 2520 字节长 prompt）全部正常；
一旦加上 `{"role":"system", ...}` 就立即崩溃、服务进程消失。

> 

段错误是原生崩溃（`librkllmrt.so` 内部访问了非法内存），Python 层无法捕获——进程直接死，服务随之消失，日志常常就停在请求那一行。它不是缺依赖：缺依赖会抛 `ImportError`/`OSError` 并带 traceback。

### 板端实测验证结果（1.3.1-4，2026-10-14）

修复后在真实板上逐项复测（工具：`tools/verify_board.py --host <板IP>:8080 --key <key>`）：

| 检查 | 结果 |
| --- | --- |
| 裸请求 | ✅ `我是来自阿里云的超大规模语言模型，我叫通义千问。` |
| 长 system（原挂起场景） | ✅ 3.3s，且完整遵守 system 指令输出 `{"isNewTopic": false, "title": "Python Quick Sort Implementation"}` |
| 紧跟其后的裸请求（污染检测） | ✅ `杭州，位于中国浙江省东部，是一座历史悠久、风景秀丽的城市。`——模板未被污染 |
| system + 多轮 | ✅ `4` |
| 流式 | ✅ 9 chunks，以 `[DONE]` 结束 |
| 超长输入 | ✅ 400 拒绝 |
| 结束时服务状态 | ✅ `requests=11 errors=0` |

对照修复前：同一个"紧跟其后的裸请求"返回的是 `的西湖。答：…考查知识点：综合读写`（考卷续写）。
这组对比确认了两个根因都已消除。

剩下的排查方法在上面两个根因已修复的前提下，仍适用于其他异常：

### 第一步：判断是否与 `/usr/bin/rkllm` 有关

用完全独立的实现路径跑同一个模型做对照——上游的 C++ demo：

```bash
cp -r /usr/share/rkllm-runtime/examples/rkllm_api_demo ~/rkdemo
cd ~/rkdemo/deploy && ./build-linux.sh        # 板端本地编译
./llm_demo /home/user/qwen2.5-vl-3b-w8a8_level1_rk3588.rkllm 512 4096
```

- 它也崩 → 与 `/usr/bin/rkllm` 无关，是模型 / runtime / 驱动层面的问题（见第三步）。

- 它正常，只有 rkllm 崩 → 问题在本包的 ctypes 封装，请把服务端完整日志发我。

### 第二步：区分 HTTP 层还是推理层

```bash
rkllm run /home/user/qwen2.5-vl-3b-w8a8_level1_rk3588.rkllm "你好"
```

单次、非流式、短 prompt。崩 → 与 HTTP/客户端无关；不崩 → 与客户端发的内容规模有关（见下）。

### 第三步：按可能性排序的原因

1. prompt 超过模型上下文（最常见）。你的启动日志里 `max_context_limit: 4096`，一旦输入超过 4096 token，runtime 会越过 KV cache 边界崩溃。注意客户端会自动塞系统提示词和对话历史（OpenWebUI 之类尤其激进），实际 prompt 可能远超你以为的长度。
本包现已内置防护：超过 `--context × 8` 字节的请求直接返回 400 而不是交给 runtime。但这只是粗估（本脚本没有 tokenizer），"刚好超一点"仍可能漏过——请确认客户端发的总长度。

1. 模型与 runtime 版本不匹配。你的模型是 `rkllm-toolkit 1.2.1` 转的，runtime 是 1.3.1；跨版本转的模型（尤其 VL）有崩的先例。换一个同版本转换的模型对照即可确认。

1. NPU 驱动版本偏低。`rknpu driver version: 0.9.8`。较新的 runtime 有时需要更新的驱动。

1. 内存不足。8G 内存跑 3B + 4096 上下文时余量不大，长 prompt 让 KV cache 增长，可能触发 OOM 而非崩溃——但如果 NPU 侧内存分配失败，表现也可能是段错误。

1. VL 模型的文本模式。`Using mrope` 说明这是多模态模型（Qwen2.5-VL）。本包只走纯文本输入路径，VL 模型是否支持纯文本推理由 runtime 决定。

### 收集证据（决定能否定位的关键）

```bash
dmesg | tail -30                     # 看 rknpu 有没有报错，OOM killer 有没有动过手
```

服务端现在会在推理前打印一行请求规模：

```
[rkllm] inference: prompt 1234 bytes, max_tokens 4096, stream=True, history=1
```

崩溃时日志的最后一行就是肇事请求的规模。把这几样发我就能继续判断：dmesg 输出、崩溃前完整的服务端日志、客户端实际发送的 prompt 长度、是流式还是非流式。

### 最小复现步骤（从最短请求逐级加压）

先确认服务健康——这一步不碰 NPU，返回 JSON 就说明进程活着：

```bash
curl -s http://127.0.0.1:8080/health
```

然后逐级加压，每发一条就回看服务端日志：

```bash
# ① 极短输入，32 个 token 输出，最快能验证基本通路
curl -s http://127.0.0.1:8080/v1/chat/completions 
-H 'Content-Type: application/json' 
-d '{"messages":[{"role":"user","content":"你好"}],"max_tokens":32}'
# ② 加一个长系统提示词，模拟客户端（OpenWebUI 之类会塞很多）
python3 - <<'EOF'
import json, urllib.request
body = {"messages": [
{"role": "system", "content": "You are a helpful assistant. " * 200},
{"role": "user", "content": "你好"}],
"max_tokens": 32}
req = urllib.request.Request("http://127.0.0.1:8080/v1/chat/completions",
data=json.dumps(body).encode(),
headers={"Content-Type": "application/json"})
print(urllib.request.urlopen(req, timeout=300).read().decode()[:400])
EOF
```

判定：

| ① 的结果 | ② 的结果 | 结论 |
| --- | --- | --- |
| 正常 | 正常 | 服务本身没问题，之前那次崩溃与客户端的具体请求内容有关，把客户端的 prompt 长度发我 |
| 正常 | 崩溃 | 确认是 prompt 长度问题——看日志里那条 `inference: prompt N bytes`，与 `--context × 8` 的预算对比 |
| 崩溃 | — | 与输入长度无关，是模型 / runtime / 驱动层面问题，走上面的"第一步"用上游 C++ demo 对照 |

想在推理进行时观察状态，另开一个终端：

```bash
while true; do curl -s http://127.0.0.1:8080/health | head -c 160; echo; sleep 1; done
```

推理期间 `busy` 会变成 `true`，结束后 `stats.requests` 递增——这能区分"在想"和"真死了"。

提示：若客户端填了 API key 而服务端没设，服务端会显示 `api key : none` 并忽略客户端发来的密钥（不鉴权）。这是预期行为，与崩溃无关。要让服务端校验，得在服务端设置（见 §3.2）。

## 8. 覆盖安装 / 升级

可以。`apt install ./新包.deb` 或 `dpkg -i 新包.deb` 都会走 dpkg 的 upgrade 路径，`prerm upgrade → unpack → postinst configure <旧版本>`，本包的三个维护脚本都已按这个流程写好。

但有几个必须注意的点：

### ① 服务配置不会再被升级改动（1.3.1-12 起）

`/etc/default/rkllm-server` 现在是 dpkg conffile，和你用过的其他软件一样：升级时 dpkg 保留你改过的内容，包里的默认值不会覆盖它。文件正文也刻意不含版本号，所以跨版本升级不会重写它，连你为放密钥而 `chmod 600` 的权限都原样保留。

卸载时会删掉它，包括 `apt remove`——dpkg 本来只在 `purge` 时删 conffile，本包在 `postrm` 里显式删除，以维持"卸载无残留"。想留着就先备份。

唯一一次例外：如果你现在装的是 1.3.1-11 或更早，那版里它是普通文件而不是 conffile。升级到 12 时 dpkg 无法判断磁盘上这份文件是"你改过的"还是"包自带的"，于是会问一次：

```
Configuration file '/etc/default/rkllm-server'
==> File on system created by you or by a script.
==> File also in package provided by package maintainer.
What would you like to do about it ?
Y/I/N/O/D/Z [default=N]
```

选 N（保留当前版本），你的 `RKLLM_MODEL` / `RKLLM_API_KEY` / 端口全部原样保留（代价是没有新版的中英注释，可以事后手工补注释）。选 Y 会装上新模板，但里面的 `RKLLM_MODEL` 是空的，需要自己再填一次。非交互安装（`apt -y`）的默认动作就是 N。

从 12 往后不再有这一提示，升级全程无感。

```bash
# 稳妥做法：先备份，再升级
sudo cp /etc/default/rkllm-server /root/rkllm-server.conf.bak
sudo apt install ./rkllm-runtime_1.3.1-12_arm64.deb
# 若升级时选了 Y，把两行设置填回去：
#   grep -E '^RKLLM_(MODEL|API_KEY)=' /root/rkllm-server.conf.bak
sudo systemctl restart rkllm-server
```

### ② 正在运行的服务会被自动重启

升级会把 `librkllmrt.so` 和 `/usr/bin/rkllm` 换成新文件，而运行中的进程仍映射着旧的 inode。`postinst` 里做了 `is-active` 守卫的 `restart`——只有你原本就启动了的服务才会被重启，没启动的不会被悄悄拉起。如果你不想它自动重启，先 `systemctl stop rkllm-server` 再升级。

### ③ 依赖变化

新版本的 `Depends` 比旧版多了 `python3:any`（`/usr/bin/rkllm` 需要解释器）。用 `apt install ./file.deb` 会自动补齐；用 `dpkg -i` 可能报缺依赖，补一句 `sudo apt -f install` 即可。

### 推荐的完整升级流程

```bash
rkllm selftest                                                  # ① 先确认现状
sudo apt install ./rkllm-runtime_1.3.1-12_arm64.deb             # ② 覆盖安装（配置自动保留）
sudo systemctl restart rkllm-server                             # ③ 需要时重启（原本在跑的会自动重启）
```
