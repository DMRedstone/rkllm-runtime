## 三、改进方案（2026-11-26 汇总）

本方案整合当日全部调研结论：视觉多模态、语音、依赖与构建、性能基线与官方资产复用。所有取舍都记了理由，包括未采用的方案。

### 3.0 结论摘要

| 主题 | 结论 | 关键理由 |
|---|---|---|
| 是否改用 Firefly LlamaPi | **不替代**，仅吸收其模型分发体验 | 闭源 deb；无 MCP、无 Prometheus 指标、无鉴权、无故障自愈；`/health` 仅返回 `ok`，本项目连接器自适应依赖 `perf/limits` 快照；其多卡卖点在单 RK3588 8G 上不存在 |
| 视觉实现 | 内置官方 C++，编 `libimgenc.so` | 第三方不重写；Python 直绑 rknn 结构体风险高 |
| 视觉模型 | `t-firefly/qwen3.5-4b-rkllm-rk3588` | 用户指定；原生 VLM，`.rkllm` + `.rknn` 成对 |
| OpenCV | **静态链接 3rdparty 的 3.4.5** | 系统 apt 是 4.5.4，与 3.4.5 大版本不同，ABI 不兼容；静态链接零运行时依赖 |
| 语音 | sherpa-onnx + SenseVoice，独立子进程走 CPU | apt 无可用 ASR；CPU 与 LLM 的 NPU 互补可并行 |
| 依赖安装 | apt + pip，不自建源、不建 venv | 系统清洁安装专用；pip 直接装系统 Python |
| 打包流程 | 保留现有纯 Python 打包，另加交叉编译一步 | `make_deb.py --packer ar` 不依赖 dpkg，Windows 可跑 |
| 性能判定 | 用官方 `benchmark.md` 基线比值判定是否降频 | 项目历史性能问题多属未定频 / 降频 / 非 `optimization_level=0` |

### 3.1 性能基线校验（PI-1，可独立先行）

**依据**：上游发行包内 `benchmark.md`，数据均在满频、`optimization_level=0` 条件下测得。

基线样例（RK3588，w8a8，seqlen 128 / new_tokens 64）：

| 模型 | TTFT | Tokens/s | 内存 |
|---|---|---|---|
| Qwen3.5 4B | 2068.88 ms | 6.22 | 4575.78 MB |
| Qwen3-VL 2B | 383.62 ms | 14.98 | 1868.98 MB |
| MiniCPM3 4B | 1408.49 ms | 5.94 | 4384.02 MB |
| Qwen3.5 2B | 776.95 ms | 13.59 | 2121.91 MB |

> 视觉基线取 **Qwen3.5 4B** 那一行。多模态运行时，内存判据要在 LLM 基线之外**另加视觉编码器常驻**（约 +1.5–1.8 GB），否则会把正常状态误判为超限。

- [ ] **基线表内置**：新增静态基线表（型号 → TTFT / Tokens/s / 内存），来源标注官方 `benchmark.md` 版本，随包分发。
- [ ] **匹配模型**：启动后按 `model_class`、参数量、量化档位匹配同一行；匹配不到则不判定，只输出「无基线可比」。
- [ ] **取实测值**：从 `/health.perf` 取预热后的 `decode_tok_s` 与 `ttft_s`，用稳定窗口而非首个请求（避免 prefill 冷启动干扰）。
- [ ] **比值判定**：`≥ 0.85` 正常；`0.60–0.85` 可疑（未定频 / 温度降频 / NPU 被占用）；`< 0.60` 疑似降频，输出固定诊断清单。
- [ ] **诊断清单（固定四项）**：NPU devfreq 的 governor 是否 `userspace` 且 `min=max` 最高档；CPU governor；NPU 是否被其他进程占用；模型是否以 `optimization_level=0` 转换。
- [ ] **只报告不干预**：结果只进 `rkllm info` 与日志；改频率仍由 `model.freq_lock` / `freq_helper` 负责。

**边界**：基线是「是否降频」的参照，不是新的性能目标，也不参与队列调度或 job 判定。

#### 3.2.2 模型

- 基线：`t-firefly/qwen3.5-4b-rkllm-rk3588`（Apache-2.0，**6.30 GB**，LlamaPi Ready）。
- Qwen3.5-4B 是原生 VLM（early fusion，24 层视觉塔，patch 16），不是纯文本模型。
- RKLLM 部署必须**成对**使用 `.rkllm` 与匹配的 `.rknn`，且同平台同批次。RK3588 W8A8 参考命名：`Qwen3.5-4B_RK3588_w8a8.rkllm` + `Qwen3.5-4B_vision_RK3588.rknn`（实际文件名以下载清单为准）。
- **内存**：LLM w8a8 约 4.5 GB + 视觉编码器约 1.5–1.8 GB，合计接近 6.3 GB；8G 板扣除系统占用后余量极小，必须压 context，`memory_check` 要按两项之和判定。

#### 3.2.3 实现路线：内置官方 C++

- [ ] **A1 板端基线验证（阻塞项）**：下载配对文件，板端跑通官方 `multimodal_model_demo` 原版，记录模型加载/编码耗时、`img_vec.bin` 的 shape 与 SHA256、模型格式版本是否与 deb 内 `librkllmrt.so` 匹配（不匹配报 `Invalid RKLLM model version`）。**同时实测 LLM + 视觉编码器的实际常驻内存**，作为 `memory_check` 预算与 context 压缩幅度的依据。
- [ ] **A2 内置官方 C++ 编码器**：`打包/vision/` 放打补丁的 `image_enc.cc`（仅修 A4 两处，文件头注明上游版本与修改点）与 `imgenc_wrap.cc`；复用官方 `expand2square` 与 OpenCV 预处理，导出单入口 `rkllm_vision_encode(model_path, image_path, out_buf, &n_tokens, &embed_size)`；编译成 `libimgenc.so` 放 `/usr/lib/rkllm-runtime/`。
  - **OpenCV 静态链接** 3rdparty 的 `opencv-linux-aarch64/lib/*.a`，零运行时依赖；预计 `.so` 增加 10–20 MB。
  - 编译要点：`aarch64-linux-gnu-g++ -shared -fPIC -O2 -I<3rdparty>/include -I/usr/include/rknn`，链接 `libopencv_core.a libopencv_imgproc.a libopencv_imgcodecs.a` 与 `librknnrt.so`，补 `-lpthread -ldl -lz -ljpeg -lpng`。
- [ ] **A3 Python 侧薄封装**：新增 `worker/vision.py`，只做 ctypes 调 `rkllm_vision_encode()` 与句柄生命周期管理，**不做任何像素运算**；`model_width/height`、`n_image_tokens`、`embed_size` 由 `.so` 探测后回传。
- [ ] **A4 上游缺陷补丁**（体现在 A2 的 `image_enc.cc`）：① dims 推断用「第一个 > 1 的维度」猜 token 数，`dims[i+1]` 在 `i=3` 越界 → 取末两维 + `n_dims >= 2` 断言；② `rknn_outputs_release(..., 1, outputs)` 写死 1，`n_output > 1` 泄漏 → 传 `io_num.n_output`。
- [ ] **A5 worker 接入**：`conversation.py` 返回 `(prompt, images)` 并保留 `image_start/end/content` 占位符；`pipeline.py` 透传 images；`engine.py` 新增 `RKLLM_INPUT_MULTIMODAL` 分支填 `_MultiModalInput.image`；`frames.py` 因 embedding 约 3.7 MB（base64 后逼近 8 MiB）改为临时文件传路径或新增二进制帧。
- [ ] **A6 对外接口**：`schemas.py` 支持数组 `content` 与 `image_url`（data URI / 本地路径）；`caps.py` 的 `image_url` 改 native，远程 `http(s)` 一期明确拒绝且标 unsupported；探测到的 `n_image_tokens`/`embed_size` 写入 `/v1/capabilities`。

### 3.3 语音

#### 3.3.1 选型

- 引擎：sherpa-onnx（Apache 2.0），CPU 推理，不占 NPU。
- 模型：SenseVoice int8（中英日韩粤，229 MB）+ silero VAD。
- 理由：模型可直接下载无需转换；CPU 与 LLM 的 NPU 推理互补，可真并行；不绑定单一模型族。

#### 3.3.2 为什么必须 pip

| 发行版 | whisper.cpp | sherpa-onnx | python3-pocketsphinx |
|---|---|---|---|
| Ubuntu 22.04 | 无 | 无 | 有 |
| Debian 12 | 无 | 无 | 有 |
| Debian 13 | 无（仅 sid） | 无 | 有 |
| Ubuntu 26.04 | 有 1.8.3 | 无 | 有 |

whisper.cpp 2024 年后才进 Debian，只存在于 sid 与 Ubuntu 26.04；sherpa-onnx 从未进入发行版仓库；`python3-pocketsphinx` 中文声学模型缺失，只适合命令词级识别。

#### 3.3.3 改动清单

- [ ] **B1 依赖落地**：`control.in` 加 `python3-pip`；postinst 执行 `PIP_BREAK_SYSTEM_PACKAGES=1 python3 -m pip install --no-cache-dir sherpa-onnx==<version>`（直接装系统 Python，不建 venv、不自研安装子命令）；末尾 `python3 -c "import sherpa_onnx"` 校验，失败即让 dpkg 配置失败。
- [ ] **B2 解码层**：一期只承诺 `wav`（标准库 `wave`，转 float32 / 16 kHz / mono）；其他格式经 `ffmpeg`（放 Suggests），缺失时返回明确错误码。
- [ ] **B3 独立子进程 + CPU**：与推理 worker 并列、由 supervisor 管理；不占 NPU，可与 LLM 真并行；主服务通过 UDS 帧协议（复用 `frames.py`）送音频路径与参数、收文本。**不用线程池**：worker 单线程串行会被阻塞，且 onnxruntime 的 GIL 行为不可控。
- [ ] **B4 接口**：`POST /v1/audio/transcriptions`（multipart：file/model/language/response_format/temperature）；`json` 返回 `{"text": ...}`，`text` 返回纯文本，`srt`/`vtt`/`verbose_json` 一期 501；移除 `unsupported.py` 中 audio 的 501 分支。
- [ ] **B5 MCP**：`本地模型连接器/rkllm/mcp/tools.py` 增 `local_llm_transcribe`（音频路径/Base64、language、response_format），受 `mcp.tools` 白名单控制；同步 `mcp_conformance`。
- [ ] **B6 能力与文档**：`caps.py` 的 `notes` 写明格式范围与长度上限；`文档/对话接口用法.md` 由 `render_caps_doc.py` 重新生成并 `--check` 通过。
- [ ] **B7 语音资产**：`audio_enc.cc`（182）、`audio_utils.cc`（211）、`audio_encoder.cpp`（174）均不采用；`audio_utils.cc` 的 mel 参数硬编码为 `GEMMA4_*`（SR 16000 / HOP 160 / FRAME 320 / FFT 512 / MEL_FLOOR 1e-3 / PAD 128 / 左垫 160），注释写明 mirroring HuggingFace `Gemma4AudioFeatureExtractor`，只适配单一模型族，留档作备选参考。

### 3.4 依赖、构建与卸载

#### 3.4.1 apt 依赖（`control.in`）

```
Depends: python3, python3-jsonschema, ..., python3-pip
Suggests: ..., ffmpeg
```

- 视觉不再新增 `python3-opencv`：预处理在 C++ 内静态链接完成。
- `ffmpeg` 仅用于非 wav 音频，缺失时明确报错。

#### 3.4.2 pip 依赖与卸载清洁

- **安装**：postinst 系统调用，`PIP_BREAK_SYSTEM_PACKAGES=1` 兼容 Debian 12 的 PEP 668；Ubuntu 22.04 的 pip 22 忽略该变量，两种情况同一条命令。
- **离线**：`python3 -m pip install --no-index --find-links <wheel目录> sherpa-onnx==<version>`。
- **失败处理**：postinst 不吞错，pip 失败即 dpkg 配置失败；`apt --fix-broken install` 可重试。
- **卸载清洁**：`postrm` 在 `remove|purge` 分支执行 `python3 -m pip uninstall -y sherpa-onnx <传递依赖>`，清掉 `/usr/local/lib/python3.x/dist-packages` 的残留与空目录；`upgrade` 分支不卸载。目标系统为专用清洁安装，不存在误删他人 pip 包的风险，无需安装前快照。

#### 3.4.3 构建流程（不废弃现有打包工具）

**事实**：`make_deb.py` 有两条路径——`--packer ar` 为纯 Python 自写 ar+tar（Windows 可跑），`--packer dpkg` 调 `dpkg-deb`；CI 用的是 `--packer ar`，`verify_deb.py` 亦为纯 Python。打包与编译解耦，交叉编译只增加「准备 `.so`」一步。

- [ ] **新增 `工具/编译工具链/build_imgenc.sh`**：检测 `aarch64-linux-gnu-g++`，用 3rdparty 静态库编译 `libimgenc.so`，输出到 `工具/prebuilt/`（gitignore）。
- [ ] **`make_deb.py` 前置检查**：`libimgenc.so` 缺失时报错并提示先跑构建脚本，而不是打出缺文件的 deb。
- [ ] **`verify_deb.py` 增项**：校验 `/usr/lib/rkllm-runtime/libimgenc.so` 存在且 `ldd` 无 `not found`。
- [ ] **`.so` 供给方式（建议）**：本地开发在 WSL 跑 `build_imgenc.sh`；CI 在 release-check job 内编译并作为 artifact；两者产物用 SHA256 对账，**二进制不入库**。
- [ ] **CI 增加**：release-check job 安装 `g++-aarch64-linux-gnu`。

### 3.8 风险与未决

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型成对性或格式版本不匹配 | 加载即失败 | A1 前置拦截：`.rkllm` 与 `.rknn` 必须同平台同批次 |
| 内存逼近上限（6.3 GB + 系统） | 8G 板 OOM | 压缩 context；`memory_check` 按 LLM + 视觉编码器之和判定；A1 实测 |
| 视觉 embedding 超 8 MiB 帧上限 | 多图请求失败 | 临时文件传路径 |
| 交叉编译引入构建依赖 | CI 打不出 deb | CI 装 `g++-aarch64-linux-gnu`；`verify_deb` 查 `ldd` |
| 静态链接 OpenCV 使 `.so` 膨胀 | deb 体积增加 | 只链 core / imgproc / imgcodecs 三个模块 |
| pip 安装需联网 | 离线环境装不上 | `--no-index --find-links` |
| PEP 668 限制 | Debian 12 直接 pip 失败 | `PIP_BREAK_SYSTEM_PACKAGES=1` |
| postinst 内 pip 失败 | deb 配置中断 | 不吞错，`apt --fix-broken install` 重试 |
| ASR 与 LLM 争 CPU / 内存 | 首 token 变慢 | ASR 独立进程走 CPU；限制 `asr.num_threads` 并实测 |
| 上游两处缺陷 | 越界读 / 内存泄漏 | A4 补丁并注明来源版本 |
| sherpa-onnx 版本漂移 | 行为变化 | 固定版本号 |

**未决**

- [ ] 一期是否需要多图输入（多图使 embedding 体积成倍增长）。
- [ ] `response_format` 一期范围（json/text 或含 srt/vtt）。

### 3.9 未采用的方案与理由

| 方案 | 不采用的理由 |
|---|---|
| **改用 Firefly LlamaPi 替代本项目** | 闭源 deb，出问题无法自行定位；无 MCP、无 Prometheus 指标、无鉴权、无 supervisor/看门狗自愈；`/health` 只返回 `ok`，缺少 `perf/limits` 快照，连接器自适应会失去数据源；PCIe 多卡级联的卖点在单 RK3588 8G 上不存在 |
| **Gemma-4 端到端音频** | `audio_utils.cc` 的 mel 参数全部硬编码为 `GEMMA4_*`，注释写明 mirroring HuggingFace `Gemma4AudioFeatureExtractor`，只适配单一模型族；换任何其他音频模型都要重写 DSP，属于重复造轮子 |
| **视觉用 Python 重写（cv2 + ctypes 直绑 rknn）** | 与「内置官方已有实现」冲突；`rknn_tensor_attr`（16 字段，含 `char name[256]`、`uint32_t dims[16]`）布局错一字节即段错误；预处理仍需逐位对齐验证。**回退条件**：若交叉编译无法稳定产出 `libimgenc.so`，回退此方案，按三条边界执行——预处理只调 `cv2`、绑定带 `struct_sizes()` 指纹、上线前 `np.allclose(atol=1e-6)` |
| **自建 APT 源打包 sherpa-onnx** | 需维护签名源与托管，成本高于收益；已否决，改走 pip |
| **OpenCV 走 apt 动态链接** | 3rdparty 是 3.4.5（仅静态库），系统 apt 是 4.5.4；soname 与 C++ 符号均不兼容，无法「用 3rdparty 头编译、运行时链系统库」。若改用系统 4.5.4，还需 aarch64 dev 包（multiarch / Docker+QEMU / 手工解包）、跨发行版包名差异（Ubuntu `4.5d` vs Debian `4.5`）、编解码 1 LSB 漂移风险 |
| **`rknn-toolkit-lite2` 走 pip** | wheel 版本必须与随包 `librknnrt.so` 严格一致，错配表现为静默输出错误结果而非报错；且 wheel 与系统 Python ABI 耦合 |
