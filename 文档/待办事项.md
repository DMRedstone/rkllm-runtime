## 五、架构评审待决策（依赖替换 / 结构改造，均未动手）

> 结论：架构总体合理（分层清晰、单配置表、caps 单一事实源、可复现打包）。以下为"是否用成熟外部依赖替代自写"的取舍点，**待决策**。

- [待决策] **MCP 连接器是否改用官方 `mcp` Python SDK**：现为自写协议栈 ~2,226 行（stdio 711 / tools 628 / backend 329 / __main__ 222 / protocol 180 / jobs 156，含 4 版协议）。换 SDK 可删 ~80% 协议/版本维护代码；代价：客户端引入 `mcp/anyio/httpx/pydantic`，**破坏「零依赖源码安装」**（需 vendoring 或允许 pip）。
- [待决策] **deb 构建是否改用 `nfpm`（跨平台单二进制）或 `dpkg-deb`**：现为自写 `ar`+`tar.xz`（make_deb 736 + verify_deb 847 行）。`nfpm` 跨平台且可复现，贴近现状；`dpkg-deb` 最权威但需 Debian+root。自写校验中「conffile↔config.py 逐键交叉核对」是独有价值，`lintian` 难等价。
- [待决策] **`root_alias` 是否重构为 `APIRouter` 双前缀挂载**：零新依赖（FastAPI 原生），可根治 C-H1/M-9 这类「手工别名漏加」缺陷；代价：改各 router 前缀/路径 + 补双前缀回归，属结构性改动。折中：保留中间件但由 `app.routes` 自动派生别名集合（零依赖、改动小）。
- [待决策] **报告是否引入 Jinja2、测试工具是否改用 httpx/httpx-sse**：均跑在开发机，无板端负担；HTML 可读性与流式处理更好。
- [待决策] **配置是否引入 `pydantic-settings`**：仅部分契合（与 caps 三档 / implemented-unwired / conffile 迁移耦合），建议保留自写，评估后再定。
- 不建议替换（DIY 合理）：`ctypes` 绑 rkllm、UDS 长度前缀帧、supervisor 心跳自愈、测试工具 stdlib HTTP（受板端 / PEP668 / 离线 / 零依赖约束）。

## 十一、缺口与不足全集（对比官方 demo + 功能/工程欠账，2026-11-17）

> 对比对象：deb 自带的 `examples/rkllm_server_demo`（`flask_server.py` 767 行、`gradio_server.py`、`chat_api_flask.py`）、`rkllm_api_demo`、`multimodal_model_demo`（ViT + audio tower 各导一个 RKNN，LLM 导 RKLLM）。
> 本节只做登记，**均未动手**；优先级见各条末尾标注。

### 11.1 官方 demo 有、本项目没有

- [ ] **LoRA 适配器（优先级高）**：官方 `build_rkllm_server_flask.sh --lora_model_path` → `rkllm_load_lora`，可热挂领域适配而不换主模型；8G 板上比换整模型省内存。本项目 `abi.py` 只定义了 `_LoraParam` / `infer_param.lora_params` 结构，**从未绑定 `rkllm_load_lora`**，等于完全不支持。改动面：abi 加函数绑定 → `config.py` 加 `model.lora_paths` → 请求侧按 `model` 名或自定义头选 adapter（handle 级加载，需与单槽串行的换 adapter 时机配合）。
- [ ] **Web 对话页（优先级中）**：官方 `gradio_server.py` 提供浏览器 UI（Chatbot + 输入框 + Clear）。**不建议引入 gradio 本体**（板端 Python 3.13、依赖重、与"零依赖源码交付"冲突），可写零依赖单文件 HTML（`fetch` + SSE 直读 `/v1/chat/completions`），以 `--webui` 开关或 `rkllm-runtime-webui` 单独小包提供。
- [ ] **HTTP 客户端封装 / 示例（优先级中）**：官方 `chat_api_flask.py` 给了 `RKLLMClient`（chat/chat_simple、流式迭代）、`TOOLS` 定义、`parse_tool_calls`、`execute_tool_calls` 完整参考实现。本项目只有 MCP 连接器（面向 Agent 宿主），**没有面向普通调用方的 Python 客户端与工具调用范例**；`rkllm chat` 是直连模型、不经 HTTP。可加 `rkllm-client` 小模块或 `examples/http_client.py`。
- [待决策] **多模态（image + audio，优先级低/成本高）**：官方 `multimodal_model_demo` 走 "RKNN ViT/audio tower + RKLLM"，Qwen2-VL / Qwen2.5-VL / Qwen3-VL / Gemma-4-E2B / DeepSeek-OCR 均有导出脚本，含 `image_enc`/`audio_enc`/`miniaudio` 全套。代价：模型体积与内存（8G 板 ViT+LLM 同时驻留余量紧张）、pipeline 需加 image token 预算与 `image_url`/base64 解析、流式与取消语义重做。
  - 注：官方 **flask server 也只定义了 `RKLLMImageInput`/`RKLLMAudioInput` 结构，未接 HTTP 路由**（只实现 `/v1/models`、`/v1/chat/completions`），所以「HTTP 面不支持图片」不是本项目独有落后。

### 11.2 官方也没有、但生产常用（本项目工程面欠账）

- [ ] **无 CI / 自动化门禁（优先级高）**：全部检查靠本地手跑（pytest 378、`verify_deb` 88 项、`magic_numbers`、`crosscheck`）。仓库无 GitHub Actions，无「提 PR 必跑」的回归门禁；`coverage` 只加了配置、未设阈值。
- [ ] **无 apt 仓库与 deb 签名（优先级中）**：只有 `git tag` 的 SSH 签名，`.deb` 本身未签名、无 `reprepro`/`aptly` 仓库，板端只能 `dpkg -i` 手工装，无法 `apt upgrade` 收版本。
- [ ] **无容器镜像（优先级低）**：无 OCI 镜像；容器内跑 NPU 需 `--device` 与驱动挂载，非必需。
- [ ] **鉴权只有单 key（优先级中）**：`server.api_key` / `api_key_file` 单一密钥，无多 key、无速率限制、无配额、无按 key 计量（`/metrics` 与 `/health.stats` 均为全局计数）。
- [ ] **指标只有计数器（优先级中）**：`/metrics` 仅有 `rkllm_requests_total` 等 counter（含 worker 重启/心跳超时/缓存命中），**没有直方图与延迟分位**、无 per-endpoint 维度、无队列深度与 NPU/内存占用的时间序列；排障要靠 `/health` 快照 + 日志。
- [ ] **无模型管理面（优先级中）**：无「列本地模型 / 校验 `.rkllm` 完整性 / 删除 / 上传」接口；`/v1/models` 只回显当前加载的那一个。
- [ ] **无多模型与热切换（优先级中）**：单模型单进程，`model` 字段只回显不路由；缺 `POST /admin/model`（停 worker → 换 `model.path` → 起 worker，切换期 503 + `Retry-After`，队列内请求显性失败而非超时）。与 §一「模型生命周期/多模型」是同一件事的小步版本。
- [ ] **无服务端会话/历史（优先级低）**：`store` 在 ignored 档、`keep_history` 默认 false，历史完全由客户端回传。
- [ ] **端点缺口（优先级低/受 runtime 限制）**：`/v1/audio/transcriptions`（需外挂 ASR）、`/v1/embeddings`（需真 embedding 模型）、`/v1/moderations`、`messages(anthropic)`、FIM/prefix completion——均在 `caps.py` 显性 unsupported，不假装支持。
- [ ] **无受约束解码（优先级低）**：工具调用与 JSON 走「提示 + 校验 + 重试」，无 GBNF/文法约束解码，理论上有失败率（见 §一）。
- [ ] **流式不支持 `response_format.json_schema`（已声明）**：流式返回 400（无法追回已发出的帧），非流式才做校验+重试。
- [ ] **采样可复现性缺口（受 runtime 限制）**：`seed`、`logprobs`、`top_logprobs`、`n>1` 均 unsupported → 无法复现同一次生成、无法拿 token 置信度、无法一次出多候选。
- [ ] **无批处理（受硬件限制）**：`n_batch=1`、单槽串行，多客户端只能排队；无连续批/in-flight batching。
- [ ] **服务以 root 运行（受 NPU/锁频限制）**：只能靠 unit 加固（`NoNewPrivileges`、`ProtectSystem=full`、`RestrictSUIDSGID`、`RestrictAddressFamilies`），无法降权到普通用户。
- [ ] **Responses 是翻译层（emulated）**：非原生实现，语义边界见 `caps.py`。

### 11.3 已有但受限/待改（沿用既有结论，此处只登记不重复）

- `tools` 走提示词注入而非 `rkllm_set_function_tools`（ADR-06：handle 级污染），精度依赖模型输出格式；官方 demo 用原生 API。
- prompt cache 受上游"加载返回 -1（内部码 10000）"限制，SCHEMA 默认关闭（板端按配置开启），冷启动首 token 仍偏慢。
- `P-推理线程常驻`、`P-minor-json`、`P-minor-缓存 I/O`、Responses 大流量截断、真实 NPU 死锁注入、7B/长稳/并发压测（§一）。
- 档位：`7b` 的 `384/1536/1024` 为保守估计待实测校准；`14b`/`27b` 无内置值（§十）。
- `changelog.Debian.in` 顶部条目仍是 47 键口径，推进版本号时需新增一条（§十）。
- 五项外部依赖/结构改造待决策：MCP 官方 SDK、`nfpm`/`dpkg-deb`、`root_alias` → `APIRouter` 双前缀、Jinja2/httpx、`pydantic-settings`（§五）。

### 11.4 明确不补（避免反复讨论）

- 官方 build 脚本的 `--adb_device` 一键推送：`dpkg` + systemd 已覆盖，且更适合量产。
- gradio 本体：用 11.1 的零依赖单页替代。
- `mirostat`/`mirostat_tau`/`mirostat_eta`：官方 HTTP 面同样不接受这三个参数、内部也固定 `mirostat=0`（`flask_server.py:281-283`、`646-648`），**不构成差距**。
- `embeddings` 假实现：没有真 embedding 模型，宁可 unsupported。
- `n_batch>1`：单槽串行下无收益。
- `messages(anthropic)`、`moderations`、`n>1`、`logprobs`、`seed`：超出「对标 DeepSeek 文本 API」的目标或受 runtime 限制。
