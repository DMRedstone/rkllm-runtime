## 〇、总体思路、功能范围与进度（2026-10-22 更新）

**版本：1.3.1-16**（本批改动不递增版本号；1.3.1-16 是本次改造的交付版本）

### 0.1 总体思路

把 OrangePi 5 Plus（RK3588 / 8 GB）上的 4B/7B 模型，做成 **WorkBuddy 可调用的
辅助推理后端**：WorkBuddy 用主模型规划，板端模型承担摘要、改写、抽取、分类、
翻译、短问答与分段批处理——**只做"可判定的短任务"，不做长文创作与多步推理**。

三层结构，边界清晰：

```
WorkBuddy（MCP stdio 客户端）
   │  local_llm_ask/chat/extract/batch/status/job 六个工具
   ▼
客户端连接器（纯 stdlib .py，本机运行）
   │  HTTP：/v1/chat/completions（+ /v1/responses 翻译层）
   ▼
板端服务：FastAPI（鉴权/队列/SSE/能力表）+ 推理子进程（ctypes → librkllmrt.so）
```

六条关键取舍（ADR，详见总体设计 §5）：

| # | 取舍 | 理由 |
|---|---|---|
| 1 | 入口只有一条：`/usr/bin/rkllm` + `rkllm-server.service` + `/etc/default/rkllm-server`（都沿用旧名） | 运维脚本、unit、conffile 零改动 |
| 2 | 推理放子进程，HTTP 崩溃隔离；崩溃自愈（周期探测 + 请求路径重试） | 单 NPU 场景下稳定性优先 |
| 3 | 工具调用用"提示词注入 + 解析"，不碰 handle 级的 `rkllm_set_function_tools` | 后者永久生效会污染后续请求 |
| 4 | 能力三档（native/emulated/unsupported）由 `caps.py` 单一事实源渲染 | 杜绝"看起来支持其实不支持" |
| 5 | 单槽 prompt 前缀缓存 + 内存预算（不足先降 context 再拒绝） | 8 GB 板上 4B/7B 可跑、27B 明确拒绝 |
| 6 | 客户端只走**源码安装**（不打包 wheel、不建 venv） | 纯 stdlib，多一层打包只增负担 |

## 二、改造目标（合并三份文档的结论）

把板上 4B/7B 模型做成 WorkBuddy 可通过 MCP 调用的辅助工具：

1. **板端**：`rkllm serve` 从 3 122 行单文件重构为模块树（FastAPI + 推理子进程 + UDS 帧协议），修复审核报告 D1–D15；
2. **客户端**：自写纯 stdlib MCP 连接器 `rkllm-mcp`（stdio、6 工具、job 轮询、取消传导），以**源码目录**交付（当晚改定：不走 wheel）；
3. **配置**：80 键 TOML 单一配置表，全部有默认值、启动校验、来源可查；
4. **诚实兼容**：能力三档（native/emulated/unsupported）单一事实源 `caps.py`，杜绝静默忽略。

三个硬约束：客户端 60 s 工具超时（>45 s 一律 job 化）；单 NPU 串行（有界队列+背压+取消）；8 GB 内存（4B/4096、7B/2048、27B 拒绝启动）。
