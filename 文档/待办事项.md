## 五、架构评审待决策（依赖替换 / 结构改造，均未动手）

> 结论：架构总体合理（分层清晰、单配置表、caps 单一事实源、可复现打包）。以下为"是否用成熟外部依赖替代自写"的取舍点，**待决策**。

- [待决策] **MCP 连接器是否改用官方 `mcp` Python SDK**：现为自写协议栈 ~2,226 行（stdio 711 / tools 628 / backend 329 / __main__ 222 / protocol 180 / jobs 156，含 4 版协议）。换 SDK 可删 ~80% 协议/版本维护代码；代价：客户端引入 `mcp/anyio/httpx/pydantic`，**破坏「零依赖源码安装」**（需 vendoring 或允许 pip）。
- [待决策] **deb 构建是否改用 `nfpm`（跨平台单二进制）或 `dpkg-deb`**：现为自写 `ar`+`tar.xz`（make_deb 736 + verify_deb 847 行）。`nfpm` 跨平台且可复现，贴近现状；`dpkg-deb` 最权威但需 Debian+root。自写校验中「conffile↔config.py 逐键交叉核对」是独有价值，`lintian` 难等价。
- [待决策] **`root_alias` 是否重构为 `APIRouter` 双前缀挂载**：零新依赖（FastAPI 原生），可根治 C-H1/M-9 这类「手工别名漏加」缺陷；代价：改各 router 前缀/路径 + 补双前缀回归，属结构性改动。折中：保留中间件但由 `app.routes` 自动派生别名集合（零依赖、改动小）。
- [待决策] **报告是否引入 Jinja2、测试工具是否改用 httpx/httpx-sse**：均跑在开发机，无板端负担；HTML 可读性与流式处理更好。
- [待决策] **配置是否引入 `pydantic-settings`**：仅部分契合（与 caps 三档 / implemented-unwired / conffile 迁移耦合），建议保留自写，评估后再定。
- 不建议替换（DIY 合理）：`ctypes` 绑 rkllm、UDS 长度前缀帧、supervisor 心跳自愈、测试工具 stdlib HTTP（受板端 / PEP668 / 离线 / 零依赖约束）。

## 七、配置自动参数实测与调参建议（2026-11-16，板端 MiniCPM3-4B / small / ctx4096）

实测（HTTP 直连板端 1.3.1-19）：
- **解码**：稳态 **4.69–4.81 tok/s**（3 次；首请求 2.19 tok/s 属冷启动）。
- **预填充**：约 **43.8 tok/s**（prompt_tokens=1611，耗时 36.79s）。
- **自动识别**：`model_class=small`、`context_len=4096`（来自 `/health`，正确）。

结论与建议：
- [ ] `PREFILL_TOK_S=50` 略乐观（实测 ~44）：建议下调至 **~44（或 40）**，使 job 估算更保守、更早转 job，避免客户端 60s 硬超时（`本地模型连接器/rkllm/mcp/jobs.py`）。
- `DECODE_TOK_S["small"]=4.5` 与实测吻合（略保守），**无需调整**。
- 冷启动首请求约 12s（2.19 tok/s）：建议连接器/网关对新会话首请求适度放宽超时或预热；`estimate_tokens_cap=128`、`task_threshold_s=45` 可维持。
- 仍需在"目标板 + 目标模型 + 目标档位"上各跑一次实测的自动项（当前环境无法覆盖）：
  - `model.platform`（SoC 探测）、`model.class`（auto 推导）、`model.freq_helper`；
  - `openai.tool_parser`（需支持工具调用的模型验证 auto 解析模板）；
  - `platform/memory.py` 内存预算（需 7B/27B 真实模型验证档位与拒绝路径）。
  - 方法：`/health` 读 model_class/context_len/npu；短 prompt（max_tokens=128）测 decode、长 prompt（max_tokens≈8）测 prefill；工具调用用例验证 tool_parser；`/v1/capabilities` 核对三档。
