# 本地模型连接器 · 开发记录

## 2026-10-16：HTTPS 目标不可达缺陷修复 + 示例配置重写

涉及文件：`rkllm_client.py`（缺陷修复）、`targets.example.conf`（重写）、`targets.conf`（本机配置修正）、连接器说明文档（同步修订）。

### 一、缺陷现象

- 目标地址为内网穿透域名（花生壳），该链路仅 HTTPS 可达，明文 HTTP 直接连不上。

- `targets.conf` 里已写 `https://` 前缀，但 `local_llm_targets` 仍显示目标 `unreachable`，详情为 `RemoteDisconnected('Remote end closed connection without response')`。

- 附带问题：`default =` 行写的目标名与目标行名字不一致（多了个字符），所有不带 `target` 参数的调用报「未知目标」。

### 二、定位过程

  - `https://<域名>/health` 无令牌 → HTTP 401，说明 DNS、TCP、TLS、服务进程全部正常，401 只是缺令牌；

  - `http://<域名>/health` → `Empty reply from server`（curl 52），远端直接断连。

1. 网络层验证（curl）：

1. 带令牌复测：用 Python urllib 按客户端同款方式请求，`https` + `Bearer <token>` 的 `/health` 返回 HTTP 200（模型在线、空闲、队列 0）——服务端完全正常，问题锁定在客户端。

  - `_normalize_host()` 解析地址时把 `http://` / `https://` 前缀剥掉丢弃，只保留 `host:port`；

  - `_SimpleBoard.__init__()` 重建 URL 时写死 `self.base = "http://" + host`；

  - `_probe_path()` 同样写死 `"http://" + host`。

  - 结果：无论配置里写什么协议，实际请求一律走明文 http → 对仅 HTTPS 的地址必然 `RemoteDisconnected`。

1. 代码走查，发现根因由三处叠加：

1. 文档与实现不符：模块 docstring 与示例第 ⑧ 条声称「地址可带协议前缀，http:// 或 https:// 都认」，该版本实现实际不支持。

### 三、修复内容（rkllm_client.py，6 处）

1. 新增 `_split_base(raw)`：从地址拆出 `(scheme, host)`，无前缀按 http；协议显式保留并附注释说明原因。

1. `_entry()`（.conf 解析）：`host = _normalize_host(...)` 改为 `scheme, host = _split_base(...)`，并把 `scheme` 写入目标条目。

1. `_parse_json()`（旧 .json 格式）与环境变量单目标两处：同上，解析时存储 `scheme`。

1. `_SimpleBoard.__init__()`：新增 `scheme="http"` 参数，`self.base = scheme + "://" + host`。

1. `_board_for()`：客户端实例缓存签名加入 `scheme`（改协议可自动重建）；仅内置客户端接收 `scheme` 参数，主项目工具链 `Board` 的调用接口不受影响；启动日志改为输出真实协议（`https://...` 而非固定 `http://...`）。

1. `_probe_path()`：签名增加 `scheme="http"`，`_probe()` 调用点传入。

兼容性：不写协议前缀的地址行为不变（按 http）；工具链 `Board` 复用路径不变。

### 四、本机配置修正（targets.conf）

- `default = qwen3-4b` → `default = qwen-4b`，与目标行名字对齐。

### 六、示例配置重写（targets.example.conf）

- `default =` 行说明与目标名必须完全一致的警告（对应本次附带的「未知目标」问题）；

- 档位别名表（rk3588/板端/默认、1.5b/2b、generic/通用、27b/30b 等）；

- 七个档位的生效值对照表（输入/输出/上下文/吞吐/超时/重试/截断余量/退化自检）；

- 全部可配置键说明（含中文别名、取值类型与校验规则）：`model` / `preset` / `key` / `max_in` / `max_out` / `context` / `tok_per_sec` / `timeout_floor` / `retries` / `retry_wait` / `chars_per_token` / `overrun` / `degen_check` / `health` / `ability`；

## 2026-10-17：换机安装暴露 MCP 服务层缺失，并重建 server.py

起因：换到新机器后按《冷启动说明》3.2 从资料库取回连接器，落盘后 local_llm_* 四个工具全部拉不起来。

### 一、现象

- 取回的文件里没有 MCP 服务层：名为 server 的节点存的其实是 rkllm_client.py（891 行，sha256 166fe8cd…）。

- 两个 .py 节点是同一文件的两个版本，都检索不到 stdio / jsonrpc / local_llm_* 等 MCP 服务层特征（命中均为 0）。

### 二、定位

- server 节点那份较新，已含 2026-10-16 的 _split_base / scheme 六处 https 修复；rkllm_client 节点那份是修复前旧版（867 行，sha256 6a858d9e…）。

- 结论：2026-10-16 那次同步把修复后的 rkllm_client.py 传到了 server 节点，覆盖了真正的 MCP 服务层；旧版客户端留在 rkllm_client 节点未被更新。

- 附带影响：按名取文件会同时丢掉两样东西——MCP 服务层本身，以及修复后的客户端（云端那份是旧的）。

### 三、处理

- 运行位置以较新那份为准落为 rkllm_client.py（含 https 修复），保证 CLI 的 targets / health / ask / calibrate 对仅 HTTPS 的目标可用。

- 重写 server.py（260 行）：stdio 上按行分隔的 JSON-RPC 2.0，处理 initialize / tools/list / tools/call / ping；通知不响应，未知方法回 -32601。

- 服务层自身不含任何地址、令牌与阈值，四个工具全部委托 rkllm_client，阈值仍由 targets.conf 与各目标档位决定。

- 协议卫生：stdout 只出协议报文，启动日志与告警一律走 stderr，避免污染 MCP 帧。

- 两份文件已同步回资料库：server 与 rkllm_client 两个节点内容替换，节点 ID 不变、版本递增，回读 sha256 与本机一致。

### 四、验证（新机实机，目标为板端 Qwen3.5-4B）

- local_llm_targets：正确列出目标、档位与能力边界，默认目标命中。

- local_llm_health：status ok、busy false、队列 0、累计请求 39 / 错误 0。

- local_llm_ask：端到端 2.83 s 返回正常文本。

- local_llm_batch：单段 2.27 s 返回，JSON 结果结构正确。

- 协议层：initialize 握手正常，tools/list 返回 4 个工具，未知方法正确回 -32601。

### 五、遗留事项

- 新机需重启客户端并在连接器管理页信任 local-rkllm（mcp.json 在客户端启动时读取，写入晚于启动则本次不加载）。

- 尚未做实机校准：建议跑 python rkllm_client.py calibrate，把建议的 tok_per_sec / timeout_floor 回写 targets.conf。
