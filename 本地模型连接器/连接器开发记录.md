### 二、部署机工作空间：安装落地与协议缺陷修复（10-16 晨）

- 安装链路：取源文件 → 装入运行目录 → 建注册配置 → 留归档副本；真实地址与令牌留空由用户自持（硬边界：令牌不落库）。

- 缺陷：远端连接被直接断开。定位沿「地址归一化 → 协议拼接 → 探测路径」逐段核对，根因是地址前缀剥离后协议被写死为明文 HTTP，仅支持加密访问（HTTPS）的目标被静默降级——静默降级把「配置写错」伪装成「网络不通」，让排查方向从一开始就偏了。

- 修法：把协议解析抽出为独立环节，协议成为一等信息，各调用点按各自协议拼接地址。明确否决三种变通：归一化处补回协议（只覆盖一条路径）、探测处写死加密（牺牲明文目标）、仅改文档提示（把缺陷转嫁给使用者）。

- 修复后需重启服务再复验整条链路——「代码改完」不等于「问题解决」，验证终点是外部可观测行为。

- 顺带纠正默认目标名两处拼写不一致（旁支问题当场修，不留「以后再说」）。

- 同期对「连接器说明」等资料库文档做同步改写（表格受平台约束需整表替换，详见部署机《智能体操作思路、态度与反应记录》）。

## 2026-10-16：HTTPS 目标不可达缺陷修复 + 示例配置重写

涉及文件：`rkllm_client.py`（缺陷修复）、`targets.example.conf`（重写）、`targets.conf`（本机配置修正）、连接器说明文档（同步修订）。

### 一、缺陷现象

- 目标地址为内网穿透域名（花生壳），该链路仅 HTTPS 可达，明文 HTTP 直接连不上。

- `targets.conf` 里已写 `https://` 前缀，但 `local_llm_targets` 仍显示目标 `unreachable`，详情为 `RemoteDisconnected('Remote end closed connection without response')`。

- 附带问题：`default =` 行写的目标名与目标行名字不一致（多了个字符），所有不带 `target` 参数的调用报「未知目标」。

### 二、定位过程

  - `https://<域名>/health` 无令牌 → HTTP 401，说明 DNS、TCP、TLS、服务进程全部正常，401 只是缺令牌；

  - `http://<域名>/health` → `Empty reply from server`（curl 52），远端直接断连。

1. 网络层验证（curl）：

1. 带令牌复测：用 Python urllib 按客户端同款方式请求，`https` + `Bearer <token>` 的 `/health` 返回 HTTP 200（模型在线、空闲、队列 0）——服务端完全正常，问题锁定在客户端。

  - `_normalize_host()` 解析地址时把 `http://` / `https://` 前缀剥掉丢弃，只保留 `host:port`；

  - `_SimpleBoard.__init__()` 重建 URL 时写死 `self.base = "http://" + host`；

  - `_probe_path()` 同样写死 `"http://" + host`。

  - 结果：无论配置里写什么协议，实际请求一律走明文 http → 对仅 HTTPS 的地址必然 `RemoteDisconnected`。

1. 代码走查，发现根因由三处叠加：

1. 文档与实现不符：模块 docstring 与示例第 ⑧ 条声称「地址可带协议前缀，http:// 或 https:// 都认」，该版本实现实际不支持。

### 三、修复内容（rkllm_client.py，6 处）

1. 新增 `_split_base(raw)`：从地址拆出 `(scheme, host)`，无前缀按 http；协议显式保留并附注释说明原因。

1. `_entry()`（.conf 解析）：`host = _normalize_host(...)` 改为 `scheme, host = _split_base(...)`，并把 `scheme` 写入目标条目。

1. `_parse_json()`（旧 .json 格式）与环境变量单目标两处：同上，解析时存储 `scheme`。

1. `_SimpleBoard.__init__()`：新增 `scheme="http"` 参数，`self.base = scheme + "://" + host`。

1. `_board_for()`：客户端实例缓存签名加入 `scheme`（改协议可自动重建）；仅内置客户端接收 `scheme` 参数，主项目工具链 `Board` 的调用接口不受影响；启动日志改为输出真实协议（`https://...` 而非固定 `http://...`）。

1. `_probe_path()`：签名增加 `scheme="http"`，`_probe()` 调用点传入。

兼容性：不写协议前缀的地址行为不变（按 http）；工具链 `Board` 复用路径不变。

## 2026-10-19：HTTP 层统一、脚本去序号与连接器通用性修复

涉及文件：`rkllm_client.py`、`server.py`、新增 `board_api.py`、`targets.example.conf`、`连接器说明.md`；同批还改了工具链 10 个脚本的文件名与 `工具/大模型测试工具链/board_api.py`。对应提交 `353a7ab`（HTTP 层与缺陷修复）、`d2713b7`（链路档位、上下文协商、吞吐自适应）。

### 一、起因

三份审查报告指向同一处：

1. 《20261019 rkllm-runtime 代码审查报告》：P0-1 锁创建竞态、P1-1 每次调用重读配置、P1-3 重试不分状态码。

### 五、部署形态：两种链路并存

实际部署是**同一台板端服务被两条链路访问**：

| 形态 | 承载能力 | 说明 |
| --- | --- | --- |
| 内网主机直连 | 不受限 | 另一台主机与板子同处内网，带宽与并发充足 |
| 本机经内网穿透 | 受限 | 隧道带宽与并发连接数有限，连接不复用、RTT 高 |

两条由此确定的原则：

1. **不能把「穿透受限」当全局前提**。用 `link=direct|tunnel` 按目标标（默认 `direct`）：直连是常态，把受限假设设为默认会让所有场景无谓变慢；穿透目标显式声明即可，忘写的最坏后果是「慢」而非「错」。
2. **不靠减少测试项目来迁就慢链路**。`list_targets` 仍然探测**全部**目标——探不全就不知道哪台还能用。链路差异只体现在并发方式与并发上限上。

### 六、链路档位 `link=`

| 行为 | `link=direct`（默认） | `link=tunnel` |
| --- | --- | --- |
| `list_targets` 探测 | 线程池 4 路并发，墙钟 ≈ 单次超时 | 串行，逐条打印进度 |
| 请求并发 | 仅受同目标 `_lock_for` 约束 | 全链路信号量 2 槽（`LINK_TUNNEL_SLOTS`） |
| 适用 | 内网直连、localhost | 内网穿透、反代、跨公网 |

链路闸门 `_link_guard` 按 **link 分组**而不是按目标：多个穿透目标走的是同一条隧道，按目标限流对隧道无效。取值校验在 `_coerce_opt` 里，非法值回落 `direct` 并告警；中文别名「链路」。

`list_targets` 的 `count` 恒等于配置里的目标数、输出顺序不变，每个目标多一个 `link` 字段——慢只影响耗时，不影响覆盖。

### 七、上下文协商（G5-a）

首次调用某目标时读一次 `/health`，若返回 `context_len`（兼容 `n_ctx`）且小于配置的 `context`，则按下调，并把 `max_in` 收紧到 `context - 64 - max_out`（不足 256 时只告警不动手）。**只下调不上调**：上调会让既有的 `max_in` / `max_out` 假设失效。

- 每个目标只探一次（`_context_probed`），失败静默——协商是增强，不能因此让调用失败。
- 配置 mtime 变化时清空 `_context_probed` 与 `_tps_samples`，重新协商。
- 协商后 `max_in` 会再校验一次输入预算，超过就拒绝（否则 context 缩小后输入仍按旧的宽预算放行）。

服务端字段由 `输入/` 侧的 `cli/rkllm.py` 提供（2026-10-19 的 11.1 修复里给 `/health` 加了 `context_len`）。

### 八、吞吐自适应（G3）

每次成功调用记录 `completion_tokens / elapsed`，保留最近 5 次；输出 <40 token 的样本丢弃（首 token 开销占比过高）。取**中位数**（抗单次抖动），样本满 3 个且中位数 **低于配置值的一半**时，写入 `cfg["_measured_tps"]`，`_timeout_for` 改按它推算并 `_warn` 一次。

**只下调不上调**：实测更快时不动配置——超时变小会误杀长尾请求，宁可等久一点。

不采用的写法：每次调用前跑一次校准（弱板子上校准本身几十秒，且会占 NPU 队列）。

### 九、其他修正

- **G8-1 探测策略**：按 link 分两组，`direct` 走 `ThreadPoolExecutor(4)`，`tunnel` 串行并在 stderr 逐条打印「探测 X（穿透链路，串行）…」。**目标数与探测项一个不少**。
- **G8-4 `default` 三态**：`default = X` 改为事后判定——X 是已定义目标名 → 默认声明；X 像地址（含 `.` 或 `:`）→ 这是「目标名就叫 `default`」的配置行；其它 → 告警「默认目标不存在」并忽略。旧实现在解析到该行时立刻 `continue`，`default = 127.0.0.1:8080` 会让该目标消失且默认名变成地址字符串；而文档承诺的 `default board` 空格写法从未生效过，本次一并修好。
- **G8-5**：删除 `_entry` 的 `key = "" if key_inline is not None else ""` 死分支。
- **G8-6**：`连接器说明.md` 与 `targets.example.conf` 补 `no_proxy` 排错（`urllib` 默认读代理，穿透域名会被全局代理拦走，表现为"目标不可达"但浏览器能打开）。
- **文档同步**：`连接器说明.md` 档位表的吞吐一列原为 60/40/30/20/10/5，代码早改成 8/5/4/3/2/1——照旧文档配的人会得到"永远超时"，已同步；`default` 不再被描述为保留字；新增链路与上下文协商两节。

## 2026-10-20：会话记忆（session）与服务端 reset

背景：服务端审查发现多轮对话错配（服务端只读最后一条消息、靠内部 KV 记历史），
并给出两路线——A 服务端改 stateless、B 连接器侧维护会话。两条同时实施。

### 一、新增能力

| 能力 | 说明 |
| --- | --- |
| `history_turns`（配置项，默认 0） | 连接器侧会话记忆轮数上限。0 = 关闭（默认），保持"每次调用独立"的既有语义 |
| `ask(..., session=...)` | 同一 session 的多轮调用自动带上之前对话；历史**拼进 prompt 文本**而非 messages 数组 |
| `reset_session()` / CLI `reset` | 清连接器侧历史 + 打服务端 `/v1/reset`；返回清理轮数与服务端状态 |
| `list_sessions()` / CLI `sessions` | 查看当前进程内的会话名与轮数（排查用） |
| MCP 工具 `local_llm_reset` | 工具数 4 → 5；`local_llm_ask` 增加可选 `session` 参数 |

### 二、为什么拼进 prompt 而不是 messages 数组

旧服务端（< 1.3.1-14）只读最后一条 user 消息、前几轮直接从 messages 里丢弃，靠服务端内部 KV
续上下文。把历史拼成「此前的对话」文本放进 content，**新旧服务端都能看懂**——这是兼容优先的选择。
服务端升级到 stateless 后，这段拼接依然成立（等价于客户端自己拼历史）。

### 三、两个防坑设计

1. **预算随历史重算**：拼上历史后若超 `max_in`，从最旧的轮次开始丢（`compose()` 循环），
   而不是直接报错——否则开多轮就必然撞预算墙；
2. **与 `RKLLM_NO_HISTORY=0` 互斥**：服务端自己记历史时若连接器再拼一遍，每轮都会重复。
   文档与示例都注明这条，服务端侧也用 `include_history=False` 做了对称处理。

### 四、验证

| 验证 | 结果 |
| --- | --- |
| 专项（FakeEngine 假服务端 + 临时配置） | **12/12 PASS**：`history_turns=0` 不记历史、`=2` 自动带历史、会话隔离（s1/s2 不串）、环形上限封顶 2 轮、reset 清空且打通 `/v1/reset`、清空后不带旧历史、超预算丢历史不报错 |
| 真实板端回归（改造时服务端仍为 1.3.1-13） | 配置解析正常（两目标 `history_turns=0`）、`ask` 1.05s 正常返回、MCP `tools/list` 5 个工具——证明**新连接器兼容旧服务端** |
| **真实板端回归（服务端已升 1.3.1-14，stateless）** | 单轮 `ask` 1.03s 正常；`history_turns=2` + `session=t` 两轮后第二轮答出「7」（usage `prompt_tokens=66` 含历史）；MCP `local_llm_reset` 返回 `cleared_turns: 0`、`server_status: 200` |
| 语法 | `py_compile` 三文件通过 |

### 五、遗留

- **服务端已上生产板**：`1.3.1-14` 已装到 192.0.2.10（服务 active，19 项功能验证全过），
  启动日志 `history=0` 即 stateless——与连接器默认 `history_turns=0` 正好匹配，
  **不会出现"服务端历史 + 连接器历史"双份重复**。若哪天把板端改成 `RKLLM_NO_HISTORY=0`，
  必须同时把连接器的 `history_turns` 保持 0，否则上下文会重复一遍；
- 长驻 MCP 进程需重启客户端才加载新代码（既有遗留）；
- `ask` 的 `session` 只在 `history_turns>0` 时生效，默认关闭——MCP 场景下上游大模型自己维护
  上下文，强行开历史反而会打乱单轮任务的语义；
- 会话历史只在进程内存里，MCP 服务重启即丢（有意为之：不做持久化，避免旧上下文串进新任务）。
