# 大模型测试工具链 — 板端大模型推理服务测试

面向 RK3588（OrangePi 5 Plus 8G）上 `rkllm serve` 部署的大模型服务，提供压力测试、客户端行为仿真、真实公文场景测试与报告生成的完整闭环。

被测目标示例：`http://192.0.2.10:8080`，模型 `qwen3.5-4b_w8a8_rk3588`。

---

## 一、脚本清单

运行顺序由 `run_all.py` 编排，文件名不带序号——脚本名同时也是合法的模块名，
`import` 与命令行都按常规 Python 习惯使用，顺序只在编排器里表达一次。所有
脚本共享同目录的 `board_api.py`，但仍可 `python llm_stress.py` 单独运行。

- `board_api.py` — 共享 HTTP 客户端：URL 与认证头构造、超时、SSE 解析、
  健康判定（2xx 但空体也算可达，vLLM 就这么回）、百分位算法。工具链内唯一
  副本；旧 `本地模型连接器/` 已裁撤，不再做双份比对。

- `quality.py` — 内容**形态**分析（不是质量评分）：截断与 overrun、重复/退化、
  乱码、流式与非流式一致性、并发响应归属。纯函数、无 HTTP 依赖，压测采集与
  报告渲染共用同一套口径。语义好坏（改写是否保留术语）它不判，只能人读输出。

### 源码级回归（不需要模型 / NPU / 板子）

1.3.1-16 起旧单文件 `cli/rkllm.py` 已删除，原先直接 import 它的
`verify_server.py` 一并退役；对应回归全部迁到新栈 pytest：

```bash
cd 输入/rkllm-runtime-1.3.1
PYTHONPATH=src python3 -m pytest tests -q      # 373 项
```

覆盖 FakeEngine、worker 帧、配置键生效性/魔法数、MCP 协议与 job、抽取 fixture、
`/v1/responses` 事件序列等；改完服务端源码**先跑 pytest 再上板**，秒级完成。

### 入口与预检

- `run_all.py` — 一键编排入口（推荐从这里开始）
依次执行：预检 → 压测 → 仿真 → 崩溃复现 → 生成报告。
板端 NPU 是独占资源，脚本自动串行化，并在步骤之间轮询 `/health` 等待守护进程把崩溃的服务拉起。

- `health_check.py` — 服务健康 / 连通性检查（由三个同功能脚本合并而成，详见第二节）
默认做基础 3 项（`/health`、`/v1/models`、端到端对话），数秒完成，适合压测前预检；
加 `--full` 追加 7 项深度检测（鉴权拒绝、长 system 应答、system 模板污染、system+多轮、
system-only 探测、流式 `[DONE]` 收尾、超长 prompt 拒绝），适合交付 / 换板后的完整体检。
退出码 0=健康、1=异常，可直接接入 CI。

### 合成负载链（由 `run_all.py` 自动串行编排）

- `llm_stress.py` — 压力与极限测试
  除延迟/吞吐/并发/耐力外，含三段内容形态用例：**A2** 流式与阻塞的内容一致性
  （不只比 TTFT）、**A3** 并发响应归属（每请求埋唯一标记，检测串包）、**A5**
  输出形态（finish_reason 分布、overrun 实测、退化分、乱码）。
`A` 单请求延迟基线 · `A2` 流式 vs 阻塞（首字延迟）· `B` 并发→吞吐曲线（p50/p90/p99）·
`C` 持续耐力（延迟漂移）· `D` 过载 / 背压 · `E` 超长 prompt 守卫 + 畸形 body。
段序「先温和、后敌意」：可能压垮服务的用例放最后，每段后做存活探测以精确定位崩溃点。

- `llm_simulate.py` — 客户端行为仿真
握手 / 多轮对话 / 长文档粘贴 / 中断（流式中断线）/ 会话切换 / 后台标题（与对话并发）/ 多 VU 混合负载。

- `crash_probe.py` — 并发崩溃隔离复现
逐个隔离触发条件并量化复现率（`--repeat N`）。

- `make_report.py` — 合成负载报告生成（读 `results/stress_*.json` + `simulate_*.json`）

- `soak_test.py` — 长时浸泡测试（N3 性能基线：首 token p95、改造前后压测对比）

- `export_csv.py` — 结果导出 CSV（并发曲线 / 压测明细 / 仿真时间线，Excel 友好）

### 真实公文场景链（独立支线：语料 → 测试 → 报告）

- `docx_corpus.py` — 真实 docx → 纯文本语料 + 规模画像（只读源文件，不改动原件；语料清单在文件顶部 `CORPUS` 中配置）

- `llm_realworld.py` — 真实公文场景测试
`A` 串行任务 / `B` 分段处理 / `C` 多轮迭代 / `D` 并发 / `E` 批量；内置崩溃自愈重试。

- `make_rw_report.py` — 真实场景报告生成（自动合并各组最新结果 + 语料画像）

运行期自动产生：`results/`（结构化 JSON、`realworld_samples/` 完整输出）、`corpus/`、`csv/`、`report*.html|md`。

## 四、快速开始

### 0. 连接配置（2026-11-10 起）

工具链各脚本可直接复用 `rkllm-mcp` 连接器安装目录的 `mcp.toml`，**不需要手动传 key**：

```bash
python health_check.py --full          # 无参数即可：自动读连接器配置
```

优先级：`RKLLM_HOST` / `RKLLM_KEY` / `RKLLM_API_KEY` 环境变量 > `mcp.toml` 的
`target_endpoint` / `target_api_key`；配置文件路径可用 `RKLLM_MCP_CONFIG` 覆盖。
实现在共享层 `board_api.py` 的 `default_host()` / `default_key()`；key 只在进程内存中使用，
不打印、不写日志、不入库。`--host` / `--key` 显式传参仍然有效。

**板端元信息自动读取（2026-11-11 起）**：`board_api.fetch_server_meta()` 从板端
`/health` 读取 `model` / `version` / `context_len` / `model_class` / `npu`，由各结果产出
脚本写入结果 JSON 的 `meta` 字段；报告生成器只格式化该字段，不联网、不写死型号、
硬件或版本号。`llm_stress.py --context-len` 也改为从 `/health` 自动取值，读不到才需
显式指定。换模型 / 换板 / 升级后，报告与压测守卫会跟着板端自动变化。

### 1. 预检（数秒）

```bash
python health_check.py
# 交付 / 换板后做一次完整体检（基础 + 9 项深度检测）
python health_check.py --full
# 显式指定（脚本读不到连接器配置时）
python health_check.py --host 192.0.2.10:8080 --key <KEY>
```

### 2. 整套合成负载测试

```bash
# 完整流程（预检 → 压测 → 仿真 → 崩溃复现 → 报告）
python run_all.py
# 快速模式（缩短各段时长，适合冒烟）
python run_all.py --quick
# 包含极限段（可能把服务压崩，仅在需要验证崩溃边界时使用）
python run_all.py --limits
```

### 3. 真实公文场景测试

```bash
python docx_corpus.py                      # 仅在需要重新画像时（语料已脱敏入库，通常无需重跑）
python llm_realworld.py --only a,b,c,d,e --concurrency 3
python make_rw_report.py --model <模型名>   # 生成 report_realworld.html / .md
```

`make_rw_report.py` **只把结果数据格式化为可读表格**，不下结论、不做可用性判断、
不给工程建议；模型名也可由 `RKLLM_MODEL` 环境变量或结果 JSON 的 `model` 字段提供。
最终结论由阅读报告的人 / Agent 基于表中数据自行做出，另文记录。

### 4. 导出数据表

```bash
python export_csv.py            # 并发曲线 / 压测明细 / 仿真时间线 三张 CSV
```

## 五、使用须注意（来自实测结论）

### 语料必须由人提供（设计边界，不是待补的能力）

自动化能覆盖的是**合成负载**（`run_all.py` 串起来的那条链）：固定 prompt、递增长度、
并发阶梯、崩溃探针——它们不需要语料，回答的是"这块板子撑不撑得住"。

真实场景链（`docx_corpus` → `llm_realworld` → `make_rw_report`）必须人工准备：

- `docx_corpus.py` 顶部的 `CORPUS` 列表指向你手上的 docx（脚本只读，不改原件）；
- `llm_realworld.py` 的 A~E 组任务写死，但"整篇润色 / 长文改写"必须投喂真实文本才有意义；
- 输出质量只能人看 `results/realworld_samples/*.txt` 判断——术语有没有保留、格式合不合规，
  脚本打不出这个分。

两条原因：① 语料通常含业务内容，不该进仓库；② "改写得好不好"不是脚本能给的分，
把判断自动化只会得到一个看着精确、实际无意义的数字。

所以标定配置时的分工是固定的：**机器量延迟与吞吐，人给文本与质量结论**。报告只负责把
量到的东西摆清楚，最后填进 `run_all.py --host/--key` 的那组参数由人确认。

### 历史观察（早期版本，勿当作当前行为）

以下条目来自早期版本的实测，部分已在后续版本修复。**它们不是当前版本的结论**；
每次换模型 / 换板 / 升级后应以本轮结果重新判定，不要照抄：

- 曾观测到 `max_tokens` 不被遵守、超发且 `finish_reason` 仍为 `stop`；后续版本已按请求上限截断。
- 曾观测到长输出（约 1000 token 以上）退化为重复字符流并串入无关英文；后续版本未复现。
- 曾在长 prompt 下偶发进程崩溃，依赖守护进程拉起；本轮 A~E 全组真实公文测试观测到 0 次崩溃。
- 曾在特定窗口下建议单请求输入控制在约 2000 字；实际窗口由板端 `/health` 的
  `context_len` 声明，脚本已改为自动读取，不再写死。
- 单 NPU 上下文串行，并发无吞吐增益、只增加排队延迟——这条属于架构约束，仍成立。
- 流式能让首字显著提前出现，对话式前端应使用流式——这条属于协议特性，仍成立。

### 职责边界（2026-11-11 定）

- **测试脚本**：负责采集。板端元信息（模型 / 版本 / 上下文 / NPU）由
  `board_api.fetch_server_meta()` 从 `/health` 自动读取，随结果 JSON 的 `meta` 字段落盘。
- **报告生成器**：只把结果数据格式化为可读表格，**不下结论、不做可用性判断、不给工程建议**，
  也不在运行时联网。模型 / 版本 / 上下文 / NPU 一律读结果字段，读不到显示 `unknown`。
- **最终结论**：由人（或 Agent）基于报告数据另文给出，例如
  `模型测试报告/<模型名>测试/` 下的结论文档。
- 脚本内不写死具体型号、硬件、版本号；需要举例时用 `<MODEL>`、`<deb 路径>` 等占位符。

### 脱敏与入库约定

- `results/*`、`corpus/`、`csv/`、`report*.html|md`、`realworld_samples/` 均为**运行产物**，
  被 `.gitignore` 排除；`results/extra.json` 是人工补充数据，白名单放行。
- 报告生成器输出目标地址时统一替换为 RFC5737 文档段（`192.0.2.x`）；运行产物本身可能仍含
  真实内网地址、本机绝对路径与用户名，**归档到资料库或贴进交付件前必须单独脱敏**。
- 入库前检查：真实内网地址、本机用户名、API key / 令牌、未脱敏的公文原文与输出样本。
