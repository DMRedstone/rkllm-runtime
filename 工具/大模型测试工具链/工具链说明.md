# 大模型测试工具链 — 板端大模型推理服务测试

面向 RK3588（OrangePi 5 Plus 8G）上 `rkllm serve` 部署的大模型服务，提供压力测试、客户端行为仿真、真实公文场景测试与报告生成的完整闭环。

被测目标示例：`http://192.0.2.10:8080`，模型 `qwen3.5-4b_w8a8_rk3588`。

---

## 一、脚本清单（文件名前缀数字 = 实际运行顺序）

### 00–01 入口与预检

- `00_run_all.py` — 一键编排入口（推荐从这里开始）
依次执行：预检 → 压测 → 仿真 → 崩溃复现 → 生成报告。
板端 NPU 是独占资源，脚本自动串行化，并在步骤之间轮询 `/health` 等待守护进程把崩溃的服务拉起。

- `01_health_check.py` — 服务健康 / 连通性检查（由三个同功能脚本合并而成，详见第二节）
默认做基础 3 项（`/health`、`/v1/models`、端到端对话），数秒完成，适合压测前预检；
加 `--full` 追加 7 项深度检测（鉴权拒绝、长 system 应答、system 模板污染、system+多轮、
system-only 探测、流式 `[DONE]` 收尾、超长 prompt 拒绝），适合交付 / 换板后的完整体检。
退出码 0=健康、1=异常，可直接接入 CI。

### 02–06 合成负载链（由 `00_run_all.py` 自动串行编排）

- `02_llm_stress.py` — 压力与极限测试
`A` 单请求延迟基线 · `A2` 流式 vs 阻塞（首字延迟）· `B` 并发→吞吐曲线（p50/p90/p99）·
`C` 持续耐力（延迟漂移）· `D` 过载 / 背压 · `E` 超长 prompt 守卫 + 畸形 body。
段序「先温和、后敌意」：可能压垮服务的用例放最后，每段后做存活探测以精确定位崩溃点。

- `03_llm_simulate.py` — 客户端行为仿真
握手 / 多轮对话 / 长文档粘贴 / 中断（流式中断线）/ 会话切换 / 后台标题（与对话并发）/ 多 VU 混合负载。

- `04_crash_probe.py` — 并发崩溃隔离复现
逐个隔离触发条件并量化复现率（`--repeat N`）。

- `05_make_report.py` — 合成负载报告生成（读 `results/stress_*.json` + `simulate_*.json`）

- `06_export_csv.py` — 结果导出 CSV（并发曲线 / 压测明细 / 仿真时间线，Excel 友好）

### 07–09 真实公文场景链（独立支线：语料 → 测试 → 报告）

- `07_docx_corpus.py` — 真实 docx → 纯文本语料 + 规模画像（只读源文件，不改动原件；语料清单在文件顶部 `CORPUS` 中配置）

- `08_llm_realworld.py` — 真实公文场景测试
`A` 串行任务 / `B` 分段处理 / `C` 多轮迭代 / `D` 并发 / `E` 批量；内置崩溃自愈重试。

- `09_make_rw_report.py` — 真实场景报告生成（自动合并各组最新结果 + 语料画像）

运行期自动产生：`results/`（结构化 JSON、`realworld_samples/` 完整输出）、`corpus/`、`csv/`、`report*.html|md`。

```bash
python 01_health_check.py --host 192.0.2.10:8080 --key <KEY>
# 交付 / 换板后做一次完整体检（基础 + 7 项深度检测）
python 01_health_check.py --host 192.0.2.10:8080 --key <KEY> --full
```

### 2. 整套合成负载测试

```bash
# 完整流程（预检 → 压测 → 仿真 → 崩溃复现 → 报告）
python 00_run_all.py --host 192.0.2.10:8080 --key <KEY>
# 快速模式（缩短各段时长，适合冒烟）
python 00_run_all.py --host 192.0.2.10:8080 --key <KEY> --quick
# 包含极限段（可能把服务压崩，仅在需要验证崩溃边界时使用）

```

```bash

```

### 4. 导出数据表

```bash

```

## 五、使用须注意（来自实测结论）

1. NPU 是独占资源：压测与仿真不能同时跑，否则结果互相污染。`00_run_all.py` 已内置串行编排。

1. 服务端不遵守 `max_tokens`：请求 8/16/64/128/256 实际输出 10/20/97/200/370（超出 25%~56%），
`finish_reason` 仍为 `stop`。客户端必须自行限制输出长度 + 设硬超时。

1. 长文本生成会退化：输出超过约 1000 token 时输出塌陷（退化为重复字符流并串入无关英文）。
长文一律分段处理（200~300 字/段）。

1. 上下文窗口 4096 token：单请求输入建议不超过约 2000 字。

1. 服务偶发崩溃：真实长 prompt（1000~2000 字）触发概率偏高，有守护进程自动拉起（数十秒内）。
脚本须带崩溃容错重试。

1. 并发无吞吐增益：NPU 单请求串行，并发只增加排队延迟。建议串行调用。

1. 流式能让首字提前约 92% 出现（实测 0.89s vs 阻塞 10.91s），对话式前端应使用流式。
