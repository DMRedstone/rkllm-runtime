口径正本为同目录《工具链说明》；本文件只记开发过程与决策理由。
2026-10-19 之前的工具链修复记在 `文档/开发记录.md` §11.8（deb 打包线记录里），

## 2026-10-19：内容形态覆盖（截断 / 退化 / 串包 / 流式一致性 / overrun）

### 一、起因

使用方提的准确：**性能测试跑完，无法验证返回的内容是否可用，最后还得人读**。

这句话把「可用」劈成了两半：

| | 例子 | 谁来判 |
| --- | --- | --- |
| **语义可用性** | 改写是否保留术语、摘要是否抓到重点、公文格式是否合规 | 只能人读 |
| **形态可用性** | 是否被截断、是否塌成重复词流、是否为串包（拿到别人的答案）、流式是否丢字 | **机器能判** |

第二类在改造前几乎是空白：`finish_reason` 只在真实场景脚本里记了一笔，报告里那句
「均为 stop」是**写死的断言**而非统计；并发段只看状态码与延迟，串包完全看不出来；
流式只比首 token 延迟，不比内容。

### 二、新增 `quality.py`

纯标准库、无 HTTP 依赖的形态分析模块，压测采集与报告渲染共用同一套口径。

| 函数 | 判什么 | 阈值来源 |
| --- | --- | --- |
| `finish_reason_stats` | `stop` / `length` / 空响应分布 | `length` 即被硬截断 |
| `overrun_stats` | 实际 token ÷ 请求 max_tokens | 配置项 `overrun` 的依据 |
| `degen_score` | 8-gram 重复率（0.7）+ 字级熵（0.3） | 实测：正常长文本 0.00，重复词流 0.74 |
| `longest_repeat_run` | 最长整段复现长度 | 正常 0 字，退化 132 字 |
| `mojibake_ratio` | U+FFFD 占比 | 多字节字符在字节预算处被切断 |
| `stream_parity` | 阻塞与流式拼接的一致性 | `identical`/`equivalent`/`mismatch`/`empty` |
| `check_attribution` | 并发响应是否回到自己的请求 | `foreign>0` 即串包 |

**退化分为什么是「重复 0.7 + 熵 0.3」而不是各半**：实测区分度差一个量级——正常长文本
的 8-gram 重复率 0–0.1，重复词流能到 0.9；而两者的字级熵只差 6.2 vs 3.5。各半权重
会让「字符种类多但整段复现」的塌陷（`杭州是一座很好的城市。` ×12）只判到 0.52，卡在
可疑区间。改权重后同一文本 0.74，稳定越过 0.55 的判定线。

阈值：`<0.35` 正常，`0.35–0.55` 可疑（建议人工复核），`>0.55` 退化。

### 三、`llm_stress.py` 的三段新用例

| 段 | 内容 | 为什么不能靠现有段 |
| --- | --- | --- |
| **A2 扩展** | 流式与阻塞的**内容**比对 | 原 A2 只比 TTFT；流式丢字、重复首字、`[DONE]` 前缺尾块都表现为内容不一致，延迟上完全正常 |
| **A3** | 并发下每请求埋唯一标记 `MKxxQZ`，校验响应归属 | D/S 段只看状态码与延迟，**串包测不出来**——而它的后果是用户拿到别人的答案 |
| **A5** | 三档 `max_tokens` 各发 2–3 次，采 `finish_reason`、实际 token、形态指标 | `overrun` 一直靠反推，没有实测值；退化只在真实场景里偶然看到 |

A3 把「未照做」（模型没遵循指令）与「串包」（服务端串了请求）分开计数：前者常见且
无害，后者必须当故障处理，混在一起会淹没真正的信号。

A5 跑完主动 `/v1/reset`：这一段灌进较长输出，不清掉会污染后续段的上下文。

### 四、报告新增「内容形态（机器可判的部分）」

`make_report.py` 加 `shape_markdown()` / `shape_html()`，两版同步渲染三张表：串包归属、
流式一致性、输出长度与形态。节首明确写「语义质量无法自动评分，须人工阅读
`results/realworld_samples/`」——避免读者把形态指标误当成质量评分。

`overrun` 的取值指引也写进了表下注释：取中位数与 1.5 之间的较大者。

### 五、顺带修掉的三个既存缺陷

跑端到端时暴露的，都不是本次新写的代码：

1. **`Board.reset()` 不存在**（`llm_stress:383` 调用）。11.9 把 HTTP 层统一到
   `board_api.py` 时漏掉了这个方法，C 段耐力测试一跑就 `AttributeError`。
   也就是说 **11.9 之后 C 段从未成功跑通过**。补 `reset()`（只认 200/204），
   两份 `board_api.py` 同步。
2. **`overload()` 里 `round_index` 未定义**（D 段）。变量名是旧版循环的遗留，
   改成 `enumerate(ladder)` 的 `index`。D 段同样从未跑通。
3. **`load()` 不检查文件存在**。docstring 写着"文件不存在返回 None"，实现只判了
   `path` 为空；`extra.json` 是可选的（渲染处有 `if extra and` 守卫），缺了它却
   会让整个报告生成失败。

三个都属于「代码写完后没跑过那条路径」。C/D 两段是压测的主要段，说明工具链的
执行覆盖本身也需要回归——这条记在遗留里。

### 六、验证

- `quality.py` 17 项断言：正常/退化文本的 degen 区分（0.00 vs 0.74）、最长复现
  （0 vs 132）、finish_reason 分布、overrun 中位与最大值、流式四态、串包判定
  （并验证「未照做」不误报 `CROSS_TALK`）、乱码检出。
- 假服务端端到端：`llm_stress --quick --skip-limits` 跑完 A/A2/A3/A5/B/C/D 全段，
  退出码 0；结果 JSON 里 A2/A3/A5 记录齐全；`make_report` 退出 0，md 与 html
  都含新章节。
- 构造「有问题的」结果验证告警路径：串包加粗、截断率 67%、退化分 0.82、
  最长复现 240 字、overrun 1.62 全部正确渲染；无数据时不渲染该节。

### 七、遗留

- **C/D 段长期未被执行**，本次才暴露两个崩溃。`run_all.py` 应在编排时把「某段抛异常」
  与「服务崩溃」区分开并给出明确提示，否则下次还会被当成"跑完了"。
- 退化分只覆盖「整段重复」这一种塌陷形态；「串入无关模板」「中英混杂」没有指标，
  仍需人看。
- A5 的长档（384 token）在弱板子上单次可能上百秒，`--quick` 已降为 32/128 两档。
- 真实场景链（`docx_corpus` / `llm_realworld`）仍必须人工提供语料——见《工具链说明》§五。

## 2026-10-20：新增 verify_server.py（服务端源码级回归）

### 一、为什么加

1.3.1-15 被外部审查抓到 4 个**新引入**的问题，全是 selftest 覆盖不到的路径：
`finally` 里的锁释放、看门狗线程的生命周期、慢速 socket、`stop` 与 usage 的耦合。
这些问题都没有触发过崩溃，也都不需要模型，但每一个都足以让服务在特定条件下
永久不可用或悄悄算错账。缺一条能秒级复现它们的回归，下次修改还会再犯。

### 二、怎么做的

- 直接 `importlib` 加载 `cli/rkllm.py` 源码（不是装好的命令），因此能拿到
  `_stream_guard`、`_read_raw_body`、`JSON_HINT` 这些内部对象；
- 起真 HTTP 服务（`Server` + 假引擎），断言走真实协议路径——不是直接调函数，
  因为问题恰恰出在协议层（keep-alive 复用、Content-Length 声明、超时）；
- 要测"stderr 不可写"这种生产环境才有的条件，用两个测试桩：
  `_BrokenStderr`（写就抛 `BrokenPipeError`）与 `_StubThread`（`start()` 同步
  执行 target、`is_alive()` 恒返回 True，逼出 join 超时分支）；
- 路径不写死：默认从脚本位置推导仓库内的源码，可用 `--source` 或 `RKLLM_SOURCE`
  覆盖；纯标准库，只读，不占端口。

### 三、踩到的坑

- 第一版想用"真让推理线程 hang"来测锁释放，结果生成器挂在 `sink.get()` 上，
  主线程既不能 `close()` 也拿不到控制权，测试直接死锁。改用 `_StubThread` 后
  才走到目标分支；
- 第一版假引擎漏了 `abort()`：流式 `stop` 命中时服务端调 `engine.abort()` →
  `AttributeError` → 工作线程崩溃、连接中断，表现为"流式响应没有 usage"。
  这反而说明 `stop` 分支确实走到了 `abort()`，是测试桩的错不是被测代码的错。
- 断言"抛出的就是原始异常"时写成了 `isinstance(exc, RKLLMError)`，实际
  `_Failure` 不是 `RKLLMError` 子类，断言误报。

### 四、验证

`verify_server: 12 passed, 0 failed`；同一轮 `rkllm selftest` 27 passed /
1 failed（`@VERSION@` 占位符）/ 2 skipped（需板端）。

## 2026-10-20 深夜 ~ 10-21：报告生成器改数据驱动 + 15 版全量测试

### 一、make_report.py：结论写死被数据打脸（第二次同类教训）

第五轮对 make_report.py 的一次审查抓到：执行摘要 4 条与「发现与建议」8 行**全部写死成
1.3.1-13 的结论**（"无背压""max_tokens 不被遵守""发生过一次崩溃"）。14 版把前两条修掉
之后，同一份生成器产出的报告仍然在说那三句话——结论与数据对不上，比没有报告更糟。

修法：加 `derive(stress, sim, extra, crash)`，摘要、建议表全部由 `results/*.json` 推导，
算不出来的不写。顺带修掉两个潜伏问题：crashprobe JSON 之前根本没接进报告；建议表的
"级别"列取了 `sev` 却没渲染，四列表头丢掉了严重度。报告头补 `extra.json` 的 `release`
字段标注被测版本。

### 二、make_rw_report.py：同样的病，同样的修法（第三次咬人）

公文报告的「核心结论」与「关键缺陷：长文本生成退化」整章也是 13 版写死文本，而 15 版
实测 A6 整篇润色（2130 字）成功、D 组并发零崩溃——报告说"不可用"，数据说"成功"。

加 `derive_rw(data, corpus)`，关键改进是**把「存疑」按 note 三类归因**：

| note 特征 | 归因 | 处理 |
| --- | --- | --- |
| `finish=length` | 输出被 max_tokens 正确截断 | 预期行为，不是缺陷 |
| `疑似照抄(重合N%)` | 模型对改写任务的保守行为 | 模型行为，非服务缺陷 |
| `中文占比低(N%)` | **真正的生成退化** | 只有它才触发缺陷章节 |

只有存在「中文占比低」项才渲染「关键缺陷」章，否则渲染「长输出任务表现」（A6 实测数据
+ 与 13 版塌陷行为的对照）。摘要各条全部来自 group_a~e。

**教训**：报告生成器的结论永远不能写死，这条已咬人三次（make_report、make_rw_report、
以及当年 make_report 的摘要硬编码）。写报告的代码和被测代码一样需要数据驱动的纪律。

### 三、verify_server.py 扩到 17 项

第五轮 413/408 关连接、reset chunked 411 落地后，回归脚本从 12 项扩到 17 项，新增：

- `413 后关闭连接并声明 Connection: close`（读到 EOF 才算关闭，单次 recv 会误判）
- `reset 拒绝 chunked body（411）`
- `401 计入 rejected 且 GET 连接可复用`
- `NPU 忙的 503 带 CORS + Retry-After 且计入 rejected`（占住 infer_lock +
  `queue_timeout=0.01` 逼出该出口）
- `404 计入 rejected 且带 Connection: close`

### 四、corpus.json 重建：摆脱 python-docx 依赖

corpus/ 不入库导致 corpus.json 丢失，而 `docx_corpus.py` 依赖未安装的 python-docx。
没有装包，用标准库 zipfile + ElementTree 重写提取（document.xml 的 w:p / w:tbl 按文档
顺序收集，clean_text 与 est_tokens 逻辑照搬），生成的 corpus.json schema 与字符数和
10-15 轮逐一吻合。若要长期解决，可把 docx_corpus.py 也改成标准库实现。

## 2026-11-10 ~ 11-11：配置自读、元信息自动读取、报告纯格式化（第四次咬人的结论写死）

### 一、起因

换模型后启动失败（模型文件缺权重）修好，用新模型重跑真实公文 A~E 全组，发现工具链
仍带着旧模型的痕迹：`make_report.py` 标题写死旧型号、两条 findings 无条件追加（"上下文
窗口 4096"、"参数不校验"）、`crash_probe.py` 会话素材自称旧型号、`llm_stress.py` 把
`--context-len` 默认写死 4096。这和前面三次「结论写死被数据打脸」是同一类病，只是从
结论蔓延到了**元信息与测试素材**。

另外每次跑测试都要手工传 `--host/--key`，而连接器安装目录里本来就有 `mcp.toml`。

### 二、配置自读（`board_api.py`）

新增 `connector_config_path()` / `load_connector_config()` / `default_host()` / `default_key()`：
标准库 `tomllib` 读连接器 `mcp.toml` 的 `target_endpoint` / `target_api_key`，
优先级为 `RKLLM_HOST` / `RKLLM_KEY` / `RKLLM_API_KEY` > 配置文件，
路径可用 `RKLLM_MCP_CONFIG` 覆盖。6 个脚本（health_check / llm_realworld / llm_stress /
llm_simulate / crash_probe / run_all）的 `--host/--key` 默认值接入，显式传参仍有效。

key 只在进程内存中使用，**不打印、不写日志、不入库**。安全层曾拒绝「把 key 读出再注入
环境变量」的做法，改由脚本自读配置后放行——这条边界值得记住。

### 三、板端元信息自动读取

`board_api.fetch_server_meta()` 从 `/health` 读 `model` / `version` / `context_len` /
`model_class` / `npu.detail`（`/v1/models` 与 `/v1/capabilities` 也有同类字段），失败返回空 dict。
4 个结果产出脚本（stress / simulate / realworld / crash_probe）把结果写进 JSON 的 `meta` 字段——
**元信息在采集侧落地**，报告生成器仍只格式化、不联网，离线也能复现。

`llm_stress.py --context-len` 默认值从 4096 改为 `None`，运行时复用
`probe_environment()` 已拿到的 health dict；读不到才要求显式指定。

### 四、报告生成器收敛为纯格式化

`make_rw_report.py` 重写：删掉全部 `derive_rw()` 推导、写死的旧模型名、"3 次崩溃"、
"整篇润色不可用"、工程建议等段落，只把 A~E 各组结果摆成 HTML / Markdown 表格。
模型名 / 版本 / 上下文 / NPU 由结果 `meta` 提供，可用 `--model` / `RKLLM_MODEL` 覆盖，
读不到显示 `unknown`。新增 `redact()` 把内网地址替换为 RFC5737 文档段。

`make_report.py` 同步：标题去掉写死型号、删两条无条件 findings（改为由实测条件推导）、
target 输出前 `redact()`、新增 `result_meta()` 读结果字段。

**职责边界定死**：脚本采集 → 报告只格式化 → 最终结论由人 / Agent 另文给出。

### 五、`redact()` 的一个真 bug

初版正则只匹配 IPv4 前三段，`10.0.0.14` 被替换成 `192.0.2.10.14`。改为先匹配完整四段
`\b\d{1,3}(?:\.\d{1,3}){3}\b` 再判断网段，并做单元校验：私网段替换、
文档段 `192.0.2.x` 与回环 `127.0.0.1` 保持不变。

- 会话素材、长文语料、测试 prompt 中的具体型号 / 硬件表述改为中性文案。
- 注释、示例命令、错误提示里的具体版本号（16 处）改为泛化表述或 `<upstream>-<revision>` /

### 八、教训（第四次）

「结论写死」不只是报告正文：标题里的型号、会话素材里的自称、压测脚本里的上下文窗口、
注释里的版本号，都是同一个病的不同位置。**凡是板端能自报的信息，一律从板端读；
凡是人对数据的判断，一律不进脚本。**
